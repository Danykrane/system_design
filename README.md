## 1. Тема и целевая аудитория

### 1.1. Тип сервиса

| Параметр | Значение |
| -------- | -------- |
| Учебное название | **MeetFlow** |
| Тип сервиса | Zoom-подобный сервис видеовстреч |
| Основной сценарий | Групповая онлайн-встреча: аудио, видео, демонстрация экрана, чат и запись |
| Реальные аналоги | Zoom, Microsoft Teams, Google Meet |

### 1.2. Рыночная ниша и реальные аналоги

| Аналог | Метрика | Что подтверждает |
| ------ | ------- | ---------------- |
| Microsoft Teams | 320 млн monthly active users, FY24 Q1 (октябрь 2023) [^1] | Масштаб аудитории коммуникационного сервиса |
| Microsoft Teams | 115 млн daily active users, октябрь 2020 [^2] | Дневную аудиторию для расчета |
| Zoom | Более 300 млн участий во встречах в день, апрель 2020 — проспект Zoom в SEC; это участия, а не уникальные пользователи [^3] | Ежедневную нагрузку именно на видеовстречи |
| Zoom | Средняя встреча — 54 минуты и 10 участников, данные за 15.11.2020–15.11.2021 [^4] | Базу продуктовой оценки |
| Zoom | $4.8688 млрд выручки за FY2026 и 4 468 клиентов с TTM-выручкой больше $100 000 [^10] | Актуальность ниши в 2026 году |

### 1.3. Функционал MVP

| № | Функция MVP | Кратко | Метрика для расчета |
| -: | ----------- | ------ | ------------------- |
| 1 | Создание встречи | Мгновенная или запланированная встреча | `MF_MEETINGS_DAY`, `POST /meetings` |
| 2 | Подключение к встрече | Вход по ссылке или приглашению | `MF_DMP`, `POST /meetings/{id}/join` |
| 3 | Групповая аудио- и видеосвязь | 720p group video | `MF_VIDEO_UP_MBPS`, `MF_VIDEO_DOWN_MBPS`, `MF_AUDIO_MBPS` |
| 4 | Демонстрация экрана | Участник показывает экран | `MF_SCREEN_MBPS_MAX` |
| 5 | Чат во время встречи | Текстовые сообщения участников | `MF_CHAT_MSG_LIMIT`, `MF_CHAT_PER_JOIN` |
| 6 | Облачная запись | Организатор включает запись встречи | `MF_RECORD_QUOTA_GB`, `MF_RECORDING_SIZE_GB` |

### 1.4. Ключевые продуктовые решения

| Решение | Значение для MVP | Что считается дальше |
| ------- | ---------------- | -------------------- |
| Расчет от групповой встречи | В средней встрече `MF_MEET_SIZE = 10` участников | Число встреч в сутки |
| Базовое качество — 720p group video | Требования Zoom к сети [^5] | Видеотрафик |
| Облачная запись | Сохраняет видео, аудио и текст чата [^7] | Хранилище записей |
| Квота на записи | У Zoom Pro/Business — 10 GB на пользователя [^8] | Верхняя граница хранилища |
| Частота чата — допущение | Есть лимит длины сообщения, но нет публичной частоты [^6]: берем 5 сообщений на участие | Нагрузка и хранилище чата |
| Данные встреч хранятся 30 дней | Метаданные, участники, чат и записи старше 30 дней удаляются | Объем хранения (2.3) |
| Худший случай для записей | Записывается каждая встреча: реальная доля публично неизвестна | Хранилище и его стоимость (2.3, 11.4) |
| Материковый Китай не обслуживаем | Нужен отдельный локальный контур: локализация данных и блокировки трафика | Доли ДЦ (3.2) |

### 1.5. Целевая аудитория

| Параметр | Значение |
| -------- | -------- |
| География | Весь мир, кроме материкового Китая. Zoom используют почти в 200 странах и территориях [^4]; крупнейшие экономики среди обслуживаемых стран — США, Германия, Япония, Великобритания, Индия [^11]. Обслуживаем из 8 ДЦ (п. 3.2) |
| Месячная аудитория | `MF_MAU = 320 000 000` |
| Дневная аудитория | `MF_DAU = 115 000 000` |
| Участий во встречах в день | `MF_DMP = 300 000 000` |
| Средняя встреча | `MF_MEET_SIZE = 10` участников, `MF_MEET_LEN_MIN = 54` минуты |

## 2. Расчет нагрузки

### 2.1. Исходные метрики и методика расчета

| Константа | Значение | Источник / основание |
| --------- | -------- | -------------------- |
| `MF_MAU` | 320 000 000 пользователей в месяц | Microsoft Teams, FY24 Q1 (2023); более новой публичной MAU-метрики нет [^1] |
| `MF_DAU` | 115 000 000 пользователей в день | Microsoft Teams, октябрь 2020; консервативная оценка дневной аудитории [^2] |
| `MF_DMP` | 300 000 000 участий во встречах в день | Zoom, апрель 2020; один пользователь может войти в несколько встреч [^3] |
| `MF_MEET_SIZE` | 10 участников | Средняя встреча Zoom, 15.11.2020–15.11.2021 [^4] |
| `MF_MEET_LEN_MIN` | 54 минуты | Там же [^4] |
| `MF_VIDEO_UP_MBPS` / `MF_VIDEO_DOWN_MBPS` | 2.6 / 1.8 Мбит/с на участника | 720p group video, требования Zoom [^5] |
| `MF_VIDEO_HQ_MBPS` | 1.0 / 0.6 Мбит/с | Group «high-quality video» ниже 720p [^5]; профиль при отказе ДЦ (п. 9.2) |
| `MF_AUDIO_MBPS` | 0.08 Мбит/с | Верхняя граница 60–80 kbps для VoIP [^5] |
| `MF_SCREEN_MBPS_MAX` | 0.15 Мбит/с | Верхняя граница 50–150 kbps для демонстрации экрана [^5] |
| `MF_CHAT_MSG_LIMIT` | 4 000 символов | Лимит сообщения Zoom Team Chat [^6] |
| `MF_CHAT_PER_JOIN` | 5 сообщений на участие | **Допущение**: публичной частоты нет [^6] |
| `MF_CHAT_MSG_SIZE` | 1 KB в среднем, до ≈ 10 KB | Допущение |
| `MF_LIST_PER_DAU` | 3 открытия списка встреч в сутки | Допущение |
| `MF_LOGIN_PER_DAU` | 1 логин в сутки | Допущение |
| `MF_CHAT_HISTORY_PER_JOIN` | 1 загрузка истории чата на участие | Допущение: при входе и после переподключения |
| `MF_REC_VIEWS_PER_REC` | не больше 1 открытия на запись | Допущение, верхняя оценка |
| `MF_REC_PART_MB` | 8 MB | Часть multipart upload: запись 0.761 GB — это ≈ 95 частей, S3 допускает до 10 000 [^46] |
| `MF_RECORD_QUOTA_GB` | 10 GB на пользователя | Квота Zoom Pro/Business [^8] |
| `MF_HEARTBEAT_SEC` | 25 секунд | `pingInterval` в Socket.IO по умолчанию [^9] |
| `MF_K_PEAK` | **1.5** | Пиковый час / среднее за сутки; одинаково для RPS, полосы и соединений. Сервис глобальный: часовые пояса сглаживают суточную кривую |

Все числа разделов 2–6, 9 и 11 считает скрипт [`resource/calc/meetflow_calc.py`](resource/calc/meetflow_calc.py): чтобы поменять допущение, достаточно изменить константу и перезапустить. ВВП для долей ДЦ (п. 3.2) — в [`imf_weo_2026apr_gdp_2025.json`](resource/calc/imf_weo_2026apr_gdp_2025.json).

### 2.2. Продуктовая оценка видеовстреч

| Название | Расчет | Значение |
| -------- | ------ | -------: |
| `MF_MEETINGS_DAY` | `MF_DMP / MF_MEET_SIZE` = `300 000 000 / 10` | **30 000 000 встреч/сутки** |
| `MF_JOINS_PER_DAU_DAY` | `MF_DMP / MF_DAU` = `300 000 000 / 115 000 000` | **2.61 подключения/DAU/день** |
| `MF_CREATED_MEETINGS_PER_DAU_DAY` | `MF_MEETINGS_DAY / MF_DAU` = `30 000 000 / 115 000 000` | **0.26 созданных встреч/DAU/день** |
| `MF_PARTICIPANT_MIN_DAY` | `MF_DMP * MF_MEET_LEN_MIN` = `300 000 000 * 54` | **16 200 000 000 participant-minutes/сутки** |
| `MF_AVG_ONLINE_PARTICIPANTS` | `MF_PARTICIPANT_MIN_DAY / 1440` | **11 250 000 участников online в среднем** |
| `MF_PEAK_ONLINE_PARTICIPANTS` | `MF_AVG_ONLINE_PARTICIPANTS * MF_K_PEAK` = `11 250 000 * 1.5` | **16 875 000 участников online в пик** |
| `MF_PEAK_WSS_CONNECTIONS` | `= MF_PEAK_ONLINE_PARTICIPANTS`, одно WSS-соединение на участника | **16 875 000 одновременных соединений** |
| `MF_PEAK_ACTIVE_MEETINGS` | `MF_PEAK_ONLINE_PARTICIPANTS / MF_MEET_SIZE` | **1 687 500 встреч одновременно** |
| `MF_HEARTBEAT_EVENTS_DAY` | `MF_PARTICIPANT_MIN_DAY * 60 / MF_HEARTBEAT_SEC` | **38 880 000 000 heartbeat-событий/сутки** |
| `MF_CHAT_MESSAGES_DAY` | `MF_DMP * MF_CHAT_PER_JOIN` = `300 000 000 * 5` | **1 500 000 000 сообщений/сутки** |
| `MF_MEETING_LIST_VIEWS_DAY` | `MF_DAU * MF_LIST_PER_DAU` = `115 000 000 * 3` | **345 000 000 открытий списка/сутки** |
| `MF_LOGINS_DAY` | `MF_DAU * MF_LOGIN_PER_DAU` | **115 000 000 логинов/сутки** |

Проверка по аналогу: на 31.10.2020 Zoom раскрывал годовой run rate более 3.5 трлн минут встреч [^3] — это ≈ 9.6 млрд минут в сутки. У нас 16.2 млрд, потому что каждый участник сидит во встрече все 54 минуты. Ошибка в безопасную сторону: онлайн, трафик и число SFU завышены, а не занижены.

### 2.4. Сетевой трафик и RPS

#### Сетевой трафик

| Тип трафика | Битрейт на участника | Суточный объем | Средний bandwidth | Пиковый bandwidth |
| ----------- | -------------------: | -------------: | ----------------: | ----------------: |
| Video upload | 2.6 Мбит/с | **315 900 000 GB** | **29 250 Gbps** | **43 875 Gbps** |
| Video download | 1.8 Мбит/с | **218 700 000 GB** | **20 250 Gbps** | **30 375 Gbps** |
| Audio VoIP | 0.08 Мбит/с | **9 720 000 GB** | **900 Gbps** | **1 350 Gbps** |
| Screen sharing, верхняя граница | 0.15 Мбит/с | **18 225 000 GB** | **1 687.5 Gbps** | **2 531.25 Gbps** |
| **Медиа клиент ↔ SFU, итого** | 4.63 Мбит/с | **562 545 000 GB** | **52 087.5 Gbps** | **78 131.25 Gbps** |
| Поток в запись SFU → recording workers, worst-case | 1.88 Мбит/с на встречу | **22 842 000 GB** (= объем записей) | **2 115 Gbps** | **3 172.5 Gbps** |

```text
суточный объем, GB  = MF_PARTICIPANT_MIN_DAY * 60 * битрейт_Мбит/с / 8 / 1000
avg_bandwidth_Gbps  = MF_AVG_ONLINE_PARTICIPANTS * битрейт_Мбит/с / 1000
peak_bandwidth_Gbps = avg_bandwidth_Gbps * MF_K_PEAK
rec_stream_Gbps     = (MF_AVG_ONLINE_PARTICIPANTS / MF_MEET_SIZE) * (1.8 + 0.08) / 1000 * K
запись, GB/сутки    = MF_PARTICIPANT_MIN_DAY / MF_MEET_SIZE * 60 * 1.88 / 8 / 1000   # битрейт на встречу
```

Поток в запись не уходит в интернет: SFU отправляет его recording workers внутри ДЦ как еще одному подписчику встречи. Он нагружает SFU и воркеры, поэтому учтен в разделе 11.

#### RPS по основным методам

| Метод / событие | Событий в сутки | Средний RPS | Пиковый RPS |
| --------------- | --------------: | ----------: | ----------: |
| `POST /auth/login` | `MF_LOGINS_DAY` = 115 000 000 | **1 331** | **1 997** |
| `POST /meetings` | `MF_MEETINGS_DAY` = 30 000 000 | **347** | **521** |
| `POST /meetings/{id}/join` | `MF_DMP` = 300 000 000 | **3 472** | **5 208** |
| `POST /meetings/{id}/leave` | `MF_DMP` = 300 000 000 | **3 472** | **5 208** |
| `WS /presence/heartbeat` | `MF_HEARTBEAT_EVENTS_DAY` = 38 880 000 000 | **450 000** | **675 000** |
| `POST /meeting-chat/messages` | `MF_CHAT_MESSAGES_DAY` = 1 500 000 000 | **17 361** | **26 042** |
| `GET /meeting-chat/messages?after_seq=N` | `MF_DMP * MF_CHAT_HISTORY_PER_JOIN` = 300 000 000 | **3 472** | **5 208** |
| `GET /users/{id}/meetings?limit=100` | `MF_MEETING_LIST_VIEWS_DAY` = 345 000 000 | **3 993** | **5 990** |
| `POST /recordings/metadata` | до `MF_MEETINGS_DAY` = 30 000 000 | **до 347** | **до 521** |
| `GET /recordings/{id}` — ссылка на скачивание | до `MF_MEETINGS_DAY * MF_REC_VIEWS_PER_REC` = 30 000 000 | **до 347** | **до 521** |
| WS push: чат и события join/leave остальным участникам | `(chat + join + leave) * (MF_MEET_SIZE − 1)` | **218 750** | **328 125** |

```text
avg_RPS  = events_per_day / 86400
peak_RPS = avg_RPS * MF_K_PEAK
```

Пики считаются от неокругленных значений, поэтому суммы округленных чисел в таблицах могут расходиться с итогом на единицу.

`GET /recordings/{id}` отдает только presigned URL: файл клиент скачивает напрямую из object storage `home_dc` (`rec.<dc>`, п. 3.5), мимо L7 и SFU. Частота просмотров неизвестна, поэтому трафик скачивания в таблицу не входит; его тариф — в п. 11.4.

## 3. Глобальная балансировка нагрузки

Глобальная балансировка отвечает на четыре вопроса. Короткие ответы:

| Вопрос | Решение в MeetFlow | Где подробно |
| ------ | ------------------ | ------------ |
| Где стоят дата-центры | 8 ДЦ: `DC-US-EAST`, `DC-US-WEST`, `DC-BR-SAOPAULO`, `DC-UK-LONDON`, `DC-DE-FRANKFURT`, `DC-IN-MUMBAI`, `DC-SG-SINGAPORE`, `DC-JP-TOKYO`. Абстрактного пула `OTHER` нет: каждая группа стран привязана к конкретному ДЦ | 3.2 |
| Как пользователь попадает в ДЦ и как ДЦ переключаются | **DNS**: GeoDNS/GTM выбирает ДЦ по гео, latency, health и весам. **Anycast** — только для доставки DNS-запросов к авторитетным NS-серверам. Медиа переключается на уровне приложения: control plane выдает новый SFU | 3.5–3.7 |
| Где точка записи | `users` — один primary в `DC-US-EAST`; все, что относится к встрече, — в `home_dc` встречи; список встреч пользователя — локально, с асинхронной репликацией во все ДЦ | 3.4 |
| Что при отказе ДЦ или переезде пользователя | ДЦ убирается из DNS, новые встречи уходят в резервные ДЦ. Переезд не требует ни миграции данных, ни повторного логина | 3.7, 3.8, 9.2 |

«ДЦ» в работе — регион провайдера из 3 зон доступности (AZ). Отказ одной AZ закрывается резервированием внутри ДЦ (разделы 4 и 9), отказ всего ДЦ — глобальной балансировкой.

### 3.1. Функциональное разбиение по доменам

| Домен | Основная нагрузка | Куда направляется запрос | Точка записи |
| ----- | ----------------- | ------------------------ | ------------ |
| `Auth / Users` | логин, профиль | ближайший ДЦ по GeoDNS | `users` — primary `auth_pg` в `DC-US-EAST`; `user_sessions` — ДЦ, где выполнен логин |
| `Meeting Control Plane` | `POST /meetings`, `join`, `leave`, список встреч | ближайший ДЦ; `join` и `leave` проксируются в `home_dc` встречи | `meetings`, `meeting_invite_links` — `home_dc` |
| `Media Plane / SFU` | видео, аудио, screen sharing | только SFU в `home_dc` встречи, адрес приходит в ответе `join` | не хранится, это поток |
| `Presence / Heartbeat` | `WS /presence/heartbeat` | WS-endpoint `home_dc` встречи | `meetings_runtime` — Redis `home_dc` |
| `Meeting Chat` | сообщения внутри встречи | `home_dc` встречи | `chat_messages` — ScyllaDB `home_dc` |
| `Recording` | запись встречи | SFU → recording workers в `home_dc` | файлы — S3 `home_dc`, метаданные — `recording_pg` `home_dc` |
| `User meetings list` | top-100 встреч пользователя | ближайший ДЦ, чтение локальной копии | `user_meetings` пишется в `home_dc` встречи, ScyllaDB реплицирует его во все ДЦ |

`home_dc` — ДЦ, за которым закреплена встреча: control plane выбирает его при `POST /meetings`, это ДЦ, принявший запрос, то есть ближайший к организатору. Код `home_dc` записан в `meeting_id` (UUIDv8, первый байт — код ДЦ [^85]) и в invite-токен, поэтому любой ДЦ знает, куда направить `join`, без глобального справочника встреч.

#### Проверка долей и влияние на продуктовые метрики

**Проверка по аналогу.** По макрорегионам: Америка — 40.89%, EMEA — 39.75%, APAC — 19.36%. ### 3.4. Точки записи данных

Правило: **у каждого объекта одна точка записи** (primary), а чтение по возможности идет из локальной копии в ближайшем ДЦ. Тогда два ДЦ никогда не пишут один объект одновременно, и не нужен multi-master с разрешением конфликтов.

| Данные | Точка записи | Где читаются | Репликация между ДЦ | Почему так |
| ------ | ------------ | ------------ | ------------------- | ---------- |
| `users` (`auth_pg`) | **один primary на весь мир — `DC-US-EAST`**, синхронная standby в другой AZ | локальная асинхронная реплика в каждом ДЦ | streaming replication: primary → 7 реплик [^27][^89] | Глобальная уникальность `email`. Записей в пик ≤ 1 997/с (верхняя оценка: каждый DAU раз в сутки меняет профиль) — одного primary хватает |
| `user_sessions` (`session_redis`) | ДЦ логина; код ДЦ — префикс `session_id` (`us-east.<128 бит>`) | там же; другой ДЦ один раз забирает сессию по префиксу (п. 3.8) | нет, перенос по запросу | Сессия нужна там, где пользователь сейчас |
| `meetings`, `meeting_invite_links` (`meeting_pg`) | `home_dc` встречи | `home_dc` | асинхронная реплика в парный ДЦ | `join` должен видеть актуальный статус (п. 5.3) |
| `meeting_participants` (`meeting_scylla`) | `home_dc` | `home_dc` | нет: keyspace ДЦ с RF=3 по 3 AZ; снапшоты — в S3 парного ДЦ | Нужны во время встречи и для истории |
| `meetings_runtime` (`runtime_redis`) | `home_dc` | `home_dc` | нет | Эфемерное состояние, клиенты восстанавливают его при переподключении |
| `chat_messages` (`chat_scylla`) | `home_dc` | `home_dc` | нет; снапшоты — в S3 парного ДЦ | Порядок задает `chat_seq` в одном Redis `home_dc` |
| `recordings` и файлы (`recording_pg`, S3) | `home_dc` | `home_dc`, по presigned URL | метаданные — реплика в парный ДЦ; файлы — ≥ 3 копии в 3 AZ `home_dc` | Копия 685 PB в другом регионе удвоила бы самую дорогую статью расходов |
| `user_meetings` (`meeting_scylla`) | `home_dc` встречи, запись с `LOCAL_QUORUM` | ближайший ДЦ, локально | RF=3 **в каждом** ДЦ (NetworkTopologyStrategy) [^80][^81] | Read model с eventual consistency (п. 5.3): список встреч доступен в любой стране |

#### Как запись попадает в точку записи

```mermaid
flowchart TB
    subgraph USERS["users: одна точка записи на весь мир"]
        direction LR
        W["Регистрация, профиль"] --> P["auth_pg primary, DC-US-EAST"]
        P -->|"sync"| S["standby, DC-US-EAST, другая AZ"]
        P -->|"async"| R1["реплика для чтения, DC-JP-TOKYO"]
        P -->|"async"| R2["реплика для чтения, DC-DE-FRANKFURT"]
    end
    subgraph MEET["данные встречи: точка записи — home_dc"]
        direction LR
        M1["create / join встречи с home_dc = JP-TOKYO"] --> D1["meeting_pg, ScyllaDB, Redis в DC-JP-TOKYO"]
        M2["create / join встречи с home_dc = DE-FRANKFURT"] --> D2["meeting_pg, ScyllaDB, Redis в DC-DE-FRANKFURT"]
    end
    USERS ~~~ MEET
```

1. Запрос приходит в ближайший ДЦ (GeoDNS, п. 3.5).
2. Сервис определяет точку записи: для `users` это всегда `DC-US-EAST`, для данных встречи — код ДЦ из `meeting_id`.
3. Если точка записи в другом ДЦ, запрос проксируется по gRPC с mTLS [^52]. Это добавляет RTT между ДЦ — например, ≈ 153 мс Токио ↔ восточное побережье США [^87], но только для редких записей.
4. После своей записи пользователь несколько секунд читает из primary (read-your-writes), пока реплика не догонит.

**Отказ точки записи.** Внутри `DC-US-EAST` Patroni автоматически переключает primary `auth_pg` на синхронную standby в соседней AZ без потери данных [^86]. При отказе всего `DC-US-EAST` primary становится реплика в `DC-US-WEST`, но по команде дежурного (runbook): в схеме с двумя площадками второй ДЦ не может сам отличить отказ первого от обрыва связи [^97]. RPO — секунды лага репликации. Логин продолжает работать на локальных репликах; на время переключения недоступны только регистрация и изменение профиля.

### 3.5. Схема DNS-балансировки — основной механизм переключения

**Ответ на вопрос «Anycast или DNS?»: ДЦ выбирается и переключается через DNS.** Используется GeoDNS/GTM — managed-сервис с геолокацией, latency-based routing, health checks и весами пулов [^15][^16][^17]. Anycast стоит только «под» DNS: авторитетные NS-серверы GTM доступны по Anycast IP (п. 3.6).

| DNS-имя | Что выбирает | Политика | TTL |
| ------- | ------------ | -------- | --: |
| `api.meetflow.example` | VIP API edge ближайшего здорового ДЦ | geo + latency + health + веса | 30 с |
| `ws.<dc>.meetflow.example` | WebSocket edge конкретного `home_dc` | фиксированное региональное имя, приходит в ответе `join` | 30 с |
| SFU, IP:port | конкретный SFU в `home_dc` | не DNS: адрес и ICE-кандидаты приходят в ответе `join` | — |
| `rec.<dc>.meetflow.example` | скачивание записей из object storage `home_dc` | региональное имя, presigned URL | 300 с |
| `static.meetflow.example` | веб-клиент и статика | CDN провайдера | по CDN |

GeoDNS определяет местоположение по IP рекурсивного резолвера или по подсети клиента из EDNS Client Subnet [^82]. Поэтому ДЦ выбирается по тому, где пользователь сейчас, а не где он регистрировался.

```mermaid
sequenceDiagram
    participant C as Клиент
    participant NS as GeoDNS / GTM (NS на Anycast IP)
    participant E as API edge ближайшего ДЦ
    participant H as home_dc встречи
    C->>NS: 1. DNS-запрос api.meetflow.example
    NS->>NS: 2. гео + latency + health + веса
    NS-->>C: 3. VIP ближайшего здорового ДЦ
    C->>E: 4. HTTPS: login, create, join
    E->>H: 5. join проксируется в home_dc по коду из meeting_id
    H-->>C: 6. join_token: meeting_id, home_dc, ws.#lt;dc#gt;, IP SFU
    C->>H: 7. WSS: presence и чат
    C->>H: 8. SRTP по UDP в SFU
```

**Время переключения.** Monitor GTM опрашивает health-endpoint каждого ДЦ; минимальный интервал у Cloudflare — 60 с на Pro, 15 с на Business, 10 с на Enterprise [^17]. Берем Enterprise: интервал 10 с и 3 неудачи подряд — ДЦ выводится из ответов за ≈ 30 с, плюс TTL 30 с. Итого новые подключения уходят в здоровый ДЦ примерно за минуту. Если резолвер кеширует дольше TTL, срабатывает fallback клиента: при ошибке он заново резолвит имя, а затем идет на резервный региональный адрес из конфигурации приложения.

### 3.6. Схема Anycast-балансировки

Anycast — один IP-адрес, который анонсируется по BGP из многих точек; пакет приходит в ближайшую по маршрутизации точку [^83]. В MeetFlow Anycast используется **только для коротких запросов без состояния на сервере**:

| Трафик | Anycast | Почему |
| ------ | ------- | ------ |
| DNS-запросы к авторитетным NS-серверам GTM | **Да** | UDP «запрос — ответ» без сессии: ответ из ближайшего PoP, устойчивость к отказу точки и DDoS [^83] |
| Статика веб-клиента | Да, через CDN провайдера | короткие запросы, контент одинаковый во всех точках |
| API `api.meetflow.example` | Нет | BGP выбирает маршрут по AS-path, а не по задержке и загрузке ДЦ: нельзя задать веса и вывести ДЦ на обслуживание. Глобальный Anycast-балансировщик есть у крупных облаков [^18], но он привязывает к сети одного облака |
| WebSocket | Нет | долгое TCP-соединение: при перестроении BGP-маршрута пакеты уйдут в другой ДЦ, где нет состояния соединения [^83] |
| RTP/SRTP медиа | Нет | встреча живет на конкретном SFU в `home_dc`, смена маршрута рвет медиасессию |

```mermaid
flowchart LR
    C1["Клиент в Японии"] -->|"DNS-запрос на 198.51.100.53"| P1["NS PoP Токио"]
    C2["Клиент в Германии"] -->|"тот же адрес 198.51.100.53"| P2["NS PoP Франкфурт"]
    P1 --> A1["GTM отвечает: VIP DC-JP-TOKYO"]
    P2 --> A2["GTM отвечает: VIP DC-DE-FRANKFURT"]
```

Оба PoP анонсируют один и тот же адрес (в примере — документационный `198.51.100.53`). Итог: Anycast ускоряет и защищает **получение DNS-ответа**, а **в какой ДЦ идти, решает GTM** — это и есть механизм переключения.

### 3.7. Регулировка трафика и переключение между дата-центрами

Регулировка идет через веса пулов в GTM; monitors регулярно проверяют endpoints и выводят нездоровый пул из ротации [^16][^17].

```text
effective_weight = geo_match * health * capacity_weight * manual_weight
```

| Ситуация | Что делаем | Кого затрагивает |
| -------- | ---------- | ---------------- |
| Норма | Пользователь → ближайший здоровый ДЦ | — |
| ДЦ перегружен | Снижаем `capacity_weight`: новые пользователи и встречи уходят в резервные ДЦ | только новые |
| Плановые работы | `manual_weight = 0` (drain): новые встречи не создаются, текущие доживают | только новые |
| ДЦ недоступен | `health = 0`, ДЦ убирается из DNS-ответов | все, см. п. 9.2 |
| Деградация пула SFU | Control plane не назначает этот пул новым встречам. При отказе SFU клиент получает адрес нового SFU по WebSocket и заново устанавливает с ним медиасоединение: новое ICE-согласование и DTLS-рукопожатие [^84] | встречи на этом SFU |

| Основной ДЦ | Резерв 1 (парный ДЦ) | Резерв 2 | Почему |
| ----------- | -------------------- | -------- | ------ |
| `DC-US-EAST` | `DC-US-WEST` | `DC-UK-LONDON` | та же страна, затем ближайший ДЦ через Атлантику |
| `DC-US-WEST` | `DC-US-EAST` | `DC-JP-TOKYO` | та же страна, затем через Тихий океан |
| `DC-BR-SAOPAULO` | `DC-US-EAST` | `DC-DE-FRANKFURT` | прямые кабели в США и Европу |
| `DC-UK-LONDON` | `DC-DE-FRANKFURT` | `DC-US-EAST` | соседний европейский ДЦ |
| `DC-DE-FRANKFURT` | `DC-UK-LONDON` | `DC-US-EAST` | соседний европейский ДЦ, затем самый емкий ДЦ через Атлантику |
| `DC-IN-MUMBAI` | `DC-SG-SINGAPORE` | `DC-DE-FRANKFURT` | ближайший ДЦ в Азии |
| `DC-SG-SINGAPORE` | `DC-JP-TOKYO` | `DC-IN-MUMBAI` | ближайшие ДЦ в Азии |
| `DC-JP-TOKYO` | `DC-SG-SINGAPORE` | `DC-US-WEST` | ближайший ДЦ в Азии, затем через Тихий океан |

Резервный ДЦ может быть меньше основного: `DC-UK-LONDON` (4.06%) не вместит `DC-DE-FRANKFURT` (35.69%). Поэтому резервы задают **порядок предпочтения**: трафик отказавшего ДЦ GTM раздает по нескольким ДЦ пропорционально свободной емкости (`capacity_weight`). Что емкости хватит, показано в п. 9.2.

### 3.8. Сценарий: вход в США, затем поездка в Японию

Вопрос: пользователь залогинился в США, а потом улетел в Японию. Что происходит?

```mermaid
sequenceDiagram
    participant C as Клиент в Японии
    participant DNS as GeoDNS
    participant JP as DC-JP-TOKYO
    participant US as DC-US-EAST
    C->>DNS: api.meetflow.example?
    DNS-->>C: VIP DC-JP-TOKYO (японский резолвер / ECS)
    C->>JP: GET /users/{id}/meetings, session_id = us-east.…
    JP->>JP: сессии нет в локальном session_redis
    JP->>US: gRPC: получить сессию us-east.…
    US-->>JP: сессия валидна, остаток TTL
    JP->>JP: сохранить сессию локально
    JP-->>C: список встреч из локальной копии user_meetings
    C->>JP: POST /meetings/{id}/join (встреча коллег, home_dc = US-EAST)
    JP->>US: проксирование join по коду ДЦ из meeting_id
    US-->>C: join_token, ws.us-east, IP SFU в US-EAST
    C->>US: WSS и SRTP напрямую в home_dc
```

#### Шаги сценария

| Шаг | Что происходит | Почему так |
| --- | -------------- | ---------- |
| 1. Логин в США | Пароль проверяется по локальной реплике `auth_pg`; сессия `us-east.<id>` создается в `session_redis` `DC-US-EAST` | Логину не нужна запись в primary |
| 2. Прилет в Японию | GeoDNS видит японский резолвер или подсеть клиента из ECS [^82] и отдает VIP `DC-JP-TOKYO` | ДЦ выбирается по текущему местоположению, привязки к стране логина нет |
| 3. Первый запрос в `DC-JP-TOKYO` | Сессии нет в локальном Redis: по префиксу `us-east` Auth один раз забирает ее из `DC-US-EAST` (+≈ 153 мс [^87]) и сохраняет у себя. **Повторный логин не нужен** | Сессии переносятся по запросу, а не копируются во все ДЦ заранее |
| 4. Профиль | Чтение — из локальной реплики `auth_pg`, изменение — в primary `DC-US-EAST` | Одна точка записи `users` (п. 3.4) |
| 5. Список встреч | Из локальной копии `user_meetings` в `DC-JP-TOKYO` | Keyspace реплицирован во все ДЦ |
| 6. Встреча американских коллег | `home_dc = DC-US-EAST`: Токио проксирует `join` туда, WS и медиа идут в `DC-US-EAST`. RTT Токио ↔ Вашингтон ≈ 153 мс [^87], в одну сторону ≈ 77 мс. По ITU-T G.114 разговор не страдает, пока задержка «от рта до уха» меньше 150 мс [^88]; в этот бюджет входят еще путь SFU → собеседник в США, кодек и джиттер-буфер: звонок возможен, но близко к границе | Все участники встречи — на одном SFU. После MVP — каскад SFU: клиент подключается к SFU в Токио, тот пересылает потоки в `home_dc` |
| 7. Новая встреча, созданная в Японии | `home_dc = DC-JP-TOKYO`; американские участники подключаются к SFU в Токио | `home_dc` выбирается по организатору |
| 8. Пользователь остался жить в Японии | Мигрировать нечего: данные пользователя глобальные (реплики во всех ДЦ), встречи привязаны к своему `home_dc`. Старая сессия в `DC-US-EAST` истечет по TTL | «Домашнего ДЦ пользователя», который пришлось бы переносить, нет |
| 9. Logout | Сессия удаляется локально и в ДЦ из префикса, событие отзыва рассылается во все 8 ДЦ | Отозванная сессия не должна жить ни в одной копии |

## 4. Локальная балансировка нагрузки

### 4.1. Границы локальной балансировки

| Поток | Где балансируется | В расчете NGINX L7 |
| ----- | ----------------- | ------------------ |
| HTTPS API | L4 (IPVS) → NGINX L7 → поды сервисов | Да |
| WSS: heartbeat, доставка чата и presence-событий | L4 (IPVS) → NGINX L7 → WebSocket-поды | Да |
| Метаданные записей и ссылки на скачивание | L4 (IPVS) → NGINX L7 | Да |
| RTP/SRTP медиа | Напрямую на публичный IP:порт SFU из ответа `join`. Балансирует control plane: он выбирает SFU для встречи | Нет |
| Скачивание файла записи | Напрямую из object storage `home_dc` по presigned URL | Нет |
| Поток записи SFU → recording workers | Внутри ДЦ, по адресу из control plane | Нет |
| Межсервисные вызовы внутри ДЦ | gRPC, клиентская балансировка по endpoints Kubernetes Service | Нет |
| Межрегиональные вызовы: прокси `join` в `home_dc`, перенос сессии | gRPC с mTLS между ДЦ | Нет |

Медиа идет мимо L4 и L7: клиент получает адрес конкретного SFU в ответе `join` (п. 3.5). Так встреча остается на одном SFU, а балансировщикам не нужно пропускать 78 Тбит/с.

**Клиент за NAT и межсетевым экраном.** SFU работает как ICE-Lite с публичным адресом: сам соединение не начинает, а отвечает на проверки клиента [^102]. Поэтому клиенту за NAT не нужны ни STUN, ни TURN. Если UDP закрыт, клиент подключается к тому же SFU по TCP: SFU слушает и UDP, и TCP [^102], а ICE умеет предлагать TCP-кандидаты [^103]. Не поддерживаем в MVP только сети, где прокси пропускает исключительно TLS на порт 443: для них нужен TURN по TLS.

### 4.2. Схема локальной и межсервисной балансировки

```mermaid
flowchart TD
    U["Client"] --> L4["L4: IPVS, Direct Routing + keepalived, VIP ДЦ"]
    L4 --> L7["NGINX L7 pool: TLS termination, HTTP/WS routing"]
    L7 --> API["Auth / Control Plane / Chat pods"]
    L7 --> WS["WebSocket / Presence pods"]
    API -->|"gRPC, round-robin по endpoints"| INT["Внутренние сервисы"]
    API --> PGB["PgBouncer"]
    U -->|"SRTP по UDP, адрес из ответа join"| SFU["SFU media pool"]
    SFU --> REC["Recording workers"]
```

**L4 — свой, на IPVS.** Директор принимает пакеты на VIP ДЦ и раздает TCP-соединения узлам NGINX; в режиме Direct Routing ответы идут к клиенту напрямую, мимо директора [^92]. Директоров два, active/standby: keepalived переносит VIP по VRRP и проверяет здоровье узлов NGINX [^93]. Облачный балансировщик провайдера не подходит: у самого мощного типа Selectel — 2 инстанса по 4 vCPU, до 3 Гбит/с (до 5 по заявке), а производительность HTTPS приведена для 10 000 соединений [^12]; в Kubernetes такой балансировщик создается для Service типа `LoadBalancer` [^21]. В одном нашем ДЦ одновременно до 6 млн WSS-соединений.

**Межсервисная балансировка.** gRPC-клиент получает список подов через headless Kubernetes Service и раздает вызовы round-robin [^52][^54]. Обычный L4 здесь не подходит: gRPC держит одно долгое HTTP/2-соединение, и все вызовы ушли бы в один под.

### 4.3. Механизмы резервирования

| Уровень | Что делает | Резервирование | Формула |
| ------- | ---------- | -------------- | ------- |
| L4: IPVS + keepalived | TCP-вход HTTPS/WSS в ДЦ, VIP | Active/standby: при отказе директора VIP переезжает по VRRP [^93] | `N+1` |
| NGINX L7 pool | HTTPS/WSS, TLS termination, routing | Active-active; keepalived исключает узел, не прошедший health check | `N+1` |
| NGINX L7 strict HA | Потеря AZ или стойки | Двойная емкость | `N*2` |
| SFU media pool | Видео, аудио, screen sharing | Sticky meeting + health checks; при отказе SFU клиент получает новый адрес и заново устанавливает медиасоединение | `N+1` |

### 4.4. Ограничители для расчета

| Ограничитель | Значение | Источник / расчет |
| ------------ | -------: | ----------------- |
| `LB_HTTPS_RPS` | **341 232 RPS** | NGINX Ingress Controller, HTTPS, ответ 1 KB по открытым keep-alive-соединениям, 16 CPU [^19] |
| `LB_TLS_CPS` | **6 676 новых TLS-соединений/с** | NGINX, полный TLS handshake на каждое соединение, RSA 2048, 16 CPU [^20]. С современным OpenSSL рукопожатия дешевле — значение консервативное |

Значения NGINX взяты для 16 CPU: в тестах это физические ядра, а облачный узел на 24 vCPU — около 12 ядер с Hyper-Threading. RPS и TLS все равно не ограничивают расчет: даже с поправкой 12/16 `N_rps` и `N_tls` в каждом ДЦ не больше `N_conn` (п. 4.5).

### 5.2. Размеры данных и QPS

### 5.3. Требования к консистентности

| Таблица | Консистентность | Почему |
| ------- | --------------- | ------ |
| `users` | Strong | Нельзя авторизовать несуществующего пользователя |
| `user_sessions` | Strong | Ошибка сессии ломает вход во встречу |
| `meetings` | Strong в `home_dc` | `join` должен видеть актуальный статус встречи |
| `meeting_participants` | Strong в `home_dc` | Нельзя дважды добавить одного участника |
| `meeting_invite_links` | Strong | Токен должен быть однозначно валиден или отозван |
| `user_meetings` | Eventual | Список встреч может обновиться с небольшой задержкой |
| `chat_messages` | Strong append внутри `meeting_id` | Внутри встречи важен порядок сообщений |
| `recordings` | Strong metadata + immutable file | UI должен видеть корректный статус записи |
| `recording_upload_buffer` | At-least-once + checksum | Часть можно перезалить под тем же номером, итоговый файл проверяется |
| `meetings_runtime` | Eventual, last write wins | Эфемерное состояние: после потери его восстанавливают heartbeat-ы клиентов |
| `chat_seq`, `chat_dedup` | Strong в одном шарде Redis: проверка и выдача номера — один атомарный скрипт | Номер выдается ровно один раз, повтор запроса не создает дубль |

### 5.4. Распределение нагрузки по ключам

| Ключ | Где используется | Распределение | Риск hot key | Что делаем логически |
| ---- | ---------------- | ------------- | ------------ | -------------------- |
| `user_id` | `users`, `user_sessions`, `user_meetings` | Почти равномерно | Низкий | Храним пользовательские данные отдельно от встреч |
| `meeting_id` | `meetings`, `participants`, `chat`, `recordings` | Неравномерно | Высокий на больших встречах | Встреча закрепляется за `home_dc`, код ДЦ — в первом байте `meeting_id` (п. 3.1) |

| `meeting_invite_links` | PostgreSQL + Citus, `meeting_pg` | `token_hash`, `token` | `home_dc` + реплика в парном ДЦ |
| `user_meetings` | ScyllaDB, `meeting_scylla` | `user_id + scheduled_start` | все ДЦ, RF=3 в каждом |
| `meetings_runtime` | Redis Cluster, `runtime_redis` | `meeting_id` | `home_dc` |

| `chat_seq`, `chat_dedup`, `active_invite_tokens` | Redis Cluster, `runtime_redis` | `meeting_id`, `token` | `home_dc` |

`meeting_pg` и `recording_pg` — две схемы одной базы на Citus-кластере ДЦ: co-location работает только внутри одной базы. У `meetings` и `recordings` одна колонка распределения — `meeting_id`, поэтому шарды встречи и ее записей лежат на одном узле [^30].

### 6.3. Выбор СУБД по таблицам

| СУБД | Таблицы | Почему |
| ---- | ------- | ------ |
| PostgreSQL | `users` | Транзакции, уникальный `email`, индексы |
| PostgreSQL + Citus | `meetings`, `meeting_invite_links`, `recordings` | SQL-метаданные со статусами, точечный lookup по токену и шардирование по `meeting_id` |
| ScyllaDB | `meeting_participants`, `user_meetings`, `chat_messages` | Много записей (`join`/`leave`, сообщения), чтение по ключу и диапазону без JOIN, мультиДЦ-репликация `user_meetings` |
| Redis Cluster | `user_sessions`, `meetings_runtime`, `chat_seq`, `chat_dedup`, `active_invite_tokens` | TTL и быстрый доступ по ключу; на `runtime_redis` ≈ 738 000 ops/s в пик: heartbeat 675 000 + `join`/`leave`/`create` + `INCR chat_seq` + `SET NX` ключа идемпотентности |
| S3-compatible Object Storage | файлы записей, `recording_upload_buffer` | Большие неизменяемые файлы и части загрузки не хранятся в SQL |
| Память Chat-сервиса | `chat_last100` | Буфер последних сообщений идущей встречи |

### 6.4. Индексы

| Таблица | Индекс | Для какого запроса |
| ------- | ------ | ------------------ |
| `users` | `PK(id)` | Получение пользователя по `user_id` |
| `users` | `UNIQUE(email)` | Логин и проверка дубля |
| `users` | `INDEX(created_at)` | Админские выборки по дате |
| `user_sessions` | `KEY session:{session_id}` | Проверка сессии |
| `user_sessions` | `TTL(expires_at)` | Автоудаление сессий |
| `meetings` | `PK(id)` | `join`, `leave`, метаданные записи |
| `meetings` | `INDEX(owner_id, scheduled_start)` | Список встреч владельца |
| `meetings` | `INDEX(home_dc, status)` | Выбор активных встреч в ДЦ |
| `meeting_participants` | `PK(meeting_id, bucket, user_id)` | Вход и выход участника |
| `meeting_participants` | `INDEX(user_id, last_joined_at)` | История участника |
| `meeting_invite_links` | `PK(token_hash, id)` | Колонка распределения `token_hash = hash(token)`: Citus сразу идет в нужный шард, PK обязан ее включать [^94] |
| `meeting_invite_links` | `UNIQUE(token_hash, token)` | Вход по ссылке; `token_hash` вычисляется из `token`, поэтому это та же уникальность токена |
| `meeting_invite_links` | `INDEX(expires_at)` | Удаление истекших ссылок |
| `user_meetings` | `PK(user_id, scheduled_start, meeting_id)` | Top-100 встреч пользователя |
| `meetings_runtime` | `KEY runtime:{meeting_id}` + TTL, его продлевает heartbeat | Heartbeat и счетчики; брошенная встреча удаляется сама [^22] |
| `chat_seq`, `chat_dedup` | `KEY chat_seq:{meeting_id}`, `KEY chat_dedup:{meeting_id}:{client_msg_id}` | Hash tag `{meeting_id}` кладет ключи встречи в один слот Redis Cluster [^31]: проверка повтора и выдача номера — один атомарный скрипт |
| `chat_messages` | `PK(meeting_id, bucket, message_seq)` | Чтение сообщений по порядку |
| `chat_messages` | Ключ идемпотентности в Redis: `SET chat_dedup:{meeting_id}:{client_msg_id} <seq> NX EX 60` [^98] | Повтор с тем же `client_msg_id` получает уже выданный `message_seq` и не создает дубль [^45]. В ScyllaDB нет UNIQUE: `INSERT` с тем же ключом перезаписывает строку [^101], а повтор получил бы новый `message_seq`, то есть другой ключ, — дубль |
| `recordings` | `PK(meeting_id, id)` | Карточка записи; таблица распределена по `meeting_id`, PK обязан ее включать [^94] |
| `recordings` | `INDEX(meeting_id, created_at)` | Список записей встречи |
| `recordings` | `INDEX(status, created_at)` | Очередь обработки |
| `recording_upload_buffer` | `UNIQUE(recording_id, chunk_number)` | Повторная загрузка части под тем же номером ее перезаписывает [^46] |
| `recording_upload_buffer` | `TTL(expires_at)` | Брошенные загрузки удаляет правило lifecycle `AbortIncompleteMultipartUpload` [^46] |

Индекс в шардированной таблице работает внутри шарда, поэтому запрос сначала должен попасть в нужный шард по `meeting_id`, `user_id` или `token_hash`.

### 6.5. Шардирование и размещение по дата-центрам

Шардирование двухуровневое. **Уровень 1 — по ДЦ:** все, что относится к встрече, лежит в ее `home_dc`, код которого записан в `meeting_id` (п. 3.1, 3.4). **Уровень 2 — внутри ДЦ:** по ключам из таблицы.

| Таблица | Шардируем | Ключ шардинга | Резервирование | Почему |
| ------- | --------- | ------------- | -------------- | ------ |
| `users` | Нет на MVP | `id` | Синхронная standby в другой AZ + реплика в каждом ДЦ | 81.92 GB, записей мало; один primary на весь мир (п. 3.4) |
| `user_sessions` | Да | `session_id` | Redis Cluster: у каждого master — replica на другом узле | 115 млн активных сессий, кластер в каждом ДЦ |
| `meetings` | Да: по `home_dc`, затем по `meeting_id` | `meeting_id` | Citus: синхронная standby в другой AZ + реплика в парном ДЦ | 900 млн строк за 30 дней; в самом большом ДЦ ≈ 321 млн |
| `meeting_participants` | Да | `meeting_id + bucket` | ScyllaDB, RF=3 по 3 AZ `home_dc` | 9 млрд строк за 30 дней |
| `meeting_invite_links` | Да | `token_hash` | Как у `meetings` | `join` начинается с токена |
| `user_meetings` | Да | `user_id` | ScyllaDB, RF=3 в каждом ДЦ | Свой список пользователь читает без fan-out |
| `meetings_runtime` | Да | `meeting_id` | Redis replica; потерю восстанавливают heartbeat-ы | ≈ 0.74 млн ops/s на весь мир вместе с `chat_seq` и `chat_dedup` |
| `chat_messages` | Да | `meeting_id + bucket` | ScyllaDB, RF=3 по 3 AZ `home_dc` + снапшоты (п. 6.12) | Чат читается по встрече и диапазону `seq` |
| `recordings` | Да | `meeting_id` | Как у `meetings` | Записи читаются по встрече |
| `recording_upload_buffer` | Да | `recording_id` | S3: ≥ 3 копии в 3 AZ | Части собираются в одну запись |

Метаданных в одном ДЦ немного: в самом большом, `DC-DE-FRANKFURT`, ≈ 206 GB и ≈ 5 950 чтений/с. Поэтому Citus в каждом ДЦ работает в режиме single-node — координатор сам хранит шарды [^90]. Колонка распределения `meeting_id` задана сразу: при росте добавляются worker-узлы с ребалансировкой шардов без смены схемы [^29][^30].

Репликация масштабирует чтение, шардирование — запись. JOIN на горячем пути нет: таблицы разных СУБД связаны логически, без физических FK, а каждый запрос идет по ключу шарда (п. 6.9).

### 6.9. Денормализация и отказ от JOIN

| Денормализация | Где хранится | Зачем |
| -------------- | ------------ | ----- |
| `topic`, `scheduled_start`, `status`, `role` в `user_meetings` | ScyllaDB | Список встреч пользователя без JOIN с `meetings` |
| `participants_online_count` в `meetings_runtime` | Redis | Не считать `COUNT(*)` по участникам |
| `home_dc` в `meetings` | PostgreSQL + Citus | Быстро направлять трафик встречи |
| `storage_bucket`, `storage_key` в `recordings` | PostgreSQL + Citus | Ссылка на файл без обхода object storage |
| `message_seq` в `chat_messages` | ScyllaDB | Клиент читает лог от `last_seen_seq` до `head_seq` |

Каждый горячий сценарий читает одну таблицу по одному ключу: свои встречи — `user_meetings` по `user_id`; события и участники встречи — по `meeting_id`; новые сообщения — `chat_messages` по `meeting_id + bucket + message_seq`.

## 7. Алгоритмы

В раздел включены алгоритмы, которые влияют на нагрузку и media plane.

### 7.1. Список алгоритмов

| Алгоритм | Где используется | Коротко | На что влияет |
| -------- | ---------------- | ------- | ------------- |
| Adaptive Bitrate | Media Plane / SFU | меняем качество под сеть участника | bandwidth, CPU клиента, SFU-routing |
| Выбор SFU-слоя видео | SFU | подписчику отдается нужный слой 720p/360p/180p | исходящий трафик SFU |

### 7.2. Adaptive Bitrate

**Задача** — подобрать качество видео под текущую сеть участника. **Вход:** `packet_loss`, `RTT`, `jitter`, `available_bitrate`, `frames_dropped`, `audio_quality`. **Результат:** `target_profile = 720p / 360p / 180p / audio_only`. **Ограничение:** звук важнее видео; понижение быстрое, повышение плавное.

Метрики сети SFU получает из RTCP внутри медиасессии: отчеты о приеме с потерями и джиттером [^44] и feedback о времени доставки пакетов для congestion control [^41]; клиент видит те же метрики через WebRTC stats API [^40]. Отдельных запросов к API ради статистики нет, поэтому в расчет нагрузки она не входит. Верхний профиль — 720p: на нем построен расчет трафика [^5]. 1080p в MVP нет: он требует 3.8/3.0 Мбит/с [^5] и увеличил бы трафик и число SFU.

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Всегда 720p | При плохой сети звонок рвется | Не подходит |
| Только клиент решает качество | SFU хуже управляет исходящим трафиком | Не выбираем |
| Server-guided ABR | SFU видит подписчиков и управляет слоями | **Выбрано** |

#### Как работает ABR

1. SFU получает RTCP-отчеты клиента — обычно несколько раз в секунду.
2. SFU оценивает сеть: потери, RTT, jitter, доступную полосу.
3. Сеть ухудшилась — профиль снижается сразу.
4. Сеть стабильна — профиль повышается на одну ступень.
5. Страдает звук — первым снижается видео.
6. Новый профиль применяется к подписке участника.

```mermaid
flowchart TD
    A[SFU получает RTCP-отчеты клиента] --> B[SFU оценивает loss, RTT, jitter, bitrate]
    B --> C{Есть проблемы со звуком?}
    C -- Да --> D[Снизить видео до audio priority]
    C -- Нет --> E{Сеть ухудшилась?}
    E -- Да --> F[Понизить профиль сразу]
    E -- Нет --> G{Есть запас по bitrate?}
    G -- Да --> H[Повысить профиль на 1 ступень]
    G -- Нет --> I[Оставить профиль]
    D --> J[Применить target_profile]
    F --> J
    H --> J
    I --> J
    J --> A
```

Состояние живет в памяти SFU: `participant_network_stats` (`meeting_id`, `user_id`, `loss`, `rtt`, `jitter`, `bitrate`) и `participant_media_profile` (`meeting_id`, `user_id`, `target_profile`, `updated_at`). Постоянные таблицы и Redis не меняются, метрики качества уходят в Prometheus. Эффект — меньше video download у участников с плохой сетью.

### 7.3. Выбор SFU-слоя видео

**Задача** — не транскодировать видео, а выбирать готовый слой. **Вход:** `target_profile`, `viewport`, `active_speaker`, доступные encodings. **Результат:** `selected_layer` для каждого подписчика. **Ограничение:** SFU не должен превращаться в MCU с высоким CPU.

SFU маршрутизирует RTP-потоки [^44] между участниками, а не смешивает их в один поток [^14]. Для нескольких качеств используется simulcast / SVC: отправитель публикует несколько encodings, SFU выбирает нужный слой [^42].

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Single stream | Всем отдается одно качество | Плохо для слабой сети |
| MCU transcoding | Высокая CPU-нагрузка | Не подходит для highload |
| SFU + simulcast/SVC | Больше upload от отправителя, зато сервер не перекодирует видео | **Выбрано** |

#### Как выбирается слой

1. Клиент публикует несколько слоев видео.
2. SFU хранит список доступных слоев каждого отправителя.
3. Для каждого подписчика считается `target_profile`.
4. Видео активного говорящего (его определяет active speaker detection [^43]) и крупной плитки отдается слоем выше.
5. Миниатюры отдаются слоем ниже.
6. При деградации сети SFU переключает подписчика на слой ниже.

```mermaid
flowchart TD
    A[Publisher отправляет video layers] --> B[SFU хранит available layers]
    C[Subscriber имеет target_profile] --> D[SFU выбирает layer]
    B --> D
    D --> E{Крупная плитка или active speaker?}
    E -- Да --> F[Выбрать слой выше]
    E -- Нет --> G[Выбрать слой ниже]
    F --> H[Отправить consumer stream]
    G --> H
```

Состояние живет в памяти SFU: `producer_layers` (`producer_id`, `rid`, `width`, `height`, `max_bitrate`), `consumer_subscription` (`consumer_id`, `producer_id`, `selected_layer`) и `participant_media_profile` (`user_id`, `target_profile`, `reason`). Новых постоянных таблиц нет. Эффект — меньше исходящего трафика SFU и никакого перекодирования на сервере.

### 9.2. Отказ целого дата-центра

Отказ одной AZ закрывается внутри ДЦ (п. 9.1). Отказ всего ДЦ редок, но для него есть явный план. Худший случай по емкости — отказ самого большого ДЦ, `DC-DE-FRANKFURT` (35.69% нагрузки).

| Шаг | Что происходит | Время |
| --- | -------------- | ----- |
| 1 | Monitors GTM фиксируют отказ, `DC-DE-FRANKFURT` убирается из DNS-ответов (п. 3.5) | ≈ 30 с + TTL 30 с |
| 2 | Новые подключения GTM раздает по `capacity_weight`: сначала `DC-UK-LONDON`, затем `DC-US-EAST`, остальное — по свободной емкости других ДЦ (п. 3.7) | сразу после шага 1 |
| 3 | Встречи `DC-DE-FRANKFURT` обрываются, клиенты переподключаются через `api` со случайной задержкой, чтобы не устроить шторм. Подписанный `join_token` (`meeting_id`, роль, срок) проверяется в любом ДЦ, поэтому комната пересоздается в резервном ДЦ без похода в недоступную БД | десятки секунд |
| 4 | Дежурный повышает реплику Citus `DC-DE-FRANKFURT` в `DC-UK-LONDON` до primary [^97]. Код ДЦ `de-frankfurt` из `meeting_id` начинает указывать на `DC-UK-LONDON` — в маршрутизации control plane и в GTM для имени `ws.de-frankfurt`. Запланированные встречи снова доступны | минуты, RPO — секунды |
| 5 | Чат и история участников встреч `DC-DE-FRANKFURT` недоступны до восстановления ДЦ или до восстановления из снапшотов в S3 парного ДЦ (п. 6.12) | осознанный компромисс |

**Особенность `DC-US-EAST`.** Шаги те же, реплику Citus повышают в `DC-US-WEST`. Кроме того, здесь primary `auth_pg`: логин все время работает на локальных репликах, а регистрация и правка профиля несколько минут ждут, пока дежурный повысит реплику в `DC-US-WEST` (п. 3.4).

#### Хватит ли емкости

Холодный резерв ×2 не закладываем: это +100% к стоимости SFU. Вместо него на время инцидента SFU во всех ДЦ, которые принимают нагрузку, ограничивают видео профилем group «high-quality video»: 1.0/0.6 Мбит/с вместо 2.6/1.8 для 720p [^5]. Поток в запись при этом не уменьшается.

```text
трафик участника, 720p              = 2.6 + 1.8 + 0.08 + 0.15 = 4.63 Мбит/с
трафик участника, high-quality      = 1.0 + 0.6 + 0.08 + 0.15 = 1.83 Мбит/с  → 39.5% от 720p
с потоком в запись (1.88 / 10 = 0.188 Мбит/с на участника):
  720p = 4.818, high-quality = 2.018 Мбит/с                              → 41.9% от 720p
емкость SFU без DC-DE-FRANKFURT     = 100% − 35.69% = 64.31% штатной
нагрузка при профиле high-quality   = 41.9% штатного пика  <  64.31%     → помещается
```

Это верно даже при худшем допущении, что пики всех ДЦ совпали; на деле они разнесены по часовым поясам. Отказ `DC-US-EAST` проверяется так же: 41.9% < 100% − 28.84% = 71.16%.

Stateless-слои (NGINX L7, WS-поды) работают на облачных VM и подах Kubernetes и досоздаются за минуты. Но и без этого запас есть:

- **Соединения.** У 21 узла L7 вне `DC-DE-FRANKFURT` — 21.8 млн соединений при пике 16.9 млн; у 22 узлов вне `DC-US-EAST` — 22.8 млн.
- **Шторм переподключений.** 6.0 млн клиентов Франкфурта открывают новые TLS-соединения: 6 022 688 / (21 узел × 6 676 в секунду) ≈ 43 с. Поэтому клиент переподключается со случайной задержкой в пределах минуты.

## 11. Список серверов

Серверы считаются **по каждому ДЦ**: данные встречи живут в ее `home_dc` (п. 3.4), поэтому в каждом ДЦ свой набор кластеров. Общее правило — `ceil(нагрузка_ДЦ / емкость_узла) + 1` (`N+1` в каждом ДЦ) с минимальным размером кластера, которого требует технология.

#### Внешний трафик

Цены выделенных серверов не покрывают наш трафик: при порте больше 1 Гбит/с Selectel дает 300 TB в месяц без ограничения полосы, а расширение стоит 336 ₽/мес за шаг 3 TB [^71][^66]. Через порты SFU проходит весь медиатрафик:

```text
медиа за месяц     = 562 545 000 GB/сутки * 30 = 16 876 350 TB ≈ 16.9 EB  (≈ 591 TB на узел SFU)
входит в тарифы    = 300 TB * 28 570 узлов     = 8 571 000 TB
сверх лимита       = 8 305 350 TB → 2 768 450 шагов по 3 TB * 336 ₽ ≈ 930.20 млн ₽/мес
```

Это верхняя оценка по публичному тарифу: на таком объеме трафик покупают по индивидуальному договору (транзит и пиринг), и он выходит дешевле. Поэтому в итог выше трафик не включен. С ним по публичному тарифу итог — **≈ 1 962.07 млн ₽/мес (≈ $23.11 млн)**, и трафик становится крупнейшей статьей. Исходящий трафик S3 при скачивании записей (1.96 ₽/GB [^70]) тоже не включен: частота просмотров неизвестна (п. 2.4).

Стоимость определяют те же блоки, что и нагрузку: хранение записей, медиа и внешний трафик медиа.
