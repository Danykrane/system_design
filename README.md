### 1. Тема и целевая аудитория

#### 1.1. Тип сервиса

| Параметр            | Значение                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| Учебное название    | **MeetFlow**                                                                                               |
| Тип сервиса         | Zoom-подобный сервис видеовстреч                                                                           |
| Основной сценарий   | Групповая онлайн-встреча с аудио, видео, демонстрацией экрана, чатом и записью                             |
| Целевые регионы     | Глобально: Америка, EMEA, Азиатско-Тихоокеанский регион; крупнейшие рынки — США, Япония, Индия, Великобритания, Канада [^12] |
| Реальные аналоги    | Zoom, Microsoft Teams, Google Meet                                                                         |
| Масштаб для расчёта | `MF_MAU = 320 млн MAU`, `MF_DAU = 115 млн DAU`, `MF_DMP = 300 млн участий во встречах в день` [^1][^2][^3] |

#### 1.2. Рыночная ниша и реальные аналоги

| Аналог | Метрика | Что подтверждает |
| ------ | ------- | ---------------- |
| Microsoft Teams | 320 млн monthly active users, раскрыто в FY24 Q1 [^1] | Массовый размер аудитории коммуникационного сервиса |
| Microsoft Teams | 115 млн daily active users, октябрь 2020 [^2] | Нижнюю публичную границу daily-аудитории для расчёта |
| Zoom | 300 млн daily meeting participants, апрель 2020; это участники встреч, а не unique users [^3] | Массовую ежедневную нагрузку именно на видеовстречи |
| Zoom | Средняя встреча — 54 минуты и 10 участников, данные за 15.11.2020–15.11.2021 [^4] | Базу для продуктовой оценки видеозвонков |
| Zoom | $4.8688 млрд выручки за FY2026 и 4 468 клиентов с TTM-выручкой больше $100 000 [^10] | Актуальность ниши на 2026 год |

#### 1.3. Функционал MVP

| № | Функция MVP | Кратко | Метрика для расчёта |
| -: | ----------- | ------ | ------------------- |
| 1 | Создание встречи | Пользователь создаёт мгновенную или запланированную встречу | `MF_MEETINGS_DAY`, `POST /meetings` |
| 2 | Подключение к встрече | Участник входит по ссылке или приглашению | `MF_DMP`, `POST /meetings/{id}/join` |
| 3 | Групповая аудио- и видеосвязь | Участники общаются в 720p group video | `MF_VIDEO_UP_MBPS`, `MF_VIDEO_DOWN_MBPS`, `MF_AUDIO_MBPS` |
| 4 | Демонстрация экрана | Участник показывает экран | `MF_SCREEN_MBPS_MAX` |
| 5 | Чат во время встречи | Участники отправляют текстовые сообщения | `MF_CHAT_MSG_LIMIT`, `MF_CHAT_PER_JOIN` |
| 6 | Облачная запись | Организатор включает запись встречи | `MF_RECORD_QUOTA_GB`, `MF_RECORDING_SIZE_GB` |

#### 1.4. Ключевые продуктовые решения

| Решение | Значение для MVP | Что считается дальше |
| ------- | ---------------- | -------------------- |
| Расчёт ведётся от групповой встречи | Средняя встреча: `MF_MEET_SIZE = 10` участников | Количество встреч в сутки |
| Базовый профиль качества | 720p group video по официальным требованиям Zoom [^5] | Видео-трафик upload/download |
| Запись встречи включается в облако | Cloud recording сохраняет видео, аудио и текст чата [^7] | Хранилище записей |
| Хранилище записей ограничено квотой | Для Pro/Business у Zoom — 10 GB на licensed user [^8] | Верхняя граница object storage |
| Частота чата — явное допущение | Есть лимит сообщения, но нет публичной частоты сообщений на пользователя [^6]; принимаем 5 сообщений на одно участие | Нагрузка и хранилище чата (2.2–2.4), уточняется после запуска |

#### 1.5. Целевая аудитория

| Параметр | Значение |
| -------- | -------: |
| География | Глобальный рынок; Zoom использовался почти в 200 странах и территориях [^4]; обслуживаем из 8 ДЦ (п. 3.2) |
| Месячная аудитория | `MF_MAU = 320 000 000` пользователей/месяц |
| Дневная аудитория | `MF_DAU = 115 000 000` пользователей/день |
| Участий во встречах в день | `MF_DMP = 300 000 000` участий/день |
| Средний размер встречи | `MF_MEET_SIZE = 10` участников |
| Средняя длительность встречи | `MF_MEET_LEN_MIN = 54` минуты |

### 2. Расчёт нагрузки

#### 2.1. Исходные метрики и методика расчёта

| Название | Описание (бывшее значение) | Источник / расчёт |
| -------- | -------------------------- | ----------------- |
| `MF_MAU` | 320 000 000 monthly active users; публичное значение Microsoft Teams, FY24 Q1 / 2023 | Берётся как целевой месячный масштаб аналога; без пересчёта на 2026, потому что более новой публичной MAU-метрики Teams в открытых источниках не найдено [^1] |
| `MF_DAU` | 115 000 000 daily active users; публичное значение Microsoft Teams, октябрь 2020 | Берётся как консервативная daily-аудитория аналога; это не статистика Zoom и не результат экстраполяции [^2] |
| `MF_DMP` | 300 000 000 daily meeting participants; публичное значение Zoom, апрель 2020 | Используется для нагрузки на видеовстречи; это участники встреч, один пользователь может считаться несколько раз [^3] |
| `MF_MEET_SIZE` | 10 участников в средней Zoom-встрече; данные за 15.11.2020–15.11.2021 | Используется для расчёта `MF_MEETINGS_DAY = MF_DMP / MF_MEET_SIZE` [^4] |
| `MF_MEET_LEN_MIN` | 54 минуты — средняя длительность Zoom-встречи; данные за 15.11.2020–15.11.2021 | Используется для расчёта participant-minutes [^4] |
| `MF_VIDEO_UP_MBPS` | 2.6 Mbps на участника для 720p group video upload | Официальные требования Zoom к bandwidth [^5] |
| `MF_VIDEO_DOWN_MBPS` | 1.8 Mbps на участника для 720p group video download | Официальные требования Zoom к bandwidth [^5] |
| `MF_VIDEO_HQ_MBPS` | 1.0 / 0.6 Mbps up/down для group «high-quality video» (ниже 720p) | Требования Zoom [^5]; профиль деградации при отказе ДЦ (п. 9.2) |
| `MF_AUDIO_MBPS` | 0.08 Mbps на участника для VoIP audio | Верхняя граница диапазона 60–80 kbps из требований Zoom [^5] |
| `MF_SCREEN_MBPS_MAX` | 0.15 Mbps на участника для screen sharing upper-bound | Верхняя граница диапазона 50–150 kbps из требований Zoom [^5] |
| `MF_CHAT_MSG_LIMIT` | 4 000 символов на одно chat-сообщение | Лимит Zoom Team Chat [^6] |
| `MF_CHAT_PER_JOIN` | 5 сообщений на одно участие во встрече | **Проектное допущение**: публичной частоты нет [^6]. Раньше стояло только в п. 6.6 — теперь задано здесь и используется везде |
| `MF_CHAT_MSG_SIZE` | 1 KB в среднем на сообщение (максимум ≈ 10 KB при 4 000 символов) | Проектное допущение для хранилища чата |
| `MF_LIST_PER_DAU` | 3 открытия списка встреч на DAU в сутки | Проектное допущение. Раньше было неявно зашито в число 11 979 в п. 6.6 |
| `MF_LOGIN_PER_DAU` | 1 создание сессии (логин) на DAU в сутки | Проектное допущение. Раньше было неявно зашито в число 3 993 в п. 5.2 |
| `MF_RECORD_QUOTA_GB` | 10 GB cloud recording storage на licensed user | Квота Zoom для Pro/Business [^8] |
| `MF_HEARTBEAT_SEC` | 25 секунд между heartbeat-событиями | Дефолтный `pingInterval = 25000 ms` в Socket.IO [^9] |
| `MF_K_PEAK` | **1.5** (в прошлой версии — 3) | Коэффициент суточного пика: пиковый час / среднее за сутки. Применяется одинаково к RPS, bandwidth и числу одновременных соединений. Сервис глобальный: когда в Америке рабочий день, в Азии ночь, и часовые пояса сглаживают общую суточную кривую. Значение 1.5 — по замечанию ревьюера; 3 удваивало пиковые значения |

Текущая актуальность ниши проверяется не устаревшими usage-числами, а финансовой метрикой: Zoom в FY2026 показал $4.8688 млрд выручки и 4 468 крупных клиентов с TTM-выручкой больше $100 000 [^10]. Старые usage-метрики используются только там, где они прямо подписаны по году и где показана формула расчёта.

Все числа разделов 2–6 и 11 считаются одним скриптом [`resource/calc/meetflow_calc.py`](resource/calc/meetflow_calc.py): при изменении допущения достаточно поменять константу и перезапустить.

#### 2.2. Продуктовая оценка видеовстреч

| Название | Расчёт | Значение |
| -------- | ------ | -------: |
| `MF_MEETINGS_DAY` | `MF_DMP / MF_MEET_SIZE` = `300 000 000 / 10` | **30 000 000 встреч/сутки** |
| `MF_JOINS_PER_DAU_DAY` | `MF_DMP / MF_DAU` = `300 000 000 / 115 000 000` | **2.61 подключения/DAU/день** |
| `MF_CREATED_MEETINGS_PER_DAU_DAY` | `MF_MEETINGS_DAY / MF_DAU` = `30 000 000 / 115 000 000` | **0.26 созданных встреч/DAU/день** |
| `MF_PARTICIPANT_MIN_DAY` | `MF_DMP * MF_MEET_LEN_MIN` = `300 000 000 * 54` | **16 200 000 000 participant-minutes/сутки** |
| `MF_AVG_ONLINE_PARTICIPANTS` | `MF_PARTICIPANT_MIN_DAY / 1440` | **11 250 000 участников online в среднем** |
| `MF_PEAK_ONLINE_PARTICIPANTS` | `MF_AVG_ONLINE_PARTICIPANTS * MF_K_PEAK` = `11 250 000 * 1.5` | **16 875 000 участников online в пик** |
| `MF_PEAK_WSS_CONNECTIONS` | `= MF_PEAK_ONLINE_PARTICIPANTS`, одно WSS-соединение на участника | **16 875 000 одновременных соединений** |
| `MF_PEAK_ACTIVE_MEETINGS` | `MF_PEAK_ONLINE_PARTICIPANTS / MF_MEET_SIZE` | **1 687 500 встреч одновременно** |
| `MF_HEARTBEAT_EVENTS_DAY` | `MF_PARTICIPANT_MIN_DAY * 60 / MF_HEARTBEAT_SEC` | **38 880 000 000 heartbeat-событий/сутки** |
| `MF_CHAT_MESSAGES_DAY` | `MF_DMP * MF_CHAT_PER_JOIN` = `300 000 000 * 5` | **1 500 000 000 сообщений/сутки** |
| `MF_MEETING_LIST_VIEWS_DAY` | `MF_DAU * MF_LIST_PER_DAU` = `115 000 000 * 3` | **345 000 000 открытий списка/сутки** |
| `MF_LOGINS_DAY` | `MF_DAU * MF_LOGIN_PER_DAU` | **115 000 000 логинов/сутки** |

#### 2.3. Хранилище пользователя и техническое хранение

| Блок данных | Название | Расчёт | Общий объём |
| ----------- | -------- | ------ | ----------: |
| Профили пользователей | `MF_USERS_STORAGE_GB` | `MF_MAU * 256 B` | **81.92 GB** |

В итоговый суммарный объём не включается `MF_RECORDING_QUOTA_EB`: это продуктовая квота, а не фактически занятое хранилище. Для sizing object storage используется worst-case 30-дневное хранение записей: `MF_RECORDING_WORST_PB_30D = 685.26 PB` (каждая встреча записывается). Объёмы хранения не зависят от `MF_K_PEAK`: пик меняет скорость, а не суточный объём.

Расчёт bandwidth в таблице:

```text
avg_bandwidth_Gbps  = MF_AVG_ONLINE_PARTICIPANTS * bitrate_Mbps / 1000
peak_bandwidth_Gbps = avg_bandwidth_Gbps * MF_K_PEAK
rec_stream_Gbps     = (MF_AVG_ONLINE_PARTICIPANTS / MF_MEET_SIZE) * (1.8 + 0.08) / 1000 * K
```

Поток в запись — внутренний трафик ДЦ: SFU отправляет его recording workers как ещё одному подписчику встречи. В интернет он не уходит, но нагружает SFU и воркеры записи, поэтому учитывается в разделе 11.

| Вопрос | Решение в MeetFlow | Где подробно |
| ------ | ------------------ | ------------ |
| Где стоят дата-центры | 8 ДЦ: `DC-US-EAST`, `DC-US-WEST`, `DC-BR-SAOPAULO`, `DC-UK-LONDON`, `DC-DE-FRANKFURT`, `DC-IN-MUMBAI`, `DC-SG-SINGAPORE`, `DC-JP-TOKYO`. Абстрактного пула `OTHER` нет: каждая группа стран привязана к конкретному ДЦ | 3.2 |
| Как пользователь попадает в ДЦ и как ДЦ переключаются | **DNS**: GeoDNS/GTM выбирает ДЦ по гео, latency, health и весам. **Anycast** — только для доставки DNS-запросов к авторитетным NS-серверам. Медиа переключается на уровне приложения: control plane выдаёт новый SFU | 3.5–3.7 |

«ДЦ» в работе — это регион провайдера из 3 зон доступности (AZ). Отказ одной AZ закрывается резервированием внутри ДЦ (разделы 4 и 9), отказ всего ДЦ — глобальной балансировкой.

#### 3.1. Функциональное разбиение по доменам

| Домен | Основная нагрузка | Куда направляется запрос | Точка записи |
| ----- | ----------------- | ------------------------ | ------------ |
| `Auth / Users` | логин, профиль | ближайший ДЦ по GeoDNS | `users` — primary `auth_pg` в `DC-US-EAST`; `user_sessions` — ДЦ, где выполнен логин |
| `Meeting Control Plane` | `POST /meetings`, `join`, `leave`, список встреч | ближайший ДЦ; `join` и `leave` проксируются в `home_dc` встречи | `meetings`, `meeting_invite_links` — `home_dc` |
| `Media Plane / SFU` | видео, аудио, screen sharing | только SFU в `home_dc` встречи, адрес приходит в ответе `join` | не хранится, это поток |
| `Presence / Heartbeat` | `WS /presence/heartbeat` | WS-endpoint `home_dc` встречи | `meetings_runtime` — Redis `home_dc` |
| `Meeting Chat` | сообщения внутри встречи | `home_dc` встречи | `chat_messages` — ScyllaDB `home_dc` |
| `Recording` | запись встречи | SFU → recording workers в `home_dc` | файлы — S3 `home_dc`, метаданные — `recording_pg` `home_dc` |
| `User meetings list` | top-100 встреч пользователя | ближайший ДЦ, чтение локальной копии | `user_meetings` пишется в `home_dc` встречи, ScyllaDB реплицирует его во все ДЦ |

`home_dc` — ДЦ, за которым закреплена встреча. Control plane выбирает его при `POST /meetings`: это ДЦ, который обработал запрос, то есть ближайший к организатору. Код `home_dc` записан в `meeting_id` (UUIDv8, первый байт — код ДЦ [^85]) и в invite-токен. Поэтому любой ДЦ понимает, куда направить `join`, без глобального справочника встреч.

#### 3.2. Выбор и расположение дата-центров

**Шаг 1. Страны с известной долей.** По SimilarWeb: U.S. — 40.73%, Japan — 5%, India — 4.35%, UK — 3.72%, Canada — 3.69%, Other — 42.5% [^12]. Other округлён до 42.51%, чтобы сумма была 100%. Другие оценки дают США ещё большую долю — около половины MAU [^11], так что США в любом случае крупнейший рынок.

**Шаг 2. Раскладываем Other (42.51%) по макрорегионам.** В прошлой версии Other был одним пулом `OTHER_REGIONAL_POOL`: у него не было ни места, ни состава стран, под него нельзя было поставить серверы.

| Шаг | Расчёт | Результат |
| --- | ------ | --------: |
| Латинская Америка | Ни одна страна LatAm не входит в топ-5, значит, каждая < 3.69%. Допущение: Бразилия ≈ 2.5%, Мексика ≈ 2%, остальные ≈ 3% | **7.5%** |
| EMEA + APAC целиком | `100 − (US + Canada) − LatAm = 100 − 44.42 − 7.5` | **48.08%** |
| Деление EMEA : APAC | По выручке Zoom за FY2026: EMEA 15.8%, APAC 12.1% [^72]. `48.08 × 15.8 / 27.9` и `48.08 × 12.1 / 27.9` | EMEA **27.23%**, APAC **20.85%** |
| Остаток EMEA | `27.23 − UK 3.72` | **23.51%** |
| Остаток APAC | `20.85 − Japan 5.00 − India 4.35` | **11.50%** |
| Проверка | `7.5 + 23.51 + 11.50 = 42.51` = Other | ✓ |

Выручку используем только для пропорции EMEA : APAC — у этих рынков близкая выручка на пользователя. Для Америк выручка не подходит: в США выручка на пользователя заметно выше. Проверка: по трафику Америки дают 51.92%, а по выручке 72.1% [^72]. Значит, выручка на единицу трафика в Америках примерно в 2.4 раза выше, чем в EMEA/APAC, — это ожидаемо.

**Шаг 3. США делим на восток и запад** по населению: на регион West по переписи 2020 приходится 23.7% населения [^73]. Один ДЦ на 40% мирового трафика — слишком большой радиус отказа, и у западного побережья задержка до восточного ДЦ выше.

#### 3.4. Точки записи данных

Правило: **у каждого объекта одна точка записи** (primary), а чтение по возможности идёт из локальной копии в ближайшем ДЦ. Тогда не бывает двух одновременных записей одного объекта в разных ДЦ, и не нужен сложный multi-master с разрешением конфликтов.

| Данные | Точка записи | Где читаются | Репликация между ДЦ | Почему так |
| ------ | ------------ | ------------ | ------------------- | ---------- |
| `users` (`auth_pg`) | **один primary на весь мир — `DC-US-EAST`**, синхронная standby в другой AZ того же ДЦ | локальная асинхронная реплика в каждом ДЦ | streaming replication: primary → 7 реплик [^27][^89] | Нужна глобальная уникальность `email`. Записи редкие: даже если каждый DAU раз в сутки меняет профиль, в пик это ≤ 1 997 записей/с — одного primary хватает |
| `user_sessions` (`session_redis`) | ДЦ, где выполнен логин; код ДЦ — префикс `session_id` (`us-east.<128 бит>`) | там же; другой ДЦ один раз забирает сессию по префиксу (п. 3.8) | нет, перенос по запросу | Сессия нужна там, где пользователь сейчас; копии во всех ДЦ не нужны |
| `meetings`, `meeting_invite_links` (`meeting_pg`) | `home_dc` встречи | `home_dc` | асинхронная реплика в парный ДЦ на случай отказа | `join` должен видеть актуальный статус (strong, п. 5.3) |
| `meeting_participants` (`meeting_scylla`) | `home_dc` | `home_dc` | нет: keyspace реплицируется только внутри `home_dc`, RF=3 по 3 AZ; снапшоты — в S3 парного ДЦ | Нужны во время встречи и для истории |
| `meetings_runtime` (`runtime_redis`) | `home_dc` | `home_dc` | нет | Эфемерное состояние, клиенты восстанавливают его при переподключении |
| `chat_messages` (`chat_scylla`) | `home_dc` | `home_dc` | нет; снапшоты — в S3 парного ДЦ | Порядок задаёт `chat_seq` в одном Redis `home_dc` |
| `recordings` и файлы (`recording_pg`, S3) | `home_dc` | `home_dc` по presigned URL | метаданные — асинхронная реплика в парный ДЦ; файлы — ≥ 3 копии в 3 AZ `home_dc` | Копия 685 PB в другой регион удвоила бы самую дорогую статью расходов |
| `user_meetings` (`meeting_scylla`) | `home_dc` встречи, запись с `LOCAL_QUORUM` | ближайший к пользователю ДЦ, локально | keyspace с RF=3 **в каждом** ДЦ (NetworkTopologyStrategy) [^80][^81] | Read model с eventual consistency (п. 5.3): список встреч доступен локально в любой стране |

```mermaid
flowchart TB
    subgraph USERS["users: одна точка записи на весь мир"]
        direction LR
        W["Регистрация, профиль"] --> P["auth_pg primary, DC-US-EAST"]
        P -->|"sync"| S["standby, DC-US-EAST, другая AZ"]
        P -->|"async"| R1["реплика для чтения, DC-JP-TOKYO"]
        P -->|"async"| R2["реплика для чтения, DC-DE-FRANKFURT"]
    end
    subgraph MEET["данные встречи: точка записи — home_dc"]
        direction LR
        M1["create / join встречи с home_dc = JP-TOKYO"] --> D1["meeting_pg, ScyllaDB, Redis в DC-JP-TOKYO"]
        M2["create / join встречи с home_dc = DE-FRANKFURT"] --> D2["meeting_pg, ScyllaDB, Redis в DC-DE-FRANKFURT"]
    end
    USERS ~~~ MEET
```

**Как запрос на запись попадает в точку записи:**

1. Запрос приходит в ближайший ДЦ (GeoDNS, п. 3.5).
2. Сервис определяет точку записи: для `users` это всегда `DC-US-EAST`, для данных встречи — код ДЦ из `meeting_id`.
3. Если точка записи в другом ДЦ, запрос проксируется по gRPC с mTLS по межрегиональному каналу [^52]. Это добавляет RTT между ДЦ — например, ≈ 153 мс Токио ↔ восточное побережье США [^87], но только для редких записей.
4. После своей записи пользователь несколько секунд читает из primary (read-your-writes), пока асинхронная реплика не догонит.

**Отказ точки записи.** Primary `auth_pg` переключается на синхронную standby в соседней AZ без потери данных; переключение автоматическое, через Patroni [^86]. При отказе всего `DC-US-EAST` primary становится реплика `DC-US-WEST`; RPO — секунды лага асинхронной репликации. Логин продолжает работать: он читает локальную реплику и пишет сессию в локальный Redis. На время переключения блокируются только регистрация и изменение профиля.

#### 3.5. Схема DNS-балансировки — основной механизм переключения

**Ответ на вопрос «Anycast или DNS?»: ДЦ выбирается и переключается через DNS.** Используется GeoDNS/GTM — managed-сервис с геолокацией, latency-based routing, health checks и весами пулов [^15][^16][^17]. Anycast стоит только «под» DNS: авторитетные NS-серверы GTM-провайдера доступны по Anycast IP (п. 3.6).

| DNS-имя | Что выбирает | Политика | TTL |
| ------- | ------------ | -------- | --: |
| `api.meetflow.example` | VIP API edge ближайшего здорового ДЦ | geo + latency + health + веса | 30 с |
| `ws.<dc>.meetflow.example` | WebSocket edge конкретного `home_dc` | фиксированное региональное имя, приходит в ответе `join` | 30 с |
| SFU, IP:port | конкретный SFU в `home_dc` | не DNS: адрес и ICE-кандидаты приходят в ответе `join` | — |
| `rec.<dc>.meetflow.example` | скачивание записей из object storage `home_dc` | региональное имя, presigned URL | 300 с |
| `static.meetflow.example` | веб-клиент и статика | CDN провайдера | по CDN |

GeoDNS определяет местоположение по IP рекурсивного резолвера или по подсети клиента из EDNS Client Subnet [^82]. Поэтому ДЦ выбирается по тому, где пользователь находится сейчас, а не где он регистрировался.

```mermaid
sequenceDiagram
    participant C as Клиент
    participant NS as GeoDNS / GTM (NS на Anycast IP)
    participant E as API edge ближайшего ДЦ
    participant H as home_dc встречи
    C->>NS: 1. DNS-запрос api.meetflow.example
    NS->>NS: 2. гео + latency + health + веса
    NS-->>C: 3. VIP ближайшего здорового ДЦ
    C->>E: 4. HTTPS: login, create, join
    E->>H: 5. join проксируется в home_dc по коду из meeting_id
    H-->>C: 6. join_token: meeting_id, home_dc, ws.<dc>, IP SFU
    C->>H: 7. WSS: presence и чат
    C->>H: 8. SRTP по UDP в SFU
```

**Время переключения через DNS.** Monitor GTM опрашивает health-endpoint каждого ДЦ, интервал настраивается — берём 10 с [^17]. После 3 неудач подряд ДЦ выводится из ответов (≈ 30 с), плюс TTL 30 с. Итого новые подключения уходят в здоровый ДЦ примерно за минуту. Часть резолверов кеширует дольше TTL, поэтому у клиента есть свой fallback: при ошибке соединения он заново резолвит имя, а если это не помогло — идёт на резервный региональный адрес из конфигурации приложения.

#### 3.6. Схема Anycast-балансировки

Anycast — один IP-адрес, который анонсируется по BGP из многих точек; пакет приходит в «ближайшую» по маршрутизации точку [^83]. В MeetFlow Anycast используется **только там, где запросы короткие и не хранят состояние на сервере**:

| Трафик | Anycast | Почему |
| ------ | ------- | ------ |
| DNS-запросы к авторитетным NS-серверам GTM | **Да** | UDP «запрос — ответ» без сессии: ответ из ближайшего PoP, устойчивость к отказу точки и DDoS [^83] |
| Статика веб-клиента | Да, через CDN провайдера | короткие запросы, контент одинаковый во всех точках |
| API `api.meetflow.example` | Нет | BGP выбирает маршрут по AS-path, а не по задержке и загрузке ДЦ: нельзя задать веса, вывести ДЦ на обслуживание (drain), учесть ёмкость. Глобальный proxy-балансировщик с одним Anycast IP есть у крупных облаков [^18], но он привязывает к сети одного облака |
| WebSocket | Нет | долгоживущее TCP-соединение: при перестроении BGP-маршрута пакеты уйдут в другой ДЦ, где нет состояния этого соединения [^83] |
| RTP/SRTP медиа | Нет | встреча живёт на конкретном SFU в `home_dc`, смена маршрута рвёт медиасессию |

```mermaid
flowchart LR
    C1["Клиент в Японии"] -->|"DNS-запрос на 198.51.100.53"| P1["NS PoP Токио"]
    C2["Клиент в Германии"] -->|"тот же адрес 198.51.100.53"| P2["NS PoP Франкфурт"]
    P1 --> A1["GTM отвечает: VIP DC-JP-TOKYO"]
    P2 --> A2["GTM отвечает: VIP DC-DE-FRANKFURT"]
```

Оба PoP анонсируют по BGP один и тот же адрес (в примере — документационный `198.51.100.53`), и маршрутизация приводит каждый запрос в ближайшую к клиенту точку.

Итог: Anycast ускоряет и защищает **получение DNS-ответа**, а **решение, в какой ДЦ идти, принимает GTM** — это и есть механизм переключения.

#### 3.7. Регулировка трафика и переключение между дата-центрами

Регулировка идёт через веса пулов в GTM. Monitors регулярно проверяют endpoints и выводят нездоровый пул из ротации [^16][^17].

```text
effective_weight = geo_match * health * capacity_weight * manual_weight
```

| Ситуация | Что делаем | Кого затрагивает |
| -------- | ---------- | ---------------- |
| Норма | Пользователь → ближайший здоровый ДЦ | — |
| ДЦ перегружен | Снижаем `capacity_weight`: новые пользователи и встречи уходят в резервные ДЦ | только новые |
| Плановые работы | `manual_weight = 0` (drain): новые встречи не создаются, текущие доживают | только новые |
| ДЦ недоступен | `health = 0`, ДЦ убирается из DNS-ответов | все, см. п. 9.2 |
| Деградация пула SFU | Control plane не назначает этот пул новым встречам. При отказе SFU клиент получает адрес нового SFU по WebSocket и делает ICE restart [^84] | встречи на этом SFU |

| Основной ДЦ | Резерв 1 | Резерв 2 | Почему |
| ----------- | -------- | -------- | ------ |
| `DC-US-EAST` | `DC-US-WEST` | `DC-UK-LONDON` | та же страна, затем ближайший ДЦ через Атлантику |
| `DC-US-WEST` | `DC-US-EAST` | `DC-JP-TOKYO` | та же страна, затем через Тихий океан |
| `DC-BR-SAOPAULO` | `DC-US-EAST` | `DC-DE-FRANKFURT` | прямые кабели в США и Европу |
| `DC-UK-LONDON` | `DC-DE-FRANKFURT` | `DC-US-EAST` | соседний европейский ДЦ |
| `DC-DE-FRANKFURT` | `DC-UK-LONDON` | `DC-IN-MUMBAI` | соседний европейский ДЦ, затем Ближний Восток |
| `DC-IN-MUMBAI` | `DC-SG-SINGAPORE` | `DC-DE-FRANKFURT` | ближайший ДЦ в Азии |
| `DC-SG-SINGAPORE` | `DC-JP-TOKYO` | `DC-IN-MUMBAI` | ближайшие ДЦ в Азии |
| `DC-JP-TOKYO` | `DC-SG-SINGAPORE` | `DC-US-WEST` | ближайший ДЦ в Азии, затем через Тихий океан |

Резервный ДЦ может быть меньше основного: `DC-US-WEST` (9.65%) не вместит `DC-US-EAST` (37.27%). Поэтому столбцы «Резерв» задают **порядок предпочтения**, а не единственный адрес. GTM раздаёт трафик отказавшего ДЦ по нескольким ДЦ пропорционально свободной ёмкости (`capacity_weight`). Расчёт того, что ёмкости хватит, — в п. 9.2.

```mermaid
flowchart TD
    M["Метрики: health, latency, загрузка SFU, свободная ёмкость"] --> GTM["GTM"]
    GTM --> W["Пересчёт весов"]
    W --> DNS["DNS-ответы, TTL 30 с"]
    DNS --> NEW["Новые подключения и встречи"]
    NEW --> DC["Здоровый ДЦ с запасом ёмкости"]
    GTM --> DRAIN["Drain перегруженного ДЦ"]
    DRAIN --> OLD["Текущие встречи доживают"]
```

#### 3.8. Сценарий: вход в США, затем поездка в Японию

Вопрос: пользователь залогинился в США, а потом улетел в Японию. Что происходит?

```mermaid
sequenceDiagram
    participant C as Клиент в Японии
    participant DNS as GeoDNS
    participant JP as DC-JP-TOKYO
    participant US as DC-US-EAST
    C->>DNS: api.meetflow.example?
    DNS-->>C: VIP DC-JP-TOKYO (японский резолвер / ECS)
    C->>JP: GET /users/{id}/meetings, session_id = us-east.…
    JP->>JP: сессии нет в локальном session_redis
    JP->>US: gRPC: получить сессию us-east.…
    US-->>JP: сессия валидна, остаток TTL
    JP->>JP: сохранить сессию локально
    JP-->>C: список встреч из локальной копии user_meetings
    C->>JP: POST /meetings/{id}/join (встреча коллег, home_dc = US-EAST)
    JP->>US: проксирование join по коду ДЦ из meeting_id
    US-->>C: join_token, ws.us-east, IP SFU в US-EAST
    C->>US: WSS и SRTP напрямую в home_dc
```

| Шаг | Что происходит | Почему так |
| --- | -------------- | ---------- |
| 1. Логин в США | Пароль проверяется по локальной реплике `auth_pg`. Сессия `us-east.<id>` создаётся в `session_redis` `DC-US-EAST` | Логину не нужна запись в primary |
| 2. Прилёт в Японию | GeoDNS видит японский резолвер или подсеть клиента из ECS [^82] и отдаёт VIP `DC-JP-TOKYO` | ДЦ выбирается по текущему местоположению; привязки к стране логина нет |
| 3. Первый запрос в `DC-JP-TOKYO` | Сессии нет в локальном Redis. По префиксу `us-east` Auth один раз забирает её из `DC-US-EAST` (+≈ 153 мс [^87]) и сохраняет у себя. **Повторный логин не нужен** | Сессии не копируются во все ДЦ заранее, а переносятся по запросу |
| 4. Профиль | Чтение — из локальной реплики `auth_pg`, изменение — в primary `DC-US-EAST` | Одна точка записи для `users` (п. 3.4) |
| 5. Список встреч | Читается из локальной копии `user_meetings` в `DC-JP-TOKYO` | Keyspace реплицирован во все ДЦ |
| 6. Встреча американских коллег | `home_dc = DC-US-EAST`. `DC-JP-TOKYO` проксирует `join` в `DC-US-EAST` по коду ДЦ в `meeting_id`. WS и медиа идут в `DC-US-EAST`: RTT ≈ 153 мс [^87], в одну сторону ≈ 76 мс — это меньше 150 мс, которые ITU-T G.114 считает приемлемыми для разговора [^88] | Все участники встречи должны быть на одном SFU. Улучшение после MVP — каскад SFU: клиент подключается к SFU в Токио, а тот пересылает потоки в SFU `home_dc` по магистрали |
| 7. Новая встреча, созданная в Японии | `home_dc = DC-JP-TOKYO`; американские участники подключаются к SFU в Токио | `home_dc` выбирается по организатору |
| 8. Пользователь остался жить в Японии | Мигрировать ничего не нужно: данные пользователя глобальные (реплики во всех ДЦ), а встречи привязаны к своему `home_dc`, а не к пользователю. Старая сессия в `DC-US-EAST` истечёт по TTL | В системе нет «домашнего ДЦ пользователя», который пришлось бы переносить |
| 9. Logout | Сессия удаляется локально и в ДЦ из префикса, событие отзыва рассылается во все 8 ДЦ | Отозванная сессия не должна жить ни в одной копии |

| Решение | Значение |
| ------- | -------- |

### 4. Локальная балансировка нагрузки

#### 4.1. Границы локальной балансировки

| Поток | Где балансируется | В расчёте NGINX L7 |
| ----- | ----------------- | ------------------ |
| HTTPS API | Provider L4 → NGINX L7 → поды сервисов | Да |
| WSS: heartbeat, доставка чата и presence-событий | Provider L4 → NGINX L7 → WebSocket-поды | Да |
| RTP/SRTP медиа | Provider L4 → пул SFU, адрес SFU назначает control plane | Нет |
| Recording metadata | Provider L4 → NGINX L7 | Да |
| Поток записи SFU → recording workers | внутри ДЦ, по адресу из control plane | Нет |
| Межсервисные вызовы внутри ДЦ | gRPC, клиентская балансировка по endpoints Kubernetes Service | Нет |
| Межрегиональные вызовы: прокси `join` в `home_dc`, перенос сессии | gRPC с mTLS между ДЦ | Нет |

#### 4.2. Схема локальной и межсервисной балансировки

```mermaid
flowchart TD
    U["Client"] --> L4["Provider L4 LB: TCP/UDP, HA у провайдера"]
    L4 --> L7["NGINX L7 pool: TLS termination, HTTP/WS routing"]
    L7 --> API["Auth / Control Plane / Chat pods"]
    L7 --> WS["WebSocket / Presence pods"]
    API -->|"gRPC, round-robin по endpoints"| INT["Внутренние сервисы"]
    API --> PGB["PgBouncer"]
    L4 --> SFU["SFU media pool"]
    SFU --> REC["Recording workers"]
```

Межсервисная балансировка: gRPC-клиент получает список подов через headless Kubernetes Service и распределяет вызовы round-robin [^52][^54]. Обычная L4-балансировка здесь не подходит: gRPC держит одно долгое HTTP/2-соединение, и все вызовы ушли бы в один под.

#### 4.3. Механизмы резервирования

| Уровень | Что делает | Резервирование | Формула |
| ------- | ---------- | -------------- | ------- |
| Provider L4 LB | TCP/UDP вход в ДЦ | Managed HA у провайдера | Не считаем |
| NGINX L7 pool | HTTPS/WSS, TLS termination, routing | Active-active + health checks | `N+1` |
| NGINX L7 strict HA | Потеря AZ или стойки | Двойная ёмкость | `N*2` |
| SFU media pool | Видео, аудио, screen sharing | Sticky meeting + health checks | `N+1` |

#### 4.4. Ограничители для расчёта

| Ограничитель | Значение | Источник / расчёт |
| ------------ | -------: | ----------------- |
| `LB_HTTPS_RPS` | **342 785 RPS** | NGINX Ingress Controller, HTTPS, 24 CPU: запросы по уже открытым соединениям [^19] |
| `LB_TLS_CPS` | **10 274 новых TLS-соединений/с** | NGINX, HTTPS CPS на 24 CPU: полный TLS handshake на каждое соединение [^20]. Берём консервативно: тест Ingress даёт 58 811 SSL TPS [^19] |
| `LB_NET_GBPS` | **8.8 Gbps** | Throughput NGINX Ingress Controller [^19] |
| `MF_L7_REQ_SIZE` | **1 KB** | Размер запроса из HTTPS/RPS-бенчмарка [^19] |
| `MF_L7_CONN_MEM` | **54 KB на WSS-соединение** | NGINX держит проксируемое WebSocket-соединение (клиент + upstream) меньше чем в 20 KB: 50 000 соединений занимают < 1 GB [^77]. Плюс до 34 KB TLS-буферов, если они не освобождены [^78]. Это худший случай |
| Узел L7 | **24 vCPU / 64 GB / 100 GB SSD** | 56 GB под соединения: `56 GB / 54 KB ≈ 1.04 млн` WSS-соединений на узел. Дескрипторы и порты настраиваются (`ulimit`, `ip_local_port_range`) |
| Provider L4 | Внешний `LoadBalancer` | В Kubernetes внешний LB создаёт провайдер, он же отвечает за HA [^21] |

> **Исправлено после ревью.** В прошлой версии весь RPS, включая heartbeat, делился на SSL TPS. Но SSL TPS — это скорость **новых** TLS-рукопожатий, а heartbeat идёт по уже открытому WSS-соединению. Теперь у каждого ограничителя своя метрика. Для WebSocket главным ограничителем оказалась **память под одновременные соединения**, которая раньше не учитывалась.

#### 4.5. Расчёт количества L7-балансировщиков

```text
MF_L7_REST_RPS  = login + create + join + leave + list + recording_metadata + chat      = 45 486
MF_L7_WS_IN     = heartbeat                                                              = 675 000
MF_L7_WS_OUT    = (chat + join + leave) * (MF_MEET_SIZE - 1)                             = 328 125
MF_L7_PEAK_RPS  = MF_L7_REST_RPS + MF_L7_WS_IN + MF_L7_WS_OUT                            = 1 048 611
MF_L7_NEW_TLS   = (login + create + join + leave + list + recording_metadata) + join     = 24 653
                  # REST без keep-alive (худший случай) + новое WSS-соединение на каждый join
MF_L7_PEAK_GBPS = MF_L7_PEAK_RPS * 1 KB * 8 / 10^6                                       = 8.39
MF_L7_PEAK_CONN = MF_PEAK_WSS_CONNECTIONS                                                = 16 875 000

N_rps  = ceil(RPS_dc / 342 785)
N_tls  = ceil(NEW_TLS_dc / 10 274)
N_net  = ceil(GBPS_dc / 8.8)
N_conn = ceil(CONN_dc * 54 KB / 56 GB)
N_base = max(N_rps, N_tls, N_net, N_conn)

N+1 = N_base + 1
N*2 = N_base * 2
```

| Таблица | Консистентность | Почему |
| ------- | --------------- | ------ |
| `users` | Strong | Нельзя авторизовать несуществующего пользователя |
| `user_sessions` | Strong | Ошибка сессии ломает вход во встречу |
| `meetings` | Strong в `home_dc` | `join` должен видеть актуальный статус встречи |
| `meeting_participants` | Strong в `home_dc` | Нельзя дважды добавить одного участника |
| `meeting_invite_links` | Strong | Токен должен быть однозначно валиден или отозван |
| `user_meetings` | Eventual | Список встреч может обновиться с небольшой задержкой |
| `chat_messages` | Strong append внутри `meeting_id` | Внутри встречи важен порядок сообщений |
| `recordings` | Strong metadata + immutable file | UI должен видеть корректный статус записи |
| `recording_upload_buffer` | At-least-once + checksum | Чанк можно перезалить, итоговый файл проверяется |

#### 6.5. Шардирование и размещение по дата-центрам

Шардирование двухуровневое. **Уровень 1 — по ДЦ:** всё, что относится к встрече, лежит в её `home_dc`, код которого записан в `meeting_id` (п. 3.1, 3.4). **Уровень 2 — внутри ДЦ:** по ключам из таблицы ниже.

| Таблица | Что шардируем | Ключ шардинга | Почему |
| ------- | ------------- | ------------- | ------ |
| `users` | Не шардируем на MVP | `id` как partition key | `81.92 GB`, запись низкая; один primary на весь мир (п. 3.4) |
| `user_sessions` | Да | `session_id` | `115 млн` активных сессий, Redis Cluster в каждом ДЦ |
| `meetings` | Да: по `home_dc`, затем по `meeting_id` | `meeting_id` | `900 млн` строк за 30 дней на весь мир, в самом большом ДЦ ≈ 335 млн |
| `meeting_participants` | Да | `meeting_id + bucket` | `9 млрд` строк за 30 дней |
| `meeting_invite_links` | Да | `token_hash` | `join` начинается с токена |
| `user_meetings` | Да | `user_id` | Пользователь читает свой сплошной список; копия в каждом ДЦ |
| `meetings_runtime` | Да | `meeting_id` | ≈ `0.71 млн` ops/s на весь мир |
| `chat_messages` | Да | `meeting_id + bucket` | Чат читается по встрече и диапазону `seq` |
| `recordings` | Да | `meeting_id` | Записи читаются по встрече |
| `recording_upload_buffer` | Да | `recording_id` | Чанки собираются в одну запись |

Объём метаданных одного ДЦ невелик: в `DC-US-EAST` ≈ 215 GB и ≈ 4 100 чтений/с. Поэтому Citus в каждом ДЦ запускается в режиме single-node — координатор сам хранит шарды [^90]. Distribution column `meeting_id` задан сразу, и при росте добавляются worker-узлы с ребалансировкой шардов без смены схемы [^29][^30].

| Правило | Как применено |
| ------- | ------------- |
| Репликация масштабирует чтение | Для чтения можно использовать read-replica |
| Репликация не масштабирует запись | Запись масштабируется шардингом |
| JOIN на больших RPS не делаем | Hot-path разбит на point queries |
| Таблицы в разных СУБД не JOIN-ятся | Связи логические, не физические FK |
| Top-100 списка пользователя | Шард по `user_id`, чтение без fan-out |
| Чат встречи | `message_seq integer`, чтение от `last_seen_seq` до `head_seq` |

| API / событие | Peak RPS | Что трогаем | Строк / ключей на запрос | Lines per second |
| ------------- | -------: | ----------- | ------------------------: | ---------------: |
| `POST /auth/login` | **1 997** | `users` (чтение реплики), `user_sessions` (запись) | 2 | **3 993** |
| `POST /meetings` | **521** | `meetings`, `meeting_invite_links`, `user_meetings`, `meetings_runtime` | 4 | **2 083** |
| `POST /meetings/{id}/join` | **5 208** | `user_sessions`, `meeting_invite_links`, `meetings`, `meeting_participants`, `user_meetings`, `meetings_runtime` | 6 | **31 250** |

| `WS /presence/heartbeat` | **675 000** | `meetings_runtime` | 1 | **675 000** |
| `POST /meeting-chat/messages` | **26 042** | `chat_seq:{meeting_id}`, `chat_messages` | 2 | **52 083** |

Частота чата и списка встреч — допущения `MF_CHAT_PER_JOIN` и `MF_LIST_PER_DAU` из п. 2.1. Heartbeat обновляет только `meetings_runtime`: WSS-соединение авторизуется один раз при подключении по `join_token`, поэтому `user_sessions` на каждом heartbeat не читается. В прошлой версии здесь стояло 2 ключа, а в п. 6.8 нагрузка на `user_sessions` считалась без heartbeat — теперь оба пункта согласованы.

#### 6.7. API -> запрос -> БД

| API | Запрос к БД | Где выполняется | Индекс |
| --- | ----------- | --------------- | ------ |

| `POST /meetings/{id}/join` | `SELECT id, status, home_dc FROM meetings WHERE id = ?` | PostgreSQL + Citus | `PK(id)` |

#### 6.8. Кеш

| Кеш | Raw size | Peak ops | Cache heat | Решение |
| --- | -------: | -------: | ---------- | ------- |
| `meetings_runtime` | **0.864 GB** | **711 979 ops/s** | Очень высокий | Обязательно Redis |
| `user_sessions` | **14.72 GB** | **13 715 ops/s** | Высокий | Обязательно Redis |
| `active_invite_tokens` | **3.84 GB** | **5 208 ops/s** | Высокий только на join | Можно Redis + PostgreSQL как source of truth |
| `user_meetings_top100` | **1.472 TB** для всех DAU | **598 958 rows/s** | Большой объём | Не кешировать полностью, хранить read model в ScyllaDB |
| `chat_last100` | **168.75 GB** raw | зависит от активных встреч | Средний | In-memory room buffer, не общий Redis |

| Формула | Значение |
| ------- | -------- |
| `meetings_runtime` | `1 687 500 active meetings * 512 B = 0.864 GB`; ops = heartbeat 675 000 + join 5 208 + leave 5 208 + create 521 + INCR `chat_seq` 26 042 |
| `user_sessions` | ops = проверки при create, join, list (11 719) + запись при login (1 997) |
| `active_invite_tokens` | `30 000 000 meetings/day * 128 B = 3.84 GB` |
| `user_meetings_top100` | `115 000 000 DAU * 100 * 128 B = 1.472 TB` |
| `chat_last100` | `1 687 500 active meetings * 100 * 1 KB = 168.75 GB` |

#### 6.9. Денормализация и отказ от JOIN

| Денормализация | Где хранится | Зачем |
| -------------- | ------------ | ----- |
| `topic`, `scheduled_start`, `status`, `role` в `user_meetings` | ScyllaDB | Список встреч пользователя без JOIN с `meetings` |
| `participants_online_count` в `meetings_runtime` | Redis | Не считать `COUNT(*)` по участникам |
| `home_dc` в `meetings` | PostgreSQL + Citus | Быстро направлять meeting traffic |
| `storage_bucket`, `storage_key` в `recordings` | PostgreSQL + Citus | UI получает ссылку без обхода object storage |
| `message_seq` в `chat_messages` | ScyllaDB | Клиент читает лог от `last_seen_seq` до `head_seq` |

| Сценарий | Физическая проекция | Ключ чтения | JOIN в hot-path |
| -------- | ------------------- | ----------- | ---------------- |

| События конкретной встречи | `meetings`, `meeting_participants`, `chat_messages` | `meeting_id` | Нет |
| Доступ пользователя к своим встречам | `user_meetings` | `user_id` | Нет |
| Доступ встречи к участникам | `meeting_participants` | `meeting_id + bucket` | Нет |
| Чтение новых сообщений | `chat_messages` | `meeting_id + bucket + message_seq` | Нет |

### 7. Алгоритмы

#### 7.1. Список алгоритмов

| Алгоритм                      | Где используется           | Коротко                                         | На что влияет                          |
| ----------------------------- | -------------------------- | ----------------------------------------------- | -------------------------------------- |
| Adaptive Bitrate              | Media Plane / SFU          | меняем качество под сеть участника              | bandwidth, CPU клиента, SFU-routing    |
| Выбор SFU-слоя видео          | SFU                        | подписчику отдаётся нужный слой 1080p/720p/480p | исходящий трафик SFU                   |

#### 7.2. Adaptive Bitrate

| Параметр | Значение |
| -------- | -------- |
| Блок | `Media Plane / SFU` |
| Задача | Подобрать качество видео под текущую сеть участника |
| Вход | `packet_loss`, `RTT`, `jitter`, `available_bitrate`, `frames_dropped`, `audio_quality` |
| Ограничение | Звук важнее видео; понижение быстрое, повышение плавное |
| Результат | `target_profile = 1080p / 720p / 480p / audio_only` |

Метрики берутся из WebRTC stats API, для congestion control используются RTCP feedback-метрики по потерям и времени доставки пакетов [^40][^41]. Базовый профиль 720p опирается на bandwidth-оценку Zoom [^5].

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Всегда 720p | При плохой сети звонок рвётся | Не подходит |
| Только клиент решает качество | SFU хуже управляет исходящим трафиком | Не выбираем |
| Server-guided ABR | SFU видит подписчиков и управляет слоями | **Выбрано** |

Алгоритм:

1. Клиент раз в `1 сек` отправляет media stats.
2. SFU считает состояние сети: потери, RTT, jitter, доступная полоса.
3. Если сеть плохая — профиль снижается сразу.
4. Если сеть стабильна — профиль повышается на одну ступень.
5. Если страдает audio — video снижается первым.
6. Новый профиль применяется к подписке участника.

| Структура | Где | Поля |
| --------- | --- | ---- |
| `participant_network_stats` | memory / metrics pipeline | `meeting_id`, `user_id`, `loss`, `rtt`, `jitter`, `bitrate` |
| `participant_media_profile` | SFU memory | `meeting_id`, `user_id`, `target_profile`, `updated_at` |
| `meetings_runtime` | Redis Cluster | `meeting_id`, `active_profile_count`, `audio_degraded_count` |

```mermaid
flowchart TD
    A[Клиент отправляет media stats] --> B[SFU оценивает loss, RTT, jitter, bitrate]
    B --> C{Есть проблемы со звуком?}
    C -- Да --> D[Снизить видео до audio priority]
    C -- Нет --> E{Сеть ухудшилась?}
    E -- Да --> F[Понизить профиль сразу]
    E -- Нет --> G{Есть запас по bitrate?}
    G -- Да --> H[Повысить профиль на 1 ступень]
    G -- Нет --> I[Оставить профиль]
    D --> J[Применить target_profile]
    F --> J
    H --> J
    I --> J
    J --> A
```

| Влияние | Что меняется |
| ------- | ------------ |
| БД | Постоянные таблицы не меняются |
| Redis | В `meetings_runtime` можно хранить агрегаты качества |
| SFU | Нужна per-participant media state |
| Нагрузка | Снижается video download при плохой сети |

#### 7.3. Выбор SFU-слоя видео

| Параметр | Значение |
| -------- | -------- |
| Блок | `Media Plane / SFU` |
| Задача | Не транскодировать видео, а выбирать готовый слой |
| Вход | `target_profile`, `viewport`, `active_speaker`, доступные encodings |
| Ограничение | SFU не должен превращаться в MCU с высоким CPU |
| Результат | `selected_layer` для каждого подписчика |

SFU-подход выбран потому, что media-сервер маршрутизирует RTP-потоки [^44] между участниками, а не смешивает их в один общий поток [^14]. Для нескольких качеств используется simulcast / SVC: отправитель публикует несколько encodings, SFU выбирает нужный слой [^42].

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Single stream | Всем отдаётся одно качество | Плохо для слабой сети |
| MCU transcoding | Высокая CPU-нагрузка | Не подходит для highload |
| SFU + simulcast/SVC | Больше upload от говорящего, зато меньше CPU на сервере | **Выбрано** |

Алгоритм:

1. Клиент публикует несколько video layers.
2. SFU хранит список доступных слоёв для producer.
3. Для каждого consumer считается `target_profile`.
4. Активному говорящему (его определяет active speaker detection [^43]) и крупной плитке даётся слой выше.
5. Миниатюрам даётся слой ниже.
6. При деградации сети SFU переключает consumer на слой ниже.

| Структура | Где | Поля |
| --------- | --- | ---- |
| `producer_layers` | SFU memory | `producer_id`, `rid`, `width`, `height`, `max_bitrate` |
| `consumer_subscription` | SFU memory | `consumer_id`, `producer_id`, `selected_layer` |
| `participant_media_profile` | SFU memory | `user_id`, `target_profile`, `reason` |

```mermaid
flowchart TD
    A[Publisher отправляет video layers] --> B[SFU хранит available layers]
    C[Subscriber имеет target_profile] --> D[SFU выбирает layer]
    B --> D
    D --> E{Крупная плитка или active speaker?}
    E -- Да --> F[Выбрать слой выше]
    E -- Нет --> G[Выбрать слой ниже]
    F --> H[Отправить consumer stream]
    G --> H
```

| Влияние | Что меняется |
| ------- | ------------ |
| БД | Не требуется новая persistent-таблица |
| SFU | Нужна таблица подписок `consumer -> producer -> layer` |
| Сеть | Снижается исходящий трафик SFU |
| CPU | Нет постоянного transcoding на сервере |

### 9. Обеспечение надёжности

#### 9.1. Резервирование компонентов

| Компонент системы | Что резервируем | Способ резервирования | Формула | При отказе |
| ----------------- | --------------- | --------------------- | ------- | ---------- |
| `GeoDNS / GTM` | выбор ДЦ и переключение между ДЦ | managed-сервис: health checks + geo/latency routing + веса пулов [^15][^16][^17] | 8 ДЦ, у каждого резерв по п. 3.7 | ДЦ убирается из DNS-ответов, новые подключения уходят в здоровые ДЦ |
| `Anycast DNS` | авторитетные NS-серверы GTM | один Anycast IP из многих PoP провайдера [^83] | `N_PoP >= 2` | DNS-запросы уходят в ближайший живой PoP |
| `Provider L4 LB` | TCP/UDP вход в ДЦ | managed HA у провайдера, Service `LoadBalancer` [^21] | provider HA | backend-ноды с ошибками исключаются из балансировки |
| `NGINX L7 pool` | HTTPS/WSS, TLS termination | active-active, health checks, запас по памяти под соединения [^19][^20][^77] | `N+1`, для strict HA — `N*2` | клиенты переподключаются на живые L7-узлы |
| `Kubernetes` | pods, nodes, deployments | replicas, reschedule, self-healing [^54][^63] | `replicas >= 2`, `N+1 nodes` | pod пересоздаётся, workload переезжает на живую ноду |
| `Auth / Users API` | логин, профиль | stateless pods + локальная реплика `auth_pg` [^27][^54] | `N+1` в каждом ДЦ | запрос повторяется на другом поде |
| `Meeting Control Plane` | create/join/leave, прокси в `home_dc` | stateless pods [^54] | `N+1` в каждом ДЦ | новые запросы идут на живые поды в том же ДЦ |
| `WebSocket / Presence` | heartbeat, доставка чата, online-state | stateless WS-поды + Redis Cluster для runtime-state [^31][^54] | `N+1` в каждом ДЦ | клиент переподключается, состояние читается из Redis |
| `SFU media pool` | audio/video/screen sharing | sticky meeting + health checks, SFU без смешивания потоков [^14][^42] | `N+1` в каждом ДЦ | новые встречи не назначаются на плохой SFU; при отказе SFU клиент получает новый SFU и делает ICE restart [^84] |
| `Recording workers` | сборка и финализация записи | worker pool + retry + multipart upload [^46] | `N+1` в каждом ДЦ | незавершённую запись дописывает другой worker |
| `PostgreSQL auth_pg` | `users` | primary в `DC-US-EAST` + синхронная standby в другой AZ + 7 асинхронных реплик в остальных ДЦ, WAL/PITR, автоматический failover через Patroni [^27][^28][^86][^89] | `1 primary + 1 sync standby + 7 async` | standby становится primary без потери данных; при отказе `DC-US-EAST` primary становится реплика `DC-US-WEST` |
| `PostgreSQL + Citus` (`meeting_pg`, `recording_pg`) | встречи, ссылки, метаданные записей | в каждом ДЦ координатор с локальными шардами + синхронная standby; асинхронная реплика в парном ДЦ; WAL/PITR [^27][^29][^90] | `2 в ДЦ + 1 в парном ДЦ` | standby в соседней AZ; при отказе ДЦ — promote реплики в парном ДЦ |
| `PgBouncer` | пул соединений PostgreSQL | несколько PgBouncer-инстансов перед БД [^32] | 3 на ДЦ | приложение переключается на живой pooler |
| `Redis session_redis` | `user_sessions` | Redis Cluster в каждом ДЦ: 3 master + 3 replica [^31] | `3 master + 3 replica` на ДЦ | replica становится master; потерянные сессии — повторный логин |
| `Redis runtime_redis` | `meetings_runtime`, `chat_seq` | Redis Cluster в каждом ДЦ + TTL для hot-state [^22][^31] | `3 master + 3 replica` на ДЦ | heartbeat-state восстанавливают клиенты после переподключения |
| `ScyllaDB meeting_scylla` | `meeting_participants`, `user_meetings` | один кластер на все ДЦ: participants — RF=3 внутри `home_dc`, `user_meetings` — RF=3 в каждом ДЦ, `LOCAL_QUORUM` [^33][^80][^81] | `RF=3` | отказ узла не останавливает чтение и запись, пока жив кворум ДЦ |
| `ScyllaDB chat_scylla` | `chat_messages` | кластер в каждом ДЦ, append-only log, снапшоты в S3 парного ДЦ [^33] | `RF=3` | сообщения читаются с реплик, запись работает при отказе узла |
| `S3-compatible Object Storage` | записи встреч и чанки | multipart upload, strong consistency, ≥ 3 копии в 3 AZ `home_dc` [^23][^24][^46] | `>=3 copies` | файл доступен, незавершённые части можно дозагрузить |
| `Observability stack` | метрики, логи, traces | Prometheus/OpenTelemetry/Loki локально в каждом ДЦ, Grafana/Jaeger центрально [^56][^57][^58][^59][^60] | 2 узла на ДЦ + 2 центральных | сервис работает, но алерты и дашборды деградируют |

#### 9.2. Отказ целого дата-центра

Отказ одной AZ закрывается внутри ДЦ (п. 9.1). Отказ всего ДЦ — редкий сценарий, но для него есть явный план. Ниже — худший случай: отказ самого большого ДЦ, `DC-US-EAST` (37.27% нагрузки).

| Шаг | Что происходит | Время |
| --- | -------------- | ----- |
| 1 | Monitors GTM фиксируют отказ, `DC-US-EAST` убирается из DNS-ответов (п. 3.5) | ≈ 30 с + TTL 30 с |
| 2 | Новые подключения GTM раздаёт по резервам по `capacity_weight`: сначала `DC-US-WEST`, затем `DC-UK-LONDON`, `DC-DE-FRANKFURT`, `DC-BR-SAOPAULO` | сразу после шага 1 |
| 3 | Активные встречи `DC-US-EAST` обрываются, клиенты переподключаются через `api`. Подписанный `join_token` (`meeting_id`, роль, срок) проверяется в любом ДЦ, поэтому комната пересоздаётся в резервном ДЦ без похода в недоступную БД | десятки секунд |
| 4 | Асинхронная реплика Citus `DC-US-EAST` в `DC-US-WEST` становится primary; в GTM меняется соответствие «код ДЦ `us-east` → обслуживает `DC-US-WEST`». Запланированные встречи снова доступны | минуты, RPO — секунды |
| 5 | Primary `auth_pg` переезжает в `DC-US-WEST` (Patroni [^86]). Логин работает всё время на локальных репликах; регистрация и правка профиля ждут переключения | минуты |
| 6 | Чат и история участников встреч `DC-US-EAST` недоступны до восстановления ДЦ или до восстановления из снапшотов в S3 парного ДЦ | осознанный компромисс |

**Хватит ли ёмкости.** Холодный резерв ×2 по всем ДЦ не закладываем: это +100% к стоимости SFU. Вместо него на время инцидента SFU ограничивает профиль видео до group «high-quality video»: 1.0/0.6 Мбит/с вместо 2.6/1.8 для 720p [^5].

```text
трафик участника, 720p          = 2.6 + 1.8 + 0.08 + 0.15 = 4.63 Мбит/с
трафик участника, high-quality  = 1.0 + 0.6 + 0.08 + 0.15 = 1.83 Мбит/с  → 39.5% от 720p
ёмкость без DC-US-EAST          = 100% − 37.27% = 62.73% штатной
нагрузка при профиле high-quality = 39.5% штатного пика  <  62.73%  → помещается
```

Это верно даже при худшем допущении, что пики всех ДЦ совпали. На деле они разнесены по часовым поясам: в пик `DC-US-EAST` азиатские ДЦ работают ночью. Stateless-слои (NGINX L7, WS-поды) работают на облачных VM и поды Kubernetes, поэтому досоздаются за минуты; запас по соединениям у L7 — 28 млн при пике 16.9 млн.

#### 10.3. Потоки данных

Все потоки начинаются у клиента и расходятся по доменам. Media-поток (RTP/SRTP) намеренно идёт мимо `Ingress L7` — через `Provider L4` прямо в `SFU`: так мы не платим за TLS termination на видеотрафике и держим встречу sticky к одному SFU.

|   № | Поток | Путь | Хранилище |
| --: | ----- | ---- | --------- |
|   1 | Авторизация | `Client -> Ingress L7 -> Auth API` в ближайшем ДЦ | реплика `auth_pg` + `Redis session_redis` |
|   2 | Создание / вход во встречу | `Client -> Ingress L7 -> Control Plane -> PgBouncer`; `join` выполняется в `home_dc` | `PG+Citus meeting_pg`, `ScyllaDB meeting_scylla`, `Redis runtime_redis` |
|   3 | Presence / heartbeat | `Client -> Ingress L7 -> WebSocket/Presence` в `home_dc` | `Redis runtime_redis` |
|   4 | Чат встречи | `Client -> Ingress L7 -> Meeting Chat` в `home_dc`, доставка через WS | `Redis` (seq) + `ScyllaDB chat_scylla` |
|   5 | Media: видео / аудио / screen | `Client -> Provider L4 -> SFU` в `home_dc` (sticky) | поток |
|   6 | Запись встречи | `SFU -> Recording workers` | `Object Storage` (файлы) + `PG+Citus recording_pg` (метаданные) |
|   7 | Межрегиональный прокси | `Control Plane ближайшего ДЦ -> gRPC/mTLS -> Control Plane home_dc` | — |
|   8 | Межрегиональная репликация | `auth_pg primary -> реплики во всех ДЦ`; `user_meetings -> все ДЦ`; `Citus -> парный ДЦ` | `auth_pg`, `meeting_scylla`, `meeting_pg`, `recording_pg` |

Упрощённый поток:

```mermaid
flowchart TD
    C["Клиент"] --> DNS["GeoDNS / GTM, NS на Anycast"]
    DNS --> L4["Provider L4 ближайшего ДЦ"]
    L4 --> ING["Ingress L7"]
    L4 --> SFU["SFU (media) в home_dc"]
    ING --> SVC["API · Control Plane · WS · Chat · Recording"]
    SVC -->|"join в чужом ДЦ: gRPC в home_dc"| HOME["Control Plane home_dc"]
    SVC --> PGB["PgBouncer"]
    PGB --> PG["PostgreSQL + Citus"]
    SVC --> SC["ScyllaDB"]
    SVC --> RD["Redis"]
    SFU --> REC["Recording workers"]
    REC --> OBJ["Object Storage"]
```

Запись использует multipart upload в object storage, метаданные пишутся отдельно в Citus [^46][^29]. Доступ к PostgreSQL во всех потоках идёт через PgBouncer, чтобы не держать тысячи прямых соединений [^32].

### 11. Список серверов

Серверы считаются **по каждому ДЦ**: данные встречи живут в её `home_dc` (п. 3.4), поэтому в каждом ДЦ свой набор кластеров. Общее правило — `ceil(нагрузка_ДЦ / ёмкость_узла) + 1` (`N+1` в каждом ДЦ) с минимальным размером кластера, которого требует технология.
