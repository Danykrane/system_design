- расчёт L7: теперь учтена память под одновременные WSS-соединения;
- ёмкость SFU проверена по CPU;
- L4 — свой (IPVS + keepalived): облачный балансировщик провайдера не рассчитан на миллионы соединений;
- медиа идёт в SFU напрямую, мимо L4;

- цены обновлены на 11.10.2026, отдельно оценён внешний трафик;
- добавлены сводные продуктовые метрики, схема резервного копирования и балансировка запросов к БД;
- несостыковки между разделами устранены.

### 1. Тема и целевая аудитория

#### 1.1. Тип сервиса

| Параметр            | Значение                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| Учебное название    | **MeetFlow**                                                                                               |
| Тип сервиса         | Zoom-подобный сервис видеовстреч                                                                           |
| Основной сценарий   | Групповая онлайн-встреча с аудио, видео, демонстрацией экрана, чатом и записью                             |
| Целевые регионы     | Глобально, кроме материкового Китая: Америка, EMEA, Азиатско-Тихоокеанский регион; крупнейшие экономики среди обслуживаемых стран — США, Германия, Япония, Великобритания, Индия [^11] |
| Реальные аналоги    | Zoom, Microsoft Teams, Google Meet                                                                         |
| Масштаб для расчёта | `MF_MAU = 320 млн MAU`, `MF_DAU = 115 млн DAU`, `MF_DMP = 300 млн участий во встречах в день` [^1][^2][^3] |

#### 1.2. Рыночная ниша и реальные аналоги

| Аналог | Метрика | Что подтверждает |
| ------ | ------- | ---------------- |
| Microsoft Teams | 320 млн monthly active users — Microsoft на звонке по итогам FY24 Q1, октябрь 2023 [^1] | Массовый размер аудитории коммуникационного сервиса |
| Microsoft Teams | 115 млн daily active users, октябрь 2020 [^2] | Нижнюю публичную границу daily-аудитории для расчёта |
| Zoom | Более 300 млн daily meeting participants в апреле 2020 — из проспекта Zoom, поданного в SEC; это участники встреч, а не unique users [^3] | Массовую ежедневную нагрузку именно на видеовстречи |
| Zoom | Средняя встреча — 54 минуты и 10 участников, данные за 15.11.2020–15.11.2021 [^4] | Базу для продуктовой оценки видеозвонков |
| Zoom | $4.8688 млрд выручки за FY2026 и 4 468 клиентов с TTM-выручкой больше $100 000 [^10] | Актуальность ниши на 2026 год |

#### 1.3. Функционал MVP

| № | Функция MVP | Кратко | Метрика для расчёта |
| -: | ----------- | ------ | ------------------- |
| 1 | Создание встречи | Пользователь создаёт мгновенную или запланированную встречу | `MF_MEETINGS_DAY`, `POST /meetings` |
| 2 | Подключение к встрече | Участник входит по ссылке или приглашению | `MF_DMP`, `POST /meetings/{id}/join` |
| 3 | Групповая аудио- и видеосвязь | Участники общаются в 720p group video | `MF_VIDEO_UP_MBPS`, `MF_VIDEO_DOWN_MBPS`, `MF_AUDIO_MBPS` |
| 4 | Демонстрация экрана | Участник показывает экран | `MF_SCREEN_MBPS_MAX` |
| 5 | Чат во время встречи | Участники отправляют текстовые сообщения | `MF_CHAT_MSG_LIMIT`, `MF_CHAT_PER_JOIN` |
| 6 | Облачная запись | Организатор включает запись встречи | `MF_RECORD_QUOTA_GB`, `MF_RECORDING_SIZE_GB` |

#### 1.4. Ключевые продуктовые решения

| Решение | Значение для MVP | Что считается дальше |
| ------- | ---------------- | -------------------- |
| Расчёт ведётся от групповой встречи | Средняя встреча: `MF_MEET_SIZE = 10` участников | Количество встреч в сутки |
| Базовый профиль качества | 720p group video по официальным требованиям Zoom [^5] | Видео-трафик upload/download |
| Запись встречи включается в облако | Cloud recording сохраняет видео, аудио и текст чата [^7] | Хранилище записей |
| Хранилище записей ограничено квотой | Для Pro/Business у Zoom — 10 GB на licensed user [^8] | Верхняя граница object storage |
| Частота чата — явное допущение | Есть лимит сообщения, но нет публичной частоты сообщений на пользователя [^6]; принимаем 5 сообщений на одно участие | Нагрузка и хранилище чата (2.2–2.4), уточняется после запуска |
| Данные встреч хранятся 30 дней | Метаданные, участники, чат и записи старше 30 дней удаляются | Объём хранения (2.3) |
| Худший случай для записей | Считаем, что записывается каждая встреча; реальная доля записываемых встреч публично неизвестна | Объём object storage и его стоимость (2.3, 11.4) |
| Материковый Китай не обслуживаем | Для Китая нужен отдельный локальный контур: требования к локализации данных и блокировки трафика. В MVP его нет | Доли ДЦ (3.2) |

#### 1.5. Целевая аудитория

| Параметр | Значение |
| -------- | -------: |
| География | Глобальный рынок без материкового Китая; Zoom использовался почти в 200 странах и территориях [^4]; обслуживаем из 8 ДЦ (п. 3.2) |
| Месячная аудитория | `MF_MAU = 320 000 000` пользователей/месяц |
| Дневная аудитория | `MF_DAU = 115 000 000` пользователей/день |
| Участий во встречах в день | `MF_DMP = 300 000 000` участий/день |
| Средний размер встречи | `MF_MEET_SIZE = 10` участников |
| Средняя длительность встречи | `MF_MEET_LEN_MIN = 54` минуты |

### 2. Расчёт нагрузки

#### 2.1. Исходные метрики и методика расчёта

| Название | Описание (бывшее значение) | Источник / расчёт |
| -------- | -------------------------- | ----------------- |
| `MF_MAU` | 320 000 000 monthly active users; публичное значение Microsoft Teams, FY24 Q1 / 2023 | Берётся как целевой месячный масштаб аналога; без пересчёта на 2026, потому что более новой публичной MAU-метрики Teams в открытых источниках не найдено [^1] |
| `MF_DAU` | 115 000 000 daily active users; публичное значение Microsoft Teams, октябрь 2020 | Берётся как консервативная daily-аудитория аналога; это не статистика Zoom и не результат экстраполяции [^2] |
| `MF_DMP` | 300 000 000 daily meeting participants; публичное значение Zoom, апрель 2020 | Используется для нагрузки на видеовстречи; это участники встреч, один пользователь может считаться несколько раз [^3] |
| `MF_MEET_SIZE` | 10 участников в средней Zoom-встрече; данные за 15.11.2020–15.11.2021 | Используется для расчёта `MF_MEETINGS_DAY = MF_DMP / MF_MEET_SIZE` [^4] |
| `MF_MEET_LEN_MIN` | 54 минуты — средняя длительность Zoom-встречи; данные за 15.11.2020–15.11.2021 | Используется для расчёта participant-minutes [^4] |
| `MF_VIDEO_UP_MBPS` | 2.6 Mbps на участника для 720p group video upload | Официальные требования Zoom к bandwidth [^5] |
| `MF_VIDEO_DOWN_MBPS` | 1.8 Mbps на участника для 720p group video download | Официальные требования Zoom к bandwidth [^5] |
| `MF_VIDEO_HQ_MBPS` | 1.0 / 0.6 Mbps up/down для group «high-quality video» (ниже 720p) | Требования Zoom [^5]; профиль деградации при отказе ДЦ (п. 9.2) |
| `MF_AUDIO_MBPS` | 0.08 Mbps на участника для VoIP audio | Верхняя граница диапазона 60–80 kbps из требований Zoom [^5] |
| `MF_SCREEN_MBPS_MAX` | 0.15 Mbps на участника для screen sharing upper-bound | Верхняя граница диапазона 50–150 kbps для демонстрации экрана с миниатюрой видео (без 1080p) из требований Zoom [^5] |
| `MF_CHAT_MSG_LIMIT` | 4 000 символов на одно chat-сообщение | Лимит сообщения в Zoom Team Chat [^6]; для чата встречи берём его как ориентир |
| `MF_CHAT_PER_JOIN` | 5 сообщений на одно участие во встрече | **Проектное допущение**: публичной частоты нет [^6]. Раньше стояло только в п. 6.6 — теперь задано здесь и используется везде |
| `MF_CHAT_MSG_SIZE` | 1 KB в среднем на сообщение (максимум ≈ 10 KB при 4 000 символов) | Проектное допущение для хранилища чата |
| `MF_LIST_PER_DAU` | 3 открытия списка встреч на DAU в сутки | Проектное допущение. Раньше было неявно зашито в число 11 979 в п. 6.6 |
| `MF_LOGIN_PER_DAU` | 1 создание сессии (логин) на DAU в сутки | Проектное допущение. Раньше было неявно зашито в число 3 993 в п. 5.2 |
| `MF_CHAT_HISTORY_PER_JOIN` | 1 загрузка истории чата на одно участие: при входе во встречу и после переподключения | Проектное допущение |
| `MF_REC_VIEWS_PER_REC` | не больше 1 открытия записи на одну запись | Проектное допущение, верхняя оценка: публичной частоты просмотров нет |
| `MF_REC_PART_MB` | 8 MB — размер части при multipart upload записи в S3 | Проектное допущение: запись в 0.761 GB — это ≈ 95 частей, а S3 допускает до 10 000 частей на объект [^46] |
| `MF_RECORD_QUOTA_GB` | 10 GB cloud recording storage на licensed user | Квота Zoom для Pro/Business [^8] |
| `MF_HEARTBEAT_SEC` | 25 секунд между heartbeat-событиями | Дефолтный `pingInterval = 25000 ms` в Socket.IO [^9] |
| `MF_K_PEAK` | **1.5** (в прошлой версии — 3) | Коэффициент суточного пика: пиковый час / среднее за сутки. Применяется одинаково к RPS, bandwidth и числу одновременных соединений. Сервис глобальный: когда в Америке рабочий день, в Азии ночь, и часовые пояса сглаживают общую суточную кривую. Значение 1.5 — по замечанию ревьюера; 3 удваивало пиковые значения |

Текущая актуальность ниши проверяется не устаревшими usage-числами, а финансовой метрикой: Zoom в FY2026 показал $4.8688 млрд выручки и 4 468 крупных клиентов с TTM-выручкой больше $100 000 [^10]. Старые usage-метрики используются только там, где они прямо подписаны по году и где показана формула расчёта.

Все числа разделов 2–6, 9 и 11 считаются одним скриптом [`resource/calc/meetflow_calc.py`](resource/calc/meetflow_calc.py): при изменении допущения достаточно поменять константу и перезапустить. Данные о ВВП для долей ДЦ (п. 3.2) лежат рядом в [`imf_weo_2026apr_gdp_2025.json`](resource/calc/imf_weo_2026apr_gdp_2025.json).

Расчёт bandwidth в таблице:

```text
avg_bandwidth_Gbps  = MF_AVG_ONLINE_PARTICIPANTS * bitrate_Mbps / 1000
peak_bandwidth_Gbps = avg_bandwidth_Gbps * MF_K_PEAK
rec_stream_Gbps     = (MF_AVG_ONLINE_PARTICIPANTS / MF_MEET_SIZE) * (1.8 + 0.08) / 1000 * K
```

Поток в запись — внутренний трафик ДЦ: SFU отправляет его recording workers как ещё одному подписчику встречи. В интернет он не уходит, но нагружает SFU и воркеры записи, поэтому учитывается в разделе 11.

Глобальная балансировка отвечает на четыре вопроса. Короткие ответы:

| Вопрос | Решение в MeetFlow | Где подробно |
| ------ | ------------------ | ------------ |
| Где стоят дата-центры | 8 ДЦ: `DC-US-EAST`, `DC-US-WEST`, `DC-BR-SAOPAULO`, `DC-UK-LONDON`, `DC-DE-FRANKFURT`, `DC-IN-MUMBAI`, `DC-SG-SINGAPORE`, `DC-JP-TOKYO`. Абстрактного пула `OTHER` нет: каждая группа стран привязана к конкретному ДЦ | 3.2 |

«ДЦ» в работе — это регион провайдера из 3 зон доступности (AZ). Отказ одной AZ закрывается резервированием внутри ДЦ (разделы 4 и 9), отказ всего ДЦ — глобальной балансировкой.

#### 3.1. Функциональное разбиение по доменам

| Домен | Основная нагрузка | Куда направляется запрос | Точка записи |
| ----- | ----------------- | ------------------------ | ------------ |
| `Auth / Users` | логин, профиль | ближайший ДЦ по GeoDNS | `users` — primary `auth_pg` в `DC-US-EAST`; `user_sessions` — ДЦ, где выполнен логин |
| `Meeting Control Plane` | `POST /meetings`, `join`, `leave`, список встреч | ближайший ДЦ; `join` и `leave` проксируются в `home_dc` встречи | `meetings`, `meeting_invite_links` — `home_dc` |
| `Media Plane / SFU` | видео, аудио, screen sharing | только SFU в `home_dc` встречи, адрес приходит в ответе `join` | не хранится, это поток |
| `Presence / Heartbeat` | `WS /presence/heartbeat` | WS-endpoint `home_dc` встречи | `meetings_runtime` — Redis `home_dc` |
| `Meeting Chat` | сообщения внутри встречи | `home_dc` встречи | `chat_messages` — ScyllaDB `home_dc` |
| `Recording` | запись встречи | SFU → recording workers в `home_dc` | файлы — S3 `home_dc`, метаданные — `recording_pg` `home_dc` |
| `User meetings list` | top-100 встреч пользователя | ближайший ДЦ, чтение локальной копии | `user_meetings` пишется в `home_dc` встречи, ScyllaDB реплицирует его во все ДЦ |

`home_dc` — ДЦ, за которым закреплена встреча. Control plane выбирает его при `POST /meetings`: это ДЦ, который обработал запрос, то есть ближайший к организатору. Код `home_dc` записан в `meeting_id` (UUIDv8, первый байт — код ДЦ [^85]) и в invite-токен. Поэтому любой ДЦ понимает, куда направить `join`, без глобального справочника встреч.

```mermaid
flowchart TD
    U["Пользователь"] --> DNS["GeoDNS / GTM"]

    NEAR --> AUTH["Auth: login, профиль"]
```

#### 3.2. Выбор и расположение дата-центров

**Откуда доли ДЦ.** Первоисточники не раскрывают, сколько пользователей видеосервисов в каждой стране: Zoom и Microsoft публикуют только глобальные числа, а данные SimilarWeb методичка запрещает использовать как первоисточник. Поэтому нагрузку распределяем по официальной статистике, в три шага.

**Шаг 1. Доля страны — её доля в мировом ВВП.** Источник — IMF World Economic Outlook (апрель 2026): ВВП 2025 года в текущих долларах [^11]. Видеовстречи — прежде всего рабочий инструмент: средняя встреча длится 54 минуты и собирает 10 участников [^4]. Поэтому объём встреч следует за экономикой страны, а не за численностью населения. Материковый Китай не обслуживаем (п. 1.4), его ВВП не учитываем. Остаётся 194 экономики на 98 537.9 млрд $.

**Шаг 2. Каждую страну относим к ближайшему по задержке ДЦ.** Полный список стран по группам — в скрипте расчёта [`meetflow_calc.py`](resource/calc/meetflow_calc.py), значения ВВП — в [`imf_weo_2026apr_gdp_2025.json`](resource/calc/imf_weo_2026apr_gdp_2025.json).

**Шаг 3. США делим на восток и запад по населению.** На регион West по переписи 2020 приходится 23.7% населения [^73]. Внутри одной страны деловая активность на человека примерно одинакова, поэтому здесь берём население, а не ВВП. Западному побережью нужен свой ДЦ: путь до Вирджинии пересекает весь континент.

Доля = ВВП группы / 98 537.9. Доли округлены до 0.01 п. п. так, чтобы сумма была ровно 100%: у Южной Америки 4.644% → 4.65%. Именно эти доли используются во всех расчётах по ДЦ.

**Проверка по аналогу.** По макрорегионам получается: Америка — 40.89%, EMEA — 39.75%, APAC — 19.36%. У Zoom доля Америки в выручке выше — 72.1% (EMEA — 15.8%, APAC — 12.1%) [^72]. Zoom исторически сильнее всего в США. Наш масштаб — масштаб лидера рынка (320 млн MAU у Teams [^1]), поэтому берём нейтральную оценку по экономике, а не по выручке одного Zoom. Если реальная доля Америки окажется выше, меняются только размеры пулов в ДЦ, а не архитектура: GTM перераспределит новые подключения весами (п. 3.7), а запас на перекос даёт резерв из п. 9.2.

#### 3.4. Точки записи данных

Правило: **у каждого объекта одна точка записи** (primary), а чтение по возможности идёт из локальной копии в ближайшем ДЦ. Тогда не бывает двух одновременных записей одного объекта в разных ДЦ, и не нужен сложный multi-master с разрешением конфликтов.

| Данные | Точка записи | Где читаются | Репликация между ДЦ | Почему так |
| ------ | ------------ | ------------ | ------------------- | ---------- |
| `users` (`auth_pg`) | **один primary на весь мир — `DC-US-EAST`**, синхронная standby в другой AZ того же ДЦ | локальная асинхронная реплика в каждом ДЦ | streaming replication: primary → 7 реплик [^27][^89] | Нужна глобальная уникальность `email`. Записи редкие: даже если каждый DAU раз в сутки меняет профиль, в пик это ≤ 1 997 записей/с — одного primary хватает |
| `user_sessions` (`session_redis`) | ДЦ, где выполнен логин; код ДЦ — префикс `session_id` (`us-east.<128 бит>`) | там же; другой ДЦ один раз забирает сессию по префиксу (п. 3.8) | нет, перенос по запросу | Сессия нужна там, где пользователь сейчас; копии во всех ДЦ не нужны |

| `meetings_runtime` (`runtime_redis`) | `home_dc` | `home_dc` | нет | Эфемерное состояние, клиенты восстанавливают его при переподключении |

**Как запрос на запись попадает в точку записи:**

1. Запрос приходит в ближайший ДЦ (GeoDNS, п. 3.5).
2. Сервис определяет точку записи: для `users` это всегда `DC-US-EAST`, для данных встречи — код ДЦ из `meeting_id`.
3. Если точка записи в другом ДЦ, запрос проксируется по gRPC с mTLS по межрегиональному каналу [^52]. Это добавляет RTT между ДЦ — например, ≈ 153 мс Токио ↔ восточное побережье США [^87], но только для редких записей.
4. После своей записи пользователь несколько секунд читает из primary (read-your-writes), пока асинхронная реплика не догонит.

**Отказ точки записи.** Внутри `DC-US-EAST` primary `auth_pg` автоматически переключается на синхронную standby в соседней AZ без потери данных — через Patroni [^86]. При отказе всего `DC-US-EAST` primary становится реплика в `DC-US-WEST`, но по команде дежурного (runbook), а не автоматически. Причина: в схеме с двумя площадками Patroni держит во втором ДЦ standby-кластер, который повышают только вручную — второй ДЦ не может сам отличить отказ первого от обрыва связи [^97]. RPO — секунды лага асинхронной репликации. Логин продолжает работать: он читает локальную реплику и пишет сессию в локальный Redis. На время переключения блокируются только регистрация и изменение профиля.

#### 3.5. Схема DNS-балансировки — основной механизм переключения

**Ответ на вопрос «Anycast или DNS?»: ДЦ выбирается и переключается через DNS.** Используется GeoDNS/GTM — managed-сервис с геолокацией, latency-based routing, health checks и весами пулов [^15][^16][^17]. Anycast стоит только «под» DNS: авторитетные NS-серверы GTM-провайдера доступны по Anycast IP (п. 3.6).

| DNS-имя | Что выбирает | Политика | TTL |
| ------- | ------------ | -------- | --: |
| `api.meetflow.example` | VIP API edge ближайшего здорового ДЦ | geo + latency + health + веса | 30 с |
| `ws.<dc>.meetflow.example` | WebSocket edge конкретного `home_dc` | фиксированное региональное имя, приходит в ответе `join` | 30 с |
| SFU, IP:port | конкретный SFU в `home_dc` | не DNS: адрес и ICE-кандидаты приходят в ответе `join` | — |
| `rec.<dc>.meetflow.example` | скачивание записей из object storage `home_dc` | региональное имя, presigned URL | 300 с |
| `static.meetflow.example` | веб-клиент и статика | CDN провайдера | по CDN |

GeoDNS определяет местоположение по IP рекурсивного резолвера или по подсети клиента из EDNS Client Subnet [^82]. Поэтому ДЦ выбирается по тому, где пользователь находится сейчас, а не где он регистрировался.

```mermaid
sequenceDiagram
    participant C as Клиент
    participant NS as GeoDNS / GTM (NS на Anycast IP)
    participant E as API edge ближайшего ДЦ
    participant H as home_dc встречи
    C->>NS: 1. DNS-запрос api.meetflow.example
    NS->>NS: 2. гео + latency + health + веса
    NS-->>C: 3. VIP ближайшего здорового ДЦ
    C->>E: 4. HTTPS: login, create, join
    E->>H: 5. join проксируется в home_dc по коду из meeting_id
    H-->>C: 6. join_token: meeting_id, home_dc, ws.<dc>, IP SFU
    C->>H: 7. WSS: presence и чат
    C->>H: 8. SRTP по UDP в SFU
```

**Время переключения через DNS.** Monitor GTM опрашивает health-endpoint каждого ДЦ. Минимальный интервал зависит от тарифа: у Cloudflare это 60 с на Pro, 15 с на Business и 10 с на Enterprise; число неудач подряд до вывода ДЦ (`consecutive_down`) задаётся через API [^17]. Берём Enterprise: интервал 10 с и 3 неудачи подряд — ДЦ выводится из ответов за ≈ 30 с, плюс TTL 30 с. Итого новые подключения уходят в здоровый ДЦ примерно за минуту. На Business-тарифе было бы ≈ 45 с + 30 с. Часть резолверов кеширует дольше TTL, поэтому у клиента есть свой fallback: при ошибке соединения он заново резолвит имя, а если это не помогло — идёт на резервный региональный адрес из конфигурации приложения.

#### 3.6. Схема Anycast-балансировки

Anycast — один IP-адрес, который анонсируется по BGP из многих точек; пакет приходит в «ближайшую» по маршрутизации точку [^83]. В MeetFlow Anycast используется **только там, где запросы короткие и не хранят состояние на сервере**:

| Трафик | Anycast | Почему |
| ------ | ------- | ------ |
| DNS-запросы к авторитетным NS-серверам GTM | **Да** | UDP «запрос — ответ» без сессии: ответ из ближайшего PoP, устойчивость к отказу точки и DDoS [^83] |
| Статика веб-клиента | Да, через CDN провайдера | короткие запросы, контент одинаковый во всех точках |
| API `api.meetflow.example` | Нет | BGP выбирает маршрут по AS-path, а не по задержке и загрузке ДЦ: нельзя задать веса, вывести ДЦ на обслуживание (drain), учесть ёмкость. Глобальный proxy-балансировщик с одним Anycast IP есть у крупных облаков [^18], но он привязывает к сети одного облака |
| WebSocket | Нет | долгоживущее TCP-соединение: при перестроении BGP-маршрута пакеты уйдут в другой ДЦ, где нет состояния этого соединения [^83] |
| RTP/SRTP медиа | Нет | встреча живёт на конкретном SFU в `home_dc`, смена маршрута рвёт медиасессию |

```mermaid
flowchart LR
    C1["Клиент в Японии"] -->|"DNS-запрос на 198.51.100.53"| P1["NS PoP Токио"]
    C2["Клиент в Германии"] -->|"тот же адрес 198.51.100.53"| P2["NS PoP Франкфурт"]
    P1 --> A1["GTM отвечает: VIP DC-JP-TOKYO"]
    P2 --> A2["GTM отвечает: VIP DC-DE-FRANKFURT"]
```

Оба PoP анонсируют по BGP один и тот же адрес (в примере — документационный `198.51.100.53`), и маршрутизация приводит каждый запрос в ближайшую к клиенту точку.

Итог: Anycast ускоряет и защищает **получение DNS-ответа**, а **решение, в какой ДЦ идти, принимает GTM** — это и есть механизм переключения.

#### 3.7. Регулировка трафика и переключение между дата-центрами

Регулировка идёт через веса пулов в GTM. Monitors регулярно проверяют endpoints и выводят нездоровый пул из ротации [^16][^17].

```text
effective_weight = geo_match * health * capacity_weight * manual_weight
```

| Ситуация | Что делаем | Кого затрагивает |
| -------- | ---------- | ---------------- |
| Норма | Пользователь → ближайший здоровый ДЦ | — |
| ДЦ перегружен | Снижаем `capacity_weight`: новые пользователи и встречи уходят в резервные ДЦ | только новые |
| Плановые работы | `manual_weight = 0` (drain): новые встречи не создаются, текущие доживают | только новые |
| ДЦ недоступен | `health = 0`, ДЦ убирается из DNS-ответов | все, см. п. 9.2 |
| Деградация пула SFU | Control plane не назначает этот пул новым встречам. При отказе SFU клиент получает адрес нового SFU по WebSocket и делает ICE restart [^84] | встречи на этом SFU |

| Основной ДЦ | Резерв 1 | Резерв 2 | Почему |
| ----------- | -------- | -------- | ------ |
| `DC-US-EAST` | `DC-US-WEST` | `DC-UK-LONDON` | та же страна, затем ближайший ДЦ через Атлантику |
| `DC-US-WEST` | `DC-US-EAST` | `DC-JP-TOKYO` | та же страна, затем через Тихий океан |
| `DC-BR-SAOPAULO` | `DC-US-EAST` | `DC-DE-FRANKFURT` | прямые кабели в США и Европу |
| `DC-UK-LONDON` | `DC-DE-FRANKFURT` | `DC-US-EAST` | соседний европейский ДЦ |
| `DC-DE-FRANKFURT` | `DC-UK-LONDON` | `DC-US-EAST` | соседний европейский ДЦ, затем самый ёмкий ДЦ через Атлантику; страны Персидского залива GTM может отправить в `DC-IN-MUMBAI` |
| `DC-IN-MUMBAI` | `DC-SG-SINGAPORE` | `DC-DE-FRANKFURT` | ближайший ДЦ в Азии |
| `DC-SG-SINGAPORE` | `DC-JP-TOKYO` | `DC-IN-MUMBAI` | ближайшие ДЦ в Азии |
| `DC-JP-TOKYO` | `DC-SG-SINGAPORE` | `DC-US-WEST` | ближайший ДЦ в Азии, затем через Тихий океан |

Резервный ДЦ может быть меньше основного: `DC-UK-LONDON` (4.06%) не вместит `DC-DE-FRANKFURT` (35.69%), а `DC-US-WEST` (7.40%) — `DC-US-EAST` (28.84%). Поэтому столбцы «Резерв» задают **порядок предпочтения**, а не единственный адрес. GTM раздаёт трафик отказавшего ДЦ по нескольким ДЦ пропорционально свободной ёмкости (`capacity_weight`). Расчёт того, что ёмкости хватит, — в п. 9.2.

#### 3.8. Сценарий: вход в США, затем поездка в Японию

Вопрос: пользователь залогинился в США, а потом улетел в Японию. Что происходит?

```mermaid
sequenceDiagram
    participant C as Клиент в Японии
    participant DNS as GeoDNS
    participant JP as DC-JP-TOKYO
    participant US as DC-US-EAST
    C->>DNS: api.meetflow.example?
    DNS-->>C: VIP DC-JP-TOKYO (японский резолвер / ECS)
    C->>JP: GET /users/{id}/meetings, session_id = us-east.…
    JP->>JP: сессии нет в локальном session_redis
    JP->>US: gRPC: получить сессию us-east.…
    US-->>JP: сессия валидна, остаток TTL
    JP->>JP: сохранить сессию локально
    JP-->>C: список встреч из локальной копии user_meetings
    C->>JP: POST /meetings/{id}/join (встреча коллег, home_dc = US-EAST)
    JP->>US: проксирование join по коду ДЦ из meeting_id
    US-->>C: join_token, ws.us-east, IP SFU в US-EAST
    C->>US: WSS и SRTP напрямую в home_dc
```

| Шаг | Что происходит | Почему так |
| --- | -------------- | ---------- |
| 1. Логин в США | Пароль проверяется по локальной реплике `auth_pg`. Сессия `us-east.<id>` создаётся в `session_redis` `DC-US-EAST` | Логину не нужна запись в primary |
| 2. Прилёт в Японию | GeoDNS видит японский резолвер или подсеть клиента из ECS [^82] и отдаёт VIP `DC-JP-TOKYO` | ДЦ выбирается по текущему местоположению; привязки к стране логина нет |
| 3. Первый запрос в `DC-JP-TOKYO` | Сессии нет в локальном Redis. По префиксу `us-east` Auth один раз забирает её из `DC-US-EAST` (+≈ 153 мс [^87]) и сохраняет у себя. **Повторный логин не нужен** | Сессии не копируются во все ДЦ заранее, а переносятся по запросу |
| 4. Профиль | Чтение — из локальной реплики `auth_pg`, изменение — в primary `DC-US-EAST` | Одна точка записи для `users` (п. 3.4) |
| 5. Список встреч | Читается из локальной копии `user_meetings` в `DC-JP-TOKYO` | Keyspace реплицирован во все ДЦ |
| 6. Встреча американских коллег | `home_dc = DC-US-EAST`. `DC-JP-TOKYO` проксирует `join` в `DC-US-EAST` по коду ДЦ в `meeting_id`. WS и медиа идут в `DC-US-EAST`. RTT Токио ↔ Вашингтон ≈ 153 мс [^87], то есть сеть в одну сторону ≈ 77 мс. По ITU-T G.114 большинство разговорных приложений не страдают, если сквозная задержка «от рта до уха» в одну сторону меньше 150 мс [^88]. В этот бюджет входят и сеть до SFU (≈ 77 мс), и путь от SFU до собеседника в США, и кодек с джиттер-буфером. Поэтому разговор возможен, но близко к границе нормы | Все участники встречи должны быть на одном SFU. Улучшение после MVP — каскад SFU: клиент подключается к SFU в Токио, а тот пересылает потоки в SFU `home_dc` по магистрали |
| 7. Новая встреча, созданная в Японии | `home_dc = DC-JP-TOKYO`; американские участники подключаются к SFU в Токио | `home_dc` выбирается по организатору |
| 8. Пользователь остался жить в Японии | Мигрировать ничего не нужно: данные пользователя глобальные (реплики во всех ДЦ), а встречи привязаны к своему `home_dc`, а не к пользователю. Старая сессия в `DC-US-EAST` истечёт по TTL | В системе нет «домашнего ДЦ пользователя», который пришлось бы переносить |
| 9. Logout | Сессия удаляется локально и в ДЦ из префикса, событие отзыва рассылается во все 8 ДЦ | Отозванная сессия не должна жить ни в одной копии |

#### 3.9. Вывод по глобальной балансировке

| Решение | Значение |
| ------- | -------- |
| ДЦ | 8 ДЦ в трёх макрорегионах. Доли — по ВВП стран (IMF WEO) без материкового Китая, США делятся по переписи 2020; абстрактного `OTHER` нет |
| Механизм выбора и переключения ДЦ | **DNS**: GeoDNS/GTM с health checks и весами, TTL 30 с, плюс клиентский fallback |
| Anycast | Только авторитетные DNS-серверы и CDN для статики |
| Переключение медиа | На уровне приложения: новый SFU от control plane, ICE restart |
| Точки записи | `users` — один primary в `DC-US-EAST`; данные встречи — `home_dc`; `user_meetings` — локально с асинхронной репликацией во все ДЦ |
| Переезд пользователя | Без миграции и без повторного логина: сессия переносится по префиксу, данные пользователя читаются из локальной реплики |

### 4. Локальная балансировка нагрузки

#### 4.1. Границы локальной балансировки

| Поток | Где балансируется | В расчёте NGINX L7 |
| ----- | ----------------- | ------------------ |
| HTTPS API | L4 (IPVS) → NGINX L7 → поды сервисов | Да |
| WSS: heartbeat, доставка чата и presence-событий | L4 (IPVS) → NGINX L7 → WebSocket-поды | Да |
| Метаданные записей и ссылки на скачивание | L4 (IPVS) → NGINX L7 | Да |
| RTP/SRTP медиа | Напрямую на публичный IP:порт SFU из ответа `join`. Балансирует control plane: он выбирает SFU для встречи | Нет |
| Скачивание файла записи | Напрямую из object storage `home_dc` по presigned URL | Нет |
| Поток записи SFU → recording workers | Внутри ДЦ, по адресу из control plane | Нет |
| Межсервисные вызовы внутри ДЦ | gRPC, клиентская балансировка по endpoints Kubernetes Service | Нет |
| Межрегиональные вызовы: прокси `join` в `home_dc`, перенос сессии | gRPC с mTLS между ДЦ | Нет |

Медиа идёт мимо L4 и L7: клиент получает адрес конкретного SFU в ответе `join` (п. 3.5). Так встреча остаётся на одном SFU, а балансировщикам не нужно пропускать 78 Тбит/с.

**Клиент за NAT и межсетевым экраном.** У SFU публичный адрес, и он работает как ICE-Lite: сам соединение не начинает, а отвечает на проверки, которые присылает клиент [^102]. Поэтому клиенту за домашним или офисным NAT не нужен ни STUN, ни TURN, чтобы достучаться до SFU. Если UDP закрыт межсетевым экраном, клиент подключается к тому же SFU по TCP: SFU слушает и UDP, и TCP [^102], а ICE умеет предлагать TCP-кандидаты [^103]. Медиа поверх TCP хуже переносит потери, но звонок не рвётся. Не поддерживаем в MVP только сети, где прокси пропускает исключительно TLS на порт 443: для них нужен TURN-релей по TLS, это улучшение после MVP.

#### 4.2. Схема локальной и межсервисной балансировки

```mermaid
flowchart TD
    U["Client"] --> L4["L4: IPVS, Direct Routing + keepalived, VIP ДЦ"]
    L4 --> L7["NGINX L7 pool: TLS termination, HTTP/WS routing"]
    L7 --> API["Auth / Control Plane / Chat pods"]
    L7 --> WS["WebSocket / Presence pods"]
    API -->|"gRPC, round-robin по endpoints"| INT["Внутренние сервисы"]
    API --> PGB["PgBouncer"]
    U -->|"SRTP по UDP, адрес из ответа join"| SFU["SFU media pool"]
    SFU --> REC["Recording workers"]
```

**L4 — свой, на IPVS.** Директор IPVS принимает пакеты на VIP ДЦ и раздаёт TCP-соединения узлам NGINX. В режиме Direct Routing ответы идут от NGINX к клиенту напрямую, мимо директора [^92], поэтому директор видит только входящий трафик. Директоров два, active/standby: keepalived переносит VIP на живой директор по VRRP и сам проверяет здоровье узлов NGINX [^93].

Почему не облачный балансировщик провайдера. У Selectel самый мощный тип — «Продвинутый с резервированием»: 2 инстанса по 4 vCPU / 2 GB, до 3 Гбит/с (до 5 по заявке), а производительность HTTPS провайдер приводит для 10 000 одновременных соединений [^12]. В Kubernetes такой балансировщик создаётся для Service типа `LoadBalancer` [^21]. В одном нашем ДЦ одновременно до 6 млн WSS-соединений, поэтому этот вариант не подходит.

Межсервисная балансировка: gRPC-клиент получает список подов через headless Kubernetes Service и распределяет вызовы round-robin [^52][^54]. Обычная L4-балансировка здесь не подходит: gRPC держит одно долгое HTTP/2-соединение, и все вызовы ушли бы в один под.

#### 4.3. Механизмы резервирования

| Уровень | Что делает | Резервирование | Формула |
| ------- | ---------- | -------------- | ------- |
| L4: IPVS + keepalived | TCP-вход HTTPS/WSS в ДЦ, VIP | Active/standby: при отказе директора VIP переезжает по VRRP [^93] | `N+1` |
| NGINX L7 pool | HTTPS/WSS, TLS termination, routing | Active-active; keepalived исключает узел, не прошедший health check | `N+1` |
| NGINX L7 strict HA | Потеря AZ или стойки | Двойная ёмкость | `N*2` |
| SFU media pool | Видео, аудио, screen sharing | Sticky meeting + health checks; при отказе SFU клиент получает новый адрес и делает ICE restart | `N+1` |

#### 4.4. Ограничители для расчёта

| Ограничитель | Значение | Источник / расчёт |
| ------------ | -------: | ----------------- |
| `LB_HTTPS_RPS` | **341 232 RPS** | NGINX Ingress Controller, HTTPS, ответ 1 KB по уже открытым keep-alive-соединениям, 16 CPU [^19] |
| `LB_TLS_CPS` | **6 676 новых TLS-соединений/с** | NGINX, HTTPS CPS на 16 CPU: полный TLS handshake на каждое соединение, RSA 2048, OpenSSL 1.0.1f [^20]. С современным OpenSSL рукопожатия дешевле, так что значение консервативное |
| `LB_NET_GBPS` | **8.8 Gbps** | Throughput NGINX Ingress Controller; упор в 10GbE-карту тестового стенда, а не в CPU [^19] |
| `MF_L7_MSG_SIZE` | **1 KB** | Размер ответа в RPS-тесте [^19]; берём его как средний размер сообщения API и WebSocket |
| Почему значения для 16 CPU | — | В тестах NGINX «CPU» — физические ядра Xeon. Облачный узел на 24 vCPU — это ≈ 12 ядер с Hyper-Threading, поэтому берём ближайшую точку теста — 16 CPU, а не 24. Ни RPS, ни TLS всё равно не ограничивают расчёт (п. 4.6) |
| `MF_L7_CONN_MEM` | **54 KB на WSS-соединение** | NGINX держит проксируемое WebSocket-соединение (клиент + upstream) меньше чем в 20 KB: 50 000 соединений занимают < 1 GB [^77]. Плюс до 34 KB TLS-буферов, если они не освобождены [^78]. Это худший случай |
| Узел L7 | **24 vCPU / 64 GB / 100 GB SSD** | 56 GB под соединения: `56 GB / 54 KB ≈ 1.04 млн` WSS-соединений на узел. Дескрипторы и порты настраиваются (`ulimit`, `ip_local_port_range`) |

| Узел L4 | **EL11-SSD-10GE: 6 ядер / 32 GB / 10GE** | Директор пропускает только входящий трафик (Direct Routing [^92]) |

> **Исправлено после ревью.** В прошлой версии весь RPS, включая heartbeat, делился на SSL TPS. Но SSL TPS — это скорость **новых** TLS-рукопожатий, а heartbeat идёт по уже открытому WSS-соединению. Теперь у каждого ограничителя своя метрика. Для WebSocket главным ограничителем оказалась **память под одновременные соединения**, которая раньше не учитывалась.

| Пользователи | `users`, `user_sessions` | Аккаунты и активные сессии |
| Встречи | `meetings`, `meeting_participants`, `meeting_invite_links`, `user_meetings` | Создание, вход, роли, список встреч пользователя |

##### Описание таблиц

| Таблица | Тип данных | Назначение | Ключ | Основные связи |
| ------- | ---------- | ---------- | ---- | -------------- |
| `users` | persistent | Аккаунт пользователя | `id` | Создаёт встречи, пишет чат, имеет сессии |
| `user_sessions` | session state | Авторизованные пользовательские сессии | `session_id` | N:1 к `users` |
| `meetings` | persistent | Основная карточка встречи | `id` | N:1 к `users`, 1:N к участникам, чату и записям |
| `meeting_participants` | persistent | Участники встречи и их состояние | `meeting_id + user_id` | N:1 к `meetings`, N:1 к `users` |
| `meeting_invite_links` | persistent | Ссылки-приглашения во встречу | `id` | N:1 к `meetings`, N:1 к `users` |
| `user_meetings` | read model | Список встреч пользователя | `user_id + meeting_id` | N:1 к `users`, N:1 к `meetings` |
| `chat_messages` | persistent | Сообщения чата встречи | `id` | N:1 к `meetings`, N:1 к `users` |
| `recordings` | persistent / file metadata | Записи встреч и ссылки на файлы | `id` | N:1 к `meetings` |
| `recording_upload_buffer` | upload buffer | Части multipart upload записи до её завершения | `chunk_id` | N:1 к `recordings` |

##### Кеши, счётчики и буферы

Это производные от основных таблиц данные. На картинке их нет, но они хранятся и нагружают хранилища, поэтому описаны здесь, а их размеры и нагрузка — в п. 5.2.

| Сущность | Тип данных | Что хранит | Ключ | Связь |
| -------- | ---------- | ---------- | ---- | ----- |
| `meetings_runtime` | hot state | Онлайн-состояние идущей встречи: статус, число участников онлайн, пул SFU, время последнего heartbeat | `meeting_id` | 1:1 к `meetings` |
| `chat_seq` | счётчик | Последний выданный номер сообщения в чате встречи | `meeting_id` | 1:1 к `meetings` |
| `chat_dedup` | ключ идемпотентности | Уже принятые `client_msg_id` за последние 60 с и выданный им `message_seq` | `meeting_id + client_msg_id` | N:1 к `meetings` |
| `active_invite_tokens` | кеш | Токены приглашений во встречи за последние сутки | `token` | кеш `meeting_invite_links` |
| `chat_last100` | буфер в памяти | Последние 100 сообщений идущей встречи | `meeting_id` | кеш `chat_messages` |

#### 5.3. Требования к консистентности

| Таблица | Консистентность | Почему |
| ------- | --------------- | ------ |
| `users` | Strong | Нельзя авторизовать несуществующего пользователя |
| `user_sessions` | Strong | Ошибка сессии ломает вход во встречу |
| `meetings` | Strong в `home_dc` | `join` должен видеть актуальный статус встречи |
| `meeting_participants` | Strong в `home_dc` | Нельзя дважды добавить одного участника |
| `meeting_invite_links` | Strong | Токен должен быть однозначно валиден или отозван |
| `user_meetings` | Eventual | Список встреч может обновиться с небольшой задержкой |
| `chat_messages` | Strong append внутри `meeting_id` | Внутри встречи важен порядок сообщений |
| `recordings` | Strong metadata + immutable file | UI должен видеть корректный статус записи |
| `recording_upload_buffer` | At-least-once + checksum | Часть можно перезалить под тем же номером, итоговый файл проверяется |
| `meetings_runtime` | Eventual, last write wins | Эфемерное состояние; после потери его восстанавливают heartbeat-ы клиентов |
| `chat_seq`, `chat_dedup` | Strong в одном шарде Redis: проверка и выдача номера — один атомарный скрипт | Номер выдаётся ровно один раз, повтор запроса не создаёт дубль |

#### 5.4. Распределение нагрузки по ключам

| Ключ | Где используется | Распределение | Риск hot key | Что делаем логически |
| ---- | ---------------- | ------------- | ------------ | -------------------- |
| `user_id` | `users`, `user_sessions`, `user_meetings` | Почти равномерно | Низкий | Храним пользовательские данные отдельно от встреч |
| `meeting_id` | `meetings`, `participants`, `chat`, `recordings` | Неравномерно | Высокий на больших встречах | Встреча закрепляется за `home_dc`, код ДЦ записан в первом байте `meeting_id` (п. 3.1) |
| `meeting_id + user_id` | `meeting_participants`, `user_meetings` | Равномернее, чем один `meeting_id` | Средний | Участники пишутся отдельными строками |
| `session_id` | `user_sessions` | Равномерно | Низкий | Сессия ищется по прямому ключу |
| `token` | `meeting_invite_links` | Равномерно | Низкий | Уникальный токен приглашения |
| `message_id` | `chat_messages` | Равномерно | Низкий | Порядок задаётся внутри `meeting_id` |
| `recording_id` | `recordings`, `recording_upload_buffer` | По созданным записям | Средний | Файл после финализации не изменяется |
| `storage_url` | `recordings` | Может перекоситься по ДЦ/дате | Средний | Путь строится как `home_dc/date/hash(recording_id)` |

#### 6.1. Физическая схема БД

Для получения картинки использовался сервис [dbdiagram](https://dbdiagram.io/) с кодом из [этого файла](resource/physical-database-sql.md) ([интерактивная ссылка на работу](https://dbdiagram.io/d/6a3beef2d0074fe75d15ee2c)).
![Физическая схема БД](resource/icons/images/physical-database.svg)

Картинка показывает таблицы, поля, связи и привязку к хранилищам. Индексы и точные ключи dbdiagram не рисует: они — в [DBML](resource/physical-database-sql.md) и в п. 6.4. В Citus первичный ключ и UNIQUE обязаны включать колонку распределения [^94], поэтому физически ключи `recordings` и `meeting_invite_links` составные (п. 6.4), а на картинке показан логический идентификатор `id`.

#### 6.2. Где хранятся данные

| Таблица | Где хранится | Что хранится физически | Главный ключ доступа | Размещение по ДЦ (п. 3.4) |
| ------- | ------------ | ---------------------- | -------------------- | ------------------------- |
| `users` | PostgreSQL, `auth_pg` | Аккаунты пользователей | `id`, `email` | primary в `DC-US-EAST`, реплики во всех ДЦ |
| `user_sessions` | Redis Cluster, `session_redis` | Активные сессии с TTL | `session_id` = `<dc>.<128 бит>` | ДЦ логина, перенос по запросу |
| `meetings` | PostgreSQL + Citus, `meeting_pg` | Метаданные встреч | `id = meeting_id` | `home_dc` + реплика в парном ДЦ |
| `meeting_participants` | ScyllaDB, `meeting_scylla` | Участники и состояние входа | `meeting_id + bucket + user_id` | `home_dc` |
| `meeting_invite_links` | PostgreSQL + Citus, `meeting_pg` | Токены приглашений | `token_hash`, `token` | `home_dc` + реплика в парном ДЦ |
| `user_meetings` | ScyllaDB, `meeting_scylla` | Список последних встреч пользователя | `user_id + scheduled_start` | все ДЦ, RF=3 в каждом |
| `meetings_runtime` | Redis Cluster, `runtime_redis` | Онлайн-состояние встречи | `meeting_id` | `home_dc` |
| `chat_messages` | ScyllaDB, `chat_scylla` | Append-only лог сообщений | `meeting_id + bucket + message_seq` | `home_dc` |
| `recordings` | PostgreSQL + Citus, `recording_pg` | Метаданные записей | `meeting_id`, `id` | `home_dc` + реплика в парном ДЦ |
| `recording_upload_buffer` | S3-compatible Object Storage | Части multipart upload незавершённых записей; их список держит воркер записи, после сбоя он читается обратно из S3 [^46] | `recording_id + chunk_number` | `home_dc` |
| `chat_seq`, `chat_dedup`, `active_invite_tokens` | Redis Cluster, `runtime_redis` | Счётчик сообщений, ключи идемпотентности, кеш токенов | `meeting_id`, `token` | `home_dc` |
| `chat_last100` | Память Chat-сервиса | Буфер последних сообщений идущей встречи | `meeting_id` | `home_dc` |

`meeting_pg` и `recording_pg` — две схемы одной базы на Citus-кластере ДЦ. Отдельные базы не подошли бы: co-location работает только между таблицами одной базы. У `meetings` и `recordings` одна колонка распределения — `meeting_id`, поэтому шарды встречи и её записей лежат на одном узле [^30]. Нагрузка на один ДЦ при этом мала (п. 11.2).

#### 6.3. Выбор СУБД по таблицам

| Таблица | СУБД | Почему так |
| ------- | ---- | ---------- |
| `users` | PostgreSQL | Нужны транзакции, уникальный `email`, индексы |
| `user_sessions` | Redis Cluster | TTL и быстрый lookup сессии |
| `meetings` | PostgreSQL + Citus | SQL-метаданные + шардирование по `meeting_id` |
| `meeting_participants` | ScyllaDB | Много записей `join/leave`, JOIN не нужен |
| `meeting_invite_links` | PostgreSQL + Citus | Точечный lookup по токену и TTL-индекс |
| `user_meetings` | ScyllaDB | Top-100 встреч пользователя без JOIN |
| `meetings_runtime` | Redis Cluster | ≈ `738 000` ops/s в пике: heartbeat 675 000 + join/leave/create + `INCR chat_seq` + `SET NX` ключа идемпотентности чата |
| `chat_messages` | ScyllaDB | Append-only лог, чтение диапазона по `message_seq` |
| `recordings` | PostgreSQL + Citus | Статусы и метаданные записей |
| `recording_upload_buffer` | S3-compatible Object Storage | Чанки и большие файлы не хранятся в SQL |

#### 6.4. Индексы

| Таблица | Индекс | Для какого запроса |
| ------- | ------ | ------------------ |
| `users` | `PK(id)` | Получение пользователя по `user_id` |
| `users` | `UNIQUE(email)` | Логин и проверка дубля |
| `users` | `INDEX(created_at)` | Админские выборки по дате |
| `user_sessions` | `KEY session:{session_id}` | Проверка сессии |
| `user_sessions` | `TTL(expires_at)` | Автоудаление сессий |
| `meetings` | `PK(id)` | `join`, `leave`, `recording_metadata` |
| `meetings` | `INDEX(owner_id, scheduled_start)` | Список встреч владельца |
| `meetings` | `INDEX(home_dc, status)` | Выбор активных встреч в ДЦ |
| `meeting_participants` | `PK(meeting_id, bucket, user_id)` | Вход/выход участника |
| `meeting_participants` | `INDEX(user_id, last_joined_at)` | История участника |
| `meeting_invite_links` | `PK(token_hash, id)` | Колонка распределения — `token_hash = hash(token)`: Citus сразу направляет запрос в один шард. PK обязан её включать [^94] |
| `meeting_invite_links` | `UNIQUE(token_hash, token)` | Вход по ссылке. `token_hash` вычисляется из `token`, поэтому это та же уникальность токена |
| `meeting_invite_links` | `INDEX(expires_at)` | Удаление истёкших ссылок |
| `user_meetings` | `PK(user_id, scheduled_start, meeting_id)` | Top-100 встреч пользователя |
| `meetings_runtime` | `KEY runtime:{meeting_id}` | Heartbeat и счётчики |
| `meetings_runtime` | TTL ключа, его продлевает heartbeat | Брошенная встреча удаляется сама [^22]. Вторичных индексов в Redis нет, поэтому поиск «по времени последнего heartbeat» не нужен |
| `chat_seq`, `chat_dedup` | `KEY chat_seq:{meeting_id}`, `KEY chat_dedup:{meeting_id}:{client_msg_id}` | Hash tag `{meeting_id}` кладёт ключи встречи в один слот Redis Cluster [^31], поэтому проверка повтора и выдача номера — один атомарный скрипт |
| `chat_messages` | `PK(meeting_id, bucket, message_seq)` | Чтение сообщений по порядку |
| `chat_messages` | Ключ идемпотентности в Redis: `SET chat_dedup:{meeting_id}:{client_msg_id} <seq> NX EX 60` [^98] | Повтор запроса с тем же `client_msg_id` получает уже выданный `message_seq` и не создаёт дубль [^45]. В самой ScyllaDB нет UNIQUE: `INSERT` с тем же ключом перезаписывает строку [^101], а повтор с новым `message_seq` стал бы дублем |
| `recordings` | `PK(meeting_id, id)` | Карточка записи. Таблица распределена по `meeting_id`, и PK обязан её включать [^94] |
| `recordings` | `INDEX(meeting_id, created_at)` | Список записей встречи |
| `recordings` | `INDEX(status, created_at)` | Очередь обработки |
| `recording_upload_buffer` | `UNIQUE(recording_id, chunk_number)` | Номер части уникален в загрузке: повторная загрузка части под тем же номером её перезаписывает [^46] |
| `recording_upload_buffer` | `TTL(expires_at)` | Брошенные загрузки удаляет правило lifecycle `AbortIncompleteMultipartUpload` [^46] |

Индекс в шардированной таблице работает внутри шарда. Поэтому запрос должен сначала попадать в правильный шард по `meeting_id`, `user_id` или `token_hash`.

#### 6.5. Шардирование и размещение по дата-центрам

Шардирование двухуровневое. **Уровень 1 — по ДЦ:** всё, что относится к встрече, лежит в её `home_dc`, код которого записан в `meeting_id` (п. 3.1, 3.4). **Уровень 2 — внутри ДЦ:** по ключам из таблицы ниже.

| Таблица | Что шардируем | Ключ шардинга | Резервирование | Почему |
| ------- | ------------- | ------------- | -------------- | ------ |
| `users` | Не шардируем на MVP | `id` как partition key | Синхронная standby в другой AZ + асинхронная реплика в каждом ДЦ | `81.92 GB`, запись низкая; один primary на весь мир (п. 3.4) |
| `user_sessions` | Да | `session_id` | Redis Cluster: у каждого master есть replica на другом узле | `115 млн` активных сессий, Redis Cluster в каждом ДЦ |
| `meetings` | Да: по `home_dc`, затем по `meeting_id` | `meeting_id` | Citus: синхронная standby в другой AZ + асинхронная реплика в парном ДЦ | `900 млн` строк за 30 дней на весь мир, в самом большом ДЦ (`DC-DE-FRANKFURT`) ≈ 321 млн |
| `meeting_participants` | Да | `meeting_id + bucket` | ScyllaDB, RF=3 по 3 AZ `home_dc` | `9 млрд` строк за 30 дней |
| `meeting_invite_links` | Да | `token_hash` | Как у `meetings` | `join` начинается с токена |
| `user_meetings` | Да | `user_id` | ScyllaDB, RF=3 в каждом ДЦ | Пользователь читает свой сплошной список; копия в каждом ДЦ |
| `meetings_runtime` | Да | `meeting_id` | Redis replica; потерю восстанавливают heartbeat-ы клиентов | ≈ `0.74 млн` ops/s на весь мир вместе с `chat_seq` и `chat_dedup` |
| `chat_messages` | Да | `meeting_id + bucket` | ScyllaDB, RF=3 по 3 AZ `home_dc` + снапшоты (п. 6.12) | Чат читается по встрече и диапазону `seq` |
| `recordings` | Да | `meeting_id` | Как у `meetings` | Записи читаются по встрече |
| `recording_upload_buffer` | Да | `recording_id` | S3: ≥ 3 копии в 3 AZ | Части собираются в одну запись |

Объём метаданных одного ДЦ невелик: в самом большом, `DC-DE-FRANKFURT`, ≈ 206 GB и ≈ 5 950 чтений/с (встречи, ссылки и записи). Поэтому Citus в каждом ДЦ запускается в режиме single-node — координатор сам хранит шарды [^90]. Distribution column `meeting_id` задан сразу, и при росте добавляются worker-узлы с ребалансировкой шардов без смены схемы [^29][^30].

| Правило | Как применено |
| ------- | ------------- |
| Репликация масштабирует чтение | Для чтения можно использовать read-replica |
| Репликация не масштабирует запись | Запись масштабируется шардингом |
| JOIN на больших RPS не делаем | Hot-path разбит на point queries |
| Таблицы в разных СУБД не JOIN-ятся | Связи логические, не физические FK |
| Top-100 списка пользователя | Шард по `user_id`, чтение без fan-out |
| Чат встречи | `message_seq integer`, чтение от `last_seen_seq` до `head_seq` |

| Кеш | Raw size | Peak ops | Cache heat | Решение |

| `chat_seq` + `chat_dedup` | **≈ 0.16 GB** | **52 083 ops/s** | Высокий | Тот же `runtime_redis`, ключи встречи в одном слоте |
| `user_sessions` | **14.72 GB** | **14 236 ops/s** | Высокий | Обязательно Redis (`session_redis`) |
| `active_invite_tokens` | **3.84 GB** | **5 208 ops/s** | Высокий только на join | Можно Redis + PostgreSQL как source of truth |
| `user_meetings_top100` | **1.472 TB** для всех DAU | **598 958 rows/s** | Большой объём | Не кешировать полностью, хранить read model в ScyllaDB |
| `chat_last100` | **168.75 GB** raw | **≤ 520 833 rows/s** чтения, 26 042 записей/с | Средний | In-memory room buffer, не общий Redis |

| Формула | Значение |
| ------- | -------- |
| `meetings_runtime` | `1 687 500 active meetings * 512 B = 0.864 GB`; ops = heartbeat 675 000 + join 5 208 + leave 5 208 + create 521 = 685 938 |
| `chat_seq` + `chat_dedup` | ops = `INCR` 26 042 + `SET NX` 26 042 = 52 083; ключей идемпотентности `26 042 * 60 с ≈ 1.56 млн * 100 B ≈ 0.16 GB`. Всего на `runtime_redis` — 738 021 ops/s |
| `user_sessions` | ops = проверки при create, join, list и открытии записи (12 240) + запись при login (1 997) = 14 236 |
| `active_invite_tokens` | `30 000 000 meetings/day * 128 B = 3.84 GB` |
| `user_meetings_top100` | `115 000 000 DAU * 100 * 128 B = 1.472 TB` |
| `chat_last100` | `1 687 500 active meetings * 100 * 1 KB = 168.75 GB`; чтения — до `5 208 * 100` строк/с, записи — каждое новое сообщение |

#### 6.9. Денормализация и отказ от JOIN

| Денормализация | Где хранится | Зачем |
| -------------- | ------------ | ----- |
| `topic`, `scheduled_start`, `status`, `role` в `user_meetings` | ScyllaDB | Список встреч пользователя без JOIN с `meetings` |
| `participants_online_count` в `meetings_runtime` | Redis | Не считать `COUNT(*)` по участникам |
| `home_dc` в `meetings` | PostgreSQL + Citus | Быстро направлять meeting traffic |
| `storage_bucket`, `storage_key` в `recordings` | PostgreSQL + Citus | UI получает ссылку без обхода object storage |
| `message_seq` в `chat_messages` | ScyllaDB | Клиент читает лог от `last_seen_seq` до `head_seq` |

| Сценарий | Физическая проекция | Ключ чтения | JOIN в hot-path |
| -------- | ------------------- | ----------- | ---------------- |
| Top-100 актуальных встреч пользователя | `user_meetings` | `user_id` | Нет |
| События конкретной встречи | `meetings`, `meeting_participants`, `chat_messages` | `meeting_id` | Нет |
| Доступ пользователя к своим встречам | `user_meetings` | `user_id` | Нет |
| Доступ встречи к участникам | `meeting_participants` | `meeting_id + bucket` | Нет |
| Чтение новых сообщений | `chat_messages` | `meeting_id + bucket + message_seq` | Нет |

#### 7.2. Adaptive Bitrate

| Параметр | Значение |
| -------- | -------- |
| Блок | `Media Plane / SFU` |
| Задача | Подобрать качество видео под текущую сеть участника |
| Вход | `packet_loss`, `RTT`, `jitter`, `available_bitrate`, `frames_dropped`, `audio_quality` |
| Ограничение | Звук важнее видео; понижение быстрое, повышение плавное |
| Результат | `target_profile = 720p / 360p / 180p / audio_only` |

Метрики сети SFU получает из RTCP внутри самой медиасессии: отчёты о приёме с потерями и джиттером [^44] и feedback о времени доставки пакетов для congestion control [^41]. Клиент видит те же метрики через WebRTC stats API [^40]. Отдельных запросов к API и WebSocket для статистики нет, поэтому в расчёт нагрузки (п. 2.4) она не входит. Верхний профиль — 720p: на нём построен расчёт трафика (п. 2.4) по bandwidth-оценке Zoom [^5]. 1080p в MVP не включаем: он требует 3.8/3.0 Мбит/с [^5] и увеличил бы трафик и число SFU.

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Всегда 720p | При плохой сети звонок рвётся | Не подходит |
| Только клиент решает качество | SFU хуже управляет исходящим трафиком | Не выбираем |
| Server-guided ABR | SFU видит подписчиков и управляет слоями | **Выбрано** |

Алгоритм:

1. SFU получает RTCP-отчёты клиента — обычно несколько раз в секунду, внутри медиасессии.
2. SFU считает состояние сети: потери, RTT, jitter, доступная полоса.
3. Если сеть плохая — профиль снижается сразу.
4. Если сеть стабильна — профиль повышается на одну ступень.
5. Если страдает audio — video снижается первым.
6. Новый профиль применяется к подписке участника.

| Структура | Где | Поля |
| --------- | --- | ---- |
| `participant_network_stats` | memory / metrics pipeline | `meeting_id`, `user_id`, `loss`, `rtt`, `jitter`, `bitrate` |
| `participant_media_profile` | SFU memory | `meeting_id`, `user_id`, `target_profile`, `updated_at` |

```mermaid
flowchart TD
    A[SFU получает RTCP-отчёты клиента] --> B[SFU оценивает loss, RTT, jitter, bitrate]
    B --> C{Есть проблемы со звуком?}
    C -- Да --> D[Снизить видео до audio priority]
    C -- Нет --> E{Сеть ухудшилась?}
    E -- Да --> F[Понизить профиль сразу]
    E -- Нет --> G{Есть запас по bitrate?}
    G -- Да --> H[Повысить профиль на 1 ступень]
    G -- Нет --> I[Оставить профиль]
    D --> J[Применить target_profile]
    F --> J
    H --> J
    I --> J
    J --> A
```

| Влияние | Что меняется |
| ------- | ------------ |
| БД | Постоянные таблицы не меняются |
| Redis | Не меняется: профили живут в памяти SFU, метрики качества уходят в Prometheus (п. 8) |
| SFU | Нужна per-participant media state |
| Нагрузка | Снижается video download при плохой сети |

#### 7.3. Выбор SFU-слоя видео

| Параметр | Значение |
| -------- | -------- |
| Блок | `Media Plane / SFU` |
| Задача | Не транскодировать видео, а выбирать готовый слой |
| Вход | `target_profile`, `viewport`, `active_speaker`, доступные encodings |
| Ограничение | SFU не должен превращаться в MCU с высоким CPU |
| Результат | `selected_layer` для каждого подписчика |

SFU-подход выбран потому, что media-сервер маршрутизирует RTP-потоки [^44] между участниками, а не смешивает их в один общий поток [^14]. Для нескольких качеств используется simulcast / SVC: отправитель публикует несколько encodings, SFU выбирает нужный слой [^42].

| Альтернатива | Минус | Решение |
| ------------ | ----- | ------- |
| Single stream | Всем отдаётся одно качество | Плохо для слабой сети |
| MCU transcoding | Высокая CPU-нагрузка | Не подходит для highload |
| SFU + simulcast/SVC | Больше upload от говорящего, зато меньше CPU на сервере | **Выбрано** |

Алгоритм:

1. Клиент публикует несколько video layers.
2. SFU хранит список доступных слоёв для producer.
3. Для каждого consumer считается `target_profile`.
4. Активному говорящему (его определяет active speaker detection [^43]) и крупной плитке даётся слой выше.
5. Миниатюрам даётся слой ниже.
6. При деградации сети SFU переключает consumer на слой ниже.

| Структура | Где | Поля |
| --------- | --- | ---- |
| `producer_layers` | SFU memory | `producer_id`, `rid`, `width`, `height`, `max_bitrate` |
| `consumer_subscription` | SFU memory | `consumer_id`, `producer_id`, `selected_layer` |
| `participant_media_profile` | SFU memory | `user_id`, `target_profile`, `reason` |

```mermaid
flowchart TD
    A[Publisher отправляет video layers] --> B[SFU хранит available layers]
    C[Subscriber имеет target_profile] --> D[SFU выбирает layer]
    B --> D
    D --> E{Крупная плитка или active speaker?}
    E -- Да --> F[Выбрать слой выше]
    E -- Нет --> G[Выбрать слой ниже]
    F --> H[Отправить consumer stream]
    G --> H
```

| Влияние | Что меняется |
| ------- | ------------ |
| БД | Не требуется новая persistent-таблица |
| SFU | Нужна таблица подписок `consumer -> producer -> layer` |
| Сеть | Снижается исходящий трафик SFU |
| CPU | Нет постоянного transcoding на сервере |

#### 9.1. Резервирование компонентов

| Компонент системы | Что резервируем | Способ резервирования | Формула | При отказе |
| ----------------- | --------------- | --------------------- | ------- | ---------- |
| `GeoDNS / GTM` | выбор ДЦ и переключение между ДЦ | managed-сервис: health checks + geo/latency routing + веса пулов [^15][^16][^17] | 8 ДЦ, у каждого резерв по п. 3.7 | ДЦ убирается из DNS-ответов, новые подключения уходят в здоровые ДЦ |
| `Anycast DNS` | авторитетные NS-серверы GTM | один Anycast IP из многих PoP провайдера [^83] | `N_PoP >= 2` | DNS-запросы уходят в ближайший живой PoP |
| `L4: IPVS + keepalived` | TCP-вход HTTPS/WSS в ДЦ | пара директоров active/standby: VIP переезжает по VRRP, keepalived проверяет узлы NGINX [^91][^92][^93] | `N+1`: 2 на ДЦ | VIP за секунды переходит на резервный директор; оборванные соединения клиенты открывают заново; узел NGINX с ошибками исключается из балансировки |

| `Kubernetes` | pods, nodes, deployments | replicas, reschedule, self-healing [^54][^63] | `replicas >= 2`, `N+1 nodes` | pod пересоздаётся, workload переезжает на живую ноду |
| `Auth / Users API` | логин, профиль | stateless pods + локальная реплика `auth_pg` [^27][^54] | `N+1` в каждом ДЦ | запрос повторяется на другом поде |
| `Meeting Control Plane` | create/join/leave, прокси в `home_dc` | stateless pods [^54] | `N+1` в каждом ДЦ | новые запросы идут на живые поды в том же ДЦ |
| `Meeting Chat` | отправка сообщений, история чата | stateless pods; буфер последних сообщений в памяти — производный, его можно собрать заново из ScyllaDB [^54] | `N+1` в каждом ДЦ | запрос уходит на живой под, история догружается из ScyllaDB |
| `WebSocket / Presence` | heartbeat, доставка чата, online-state | stateless WS-поды + Redis Cluster для runtime-state [^31][^54] | `N+1` в каждом ДЦ | клиент переподключается, состояние читается из Redis |
| `SFU media pool` | audio/video/screen sharing | sticky meeting + health checks, SFU без смешивания потоков [^14][^42] | `N+1` в каждом ДЦ | новые встречи не назначаются на плохой SFU; при отказе SFU клиент получает новый SFU и делает ICE restart [^84] |
| `Recording workers` | сборка и финализация записи | worker pool + retry + multipart upload [^46] | `N+1` в каждом ДЦ | незавершённую запись дописывает другой worker |
| `PostgreSQL auth_pg` | `users` | primary в `DC-US-EAST` + синхронная standby в другой AZ + 7 асинхронных реплик в остальных ДЦ, WAL/PITR, автоматический failover внутри ДЦ через Patroni [^27][^28][^86][^89] | `1 primary + 1 sync standby + 7 async` | standby становится primary без потери данных; при отказе всего `DC-US-EAST` дежурный повышает реплику `DC-US-WEST` [^97] |
| `PostgreSQL + Citus` (`meeting_pg`, `recording_pg`) | встречи, ссылки, метаданные записей | в каждом ДЦ координатор с локальными шардами + синхронная standby; асинхронная реплика в парном ДЦ; WAL/PITR [^27][^29][^90] | `2 в ДЦ + 1 в парном ДЦ` | standby в соседней AZ; при отказе ДЦ дежурный повышает реплику в парном ДЦ [^97] |
| `PgBouncer` | пул соединений PostgreSQL | несколько PgBouncer-инстансов перед БД [^32] | 3 на ДЦ | приложение переключается на живой pooler |
| `Redis session_redis` | `user_sessions` | Redis Cluster в каждом ДЦ: 3 master + 3 replica [^31]. Оба кластера ДЦ работают на 3 общих серверах: на каждом сервере master одного шарда и replica другого (п. 11.3) | `3 master + 3 replica` на ДЦ | replica становится master; потерянные сессии — повторный логин |
| `Redis runtime_redis` | `meetings_runtime`, `chat_seq`, `chat_dedup` | Redis Cluster в каждом ДЦ + TTL для hot-state [^22][^31] | `3 master + 3 replica` на ДЦ | heartbeat-state восстанавливают клиенты после переподключения |
| `ScyllaDB meeting_scylla` | `meeting_participants`, `user_meetings` | один кластер на все ДЦ: у participants отдельный keyspace в каждом ДЦ с RF=3 внутри него, `user_meetings` — RF=3 в каждом ДЦ, `LOCAL_QUORUM` [^33][^80][^81] | `RF=3` | отказ узла не останавливает чтение и запись, пока жив кворум ДЦ |
| `ScyllaDB chat_scylla` | `chat_messages` | кластер в каждом ДЦ, append-only log, снапшоты в S3 парного ДЦ [^33] | `RF=3` | сообщения читаются с реплик, запись работает при отказе узла |
| `S3-compatible Object Storage` | записи встреч и части загрузки | multipart upload, strong consistency, ≥ 3 копии в 3 AZ `home_dc` [^23][^24][^46] | `>=3 copies` | файл доступен, незавершённые части можно дозагрузить |
| `Observability stack` | метрики, логи, traces | Prometheus/OpenTelemetry/Loki локально в каждом ДЦ, Grafana/Jaeger центрально [^56][^57][^58][^59][^60] | 2 узла на ДЦ + 2 центральных | сервис работает, но алерты и дашборды деградируют |

#### 9.2. Отказ целого дата-центра

Отказ одной AZ закрывается внутри ДЦ (п. 9.1). Отказ всего ДЦ — редкий сценарий, но для него есть явный план. Худший случай по ёмкости — отказ самого большого ДЦ, `DC-DE-FRANKFURT` (35.69% нагрузки). Особенность `DC-US-EAST`, где стоит primary `auth_pg`, разобрана после таблицы.

| Шаг | Что происходит | Время |
| --- | -------------- | ----- |
| 1 | Monitors GTM фиксируют отказ, `DC-DE-FRANKFURT` убирается из DNS-ответов (п. 3.5) | ≈ 30 с + TTL 30 с |
| 2 | Новые подключения GTM раздаёт по `capacity_weight`: сначала `DC-UK-LONDON`, затем `DC-US-EAST`, остальное — по свободной ёмкости других ДЦ (п. 3.7) | сразу после шага 1 |
| 3 | Активные встречи `DC-DE-FRANKFURT` обрываются, клиенты переподключаются через `api` со случайной задержкой, чтобы не устроить шторм. Подписанный `join_token` (`meeting_id`, роль, срок) проверяется в любом ДЦ, поэтому комната пересоздаётся в резервном ДЦ без похода в недоступную БД | десятки секунд |
| 4 | Дежурный повышает асинхронную реплику Citus `DC-DE-FRANKFURT` в `DC-UK-LONDON` до primary [^97]. Код ДЦ `de-frankfurt` из `meeting_id` начинает указывать на `DC-UK-LONDON`: в маршрутизации control plane и в GTM для регионального имени `ws.de-frankfurt`. Запланированные встречи снова доступны | минуты, RPO — секунды |
| 5 | Чат и история участников встреч `DC-DE-FRANKFURT` недоступны до восстановления ДЦ или до восстановления из снапшотов в S3 парного ДЦ (п. 6.12) | осознанный компромисс |

**Особенность `DC-US-EAST`.** Шаги те же, реплику Citus повышают в `DC-US-WEST`. Дополнительно в этом ДЦ стоит primary `auth_pg`. Логин всё время работает на локальных репликах в каждом ДЦ, а регистрация и правка профиля ждут, пока дежурный повысит реплику в `DC-US-WEST` (п. 3.4) — это минуты.

**Хватит ли ёмкости.** Холодный резерв ×2 по всем ДЦ не закладываем: это +100% к стоимости SFU. Вместо него на время инцидента SFU во всех ДЦ, которые принимают нагрузку, ограничивают профиль видео до group «high-quality video»: 1.0/0.6 Мбит/с вместо 2.6/1.8 для 720p [^5]. Поток в запись при этом не уменьшается.

```text
трафик участника, 720p              = 2.6 + 1.8 + 0.08 + 0.15 = 4.63 Мбит/с
трафик участника, high-quality      = 1.0 + 0.6 + 0.08 + 0.15 = 1.83 Мбит/с  → 39.5% от 720p
с потоком в запись (1.88 / 10 = 0.188 Мбит/с на участника):
  720p = 4.818, high-quality = 2.018 Мбит/с                              → 41.9% от 720p
ёмкость SFU без DC-DE-FRANKFURT     = 100% − 35.69% = 64.31% штатной
нагрузка при профиле high-quality   = 41.9% штатного пика  <  64.31%     → помещается
```

Это верно даже при худшем допущении, что пики всех ДЦ совпали. На деле они разнесены по часовым поясам. Отказ `DC-US-EAST` проверяется так же: 41.9% < 100% − 28.84% = 71.16%.

Stateless-слои (NGINX L7, WS-поды) работают на облачных VM и подах Kubernetes, поэтому досоздаются за минуты. Но и без этого запас есть:

- **Соединения.** У 21 узла L7 вне `DC-DE-FRANKFURT` — 21.8 млн соединений при пике 16.9 млн. У 22 узлов вне `DC-US-EAST` — 22.8 млн.
- **Шторм переподключений.** 6.0 млн клиентов Франкфурта открывают новые TLS-соединения: 6 022 688 / (21 узел × 6 676 в секунду) ≈ 43 с. Поэтому клиент переподключается со случайной задержкой в пределах минуты.

#### 10.3. Потоки данных

Все потоки начинаются у клиента и расходятся по доменам. Media-поток (RTP/SRTP) намеренно идёт мимо L4 и `Ingress L7` — прямо на публичный адрес `SFU` из ответа `join`. Так балансировщикам не нужно пропускать 78 Тбит/с, мы не платим за TLS termination на видеотрафике, а встреча остаётся на одном SFU.

|   № | Поток | Путь | Хранилище |
| --: | ----- | ---- | --------- |
|   1 | Авторизация | `Client -> L4 -> Ingress L7 -> Auth API` в ближайшем ДЦ | реплика `auth_pg` + `Redis session_redis` |
|   2 | Создание / вход во встречу | `Client -> L4 -> Ingress L7 -> Control Plane -> PgBouncer`; `join` выполняется в `home_dc` | `PG+Citus meeting_pg`, `ScyllaDB meeting_scylla`, `Redis runtime_redis` |
|   3 | Presence / heartbeat | `Client -> L4 -> Ingress L7 -> WebSocket/Presence` в `home_dc` | `Redis runtime_redis` |
|   4 | Чат встречи | `Client -> L4 -> Ingress L7 -> Meeting Chat` в `home_dc`, доставка через WS | `Redis` (seq, идемпотентность) + `ScyllaDB chat_scylla` |
|   5 | Media: видео / аудио / screen | `Client -> SFU` в `home_dc`, напрямую по адресу из ответа `join` | поток |
|   6 | Запись встречи | `SFU -> Recording workers -> Object Storage`; скачивание — `Client -> Object Storage` по presigned URL | `Object Storage` (файлы) + `PG+Citus recording_pg` (метаданные) |
|   7 | Межрегиональный прокси | `Control Plane ближайшего ДЦ -> gRPC/mTLS -> Control Plane home_dc` | — |
|   8 | Межрегиональная репликация | `auth_pg primary -> реплики во всех ДЦ`; `user_meetings -> все ДЦ`; `Citus -> парный ДЦ` | `auth_pg`, `meeting_scylla`, `meeting_pg`, `recording_pg` |

Упрощённый поток:

```mermaid
flowchart TD
    C["Клиент"] --> DNS["GeoDNS / GTM, NS на Anycast"]
    DNS --> L4["L4: IPVS ближайшего ДЦ"]
    L4 --> ING["Ingress L7"]
    C -->|"SRTP напрямую"| SFU["SFU (media) в home_dc"]
    ING --> SVC["API · Control Plane · WS · Chat · Recording"]
    SVC -->|"join в чужом ДЦ: gRPC в home_dc"| HOME["Control Plane home_dc"]
    SVC --> PGB["PgBouncer"]
    PGB --> PG["PostgreSQL + Citus"]
    SVC --> SC["ScyllaDB"]
    SVC --> RD["Redis"]
    SFU --> REC["Recording workers"]
    REC --> OBJ["Object Storage"]
```

Запись использует multipart upload в object storage, метаданные пишутся отдельно в Citus [^46][^29]. Доступ к PostgreSQL во всех потоках идёт через PgBouncer, чтобы не держать тысячи прямых соединений [^32].

#### 10.4. Балансировка: внешняя и внутренняя

| Уровень | Назначение | Граница балансировки |
| ------- | ---------- | -------------------- |
| Глобальный | Выбор ближайшего здорового ДЦ | внешняя: GeoDNS/GTM; Anycast только у DNS-серверов |
| ДЦ / Kubernetes | Приём трафика и stateless-сервисы | внутренняя: L4 (IPVS) → Ingress L7; медиа — напрямую в SFU, его выбирает control plane; gRPC round-robin между сервисами |
| Межрегиональный | Запись в точку записи другого ДЦ | gRPC с mTLS: прокси `join`, перенос сессии, репликация |
| Слой данных | Хранение и hot-state | шардинг по `home_dc` и ключам + репликация, не L7 |
| Наблюдаемость | Метрики, логи, traces | side-stack, HA |

Конфигурации `CL62R-NVMe` (Redis сессий) и `PL70-NVMe-10GE` (Scylla чата) из прошлой версии больше не используются. Эти нагрузки упираются в объём данных и ops/s, а не в 128–256 GB RAM и 32 ядра. Например, чат — это 26 042 записи/с на весь мир, а под него стояло 150 серверов по 32 ядра.

**Сверка ёмкости SFU с LiveKit.** LiveKit тестировал свой SFU на 16-ядерном инстансе Google Cloud `c2-standard-16` [^75]. В сценарии livestream пакеты размером с видео (≈ 950 байт): 4.25 Гбит/с при 92% CPU, то есть ≈ 0.29 Гбит/с на ядро инстанса. В сценарии «встреча 150 × 150» пакеты мелкие (≈ 120 байт), и выходит лишь ≈ 0.08 Гбит/с на ядро: SFU нагружают пакеты в секунду, а не биты. Во встрече на 10 человек основной трафик — пакеты видео 720p, поэтому за основу взят замер Jitsi. Это оптимистичная оценка: если реальные пакеты окажутся мельче, SFU-узлов понадобится больше.

Цены выделенных серверов не покрывают наш трафик. При порте больше 1 Гбит/с Selectel даёт 300 TB в месяц без ограничения полосы, увеличение лимита стоит 336 ₽/мес за шаг 3 TB. При среднем потоке больше 100 Мбит/с провайдер предлагает индивидуальные условия [^71][^66]. Через порты SFU проходит весь медиатрафик:

```text
медиа за месяц     = 562 545 000 GB/сутки * 30 = 16 876 350 TB ≈ 16.9 EB  (≈ 591 TB на узел SFU)
входит в тарифы    = 300 TB * 28 570 узлов     = 8 571 000 TB
сверх лимита       = 8 305 350 TB → 2 768 450 шагов по 3 TB * 336 ₽ ≈ 930.20 млн ₽/мес
```

Это верхняя оценка по публичному тарифу: на таком объёме трафик покупают по индивидуальному договору (транзит и пиринг), и он выходит дешевле. Поэтому в итог выше трафик не включён. С ним по публичному тарифу итог — **≈ 1 962.07 млн ₽/мес (≈ $23.11 млн)**, и трафик становится крупнейшей статьёй — больше хранения записей. Исходящий трафик S3 при скачивании записей стоит 1.96 ₽/GB [^70] и тоже не включён: частота просмотров неизвестна (п. 2.4).

**Изменение относительно версии, которую смотрел ревьюер (800.08 млн ₽/мес):**

- **Переход на `MF_K_PEAK = 1.5`** вместе с новыми долями ДЦ снизил итог примерно на 120 млн ₽. Пик определяет число серверов, но не объём записей, поэтому S3 от него не зависит.
- **Проверка SFU по CPU** добавила ≈ 297.16 млн ₽: без неё, при 10 Гбит/с на узел, итог был бы ≈ 734.70 млн ₽.
- **Рост цен Selectel с 01.07.2026** добавил ≈ 55 млн ₽, почти всё — S3.

Стоимость по-прежнему определяют те же блоки, что и нагрузку: хранение записей, медиа и внешний трафик медиа.
