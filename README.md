## 1. Тема и целевая аудитория

### 1.1. Тип сервиса

| Параметр | Значение |
| -------- | -------- |
| Учебное название | **MeetFlow** |
| Тип сервиса | Zoom-подобный сервис видеовстреч |
| Основной сценарий | Групповая онлайн-встреча: аудио, видео, демонстрация экрана, чат и запись |
| Реальные аналоги | Zoom, Microsoft Teams, Google Meet |

### 1.2. Рыночная ниша и реальные аналоги

| Аналог | Метрика | Что подтверждает |
| ------ | ------- | ---------------- |
| Microsoft Teams | 320 млн monthly active users, FY24 Q1 (октябрь 2023) [^1] | Масштаб аудитории коммуникационного сервиса |
| Microsoft Teams | 115 млн daily active users, октябрь 2020 [^2] | Дневную аудиторию для расчета |
| Zoom | Более 300 млн участий во встречах в день, апрель 2020 — проспект Zoom в SEC; это участия, а не уникальные пользователи [^3] | Ежедневную нагрузку именно на видеовстречи |
| Zoom | Средняя встреча — 54 минуты и 10 участников, данные за 15.11.2020–15.11.2021 [^4] | Базу продуктовой оценки |
| Zoom | $4.8688 млрд выручки за FY2026 и 4 468 клиентов с TTM-выручкой больше $100 000 [^10] | Актуальность ниши в 2026 году |

### 1.3. Функционал MVP

| № | Функция MVP | Кратко | Метрика для расчета |
| -: | ----------- | ------ | ------------------- |
| 1 | Создание встречи | Мгновенная или запланированная встреча | `MF_MEETINGS_DAY`, `POST /meetings` |
| 2 | Подключение к встрече | Вход по ссылке или приглашению | `MF_DMP`, `POST /meetings/{id}/join` |
| 3 | Групповая аудио- и видеосвязь | 720p group video | `MF_VIDEO_UP_MBPS`, `MF_VIDEO_DOWN_MBPS`, `MF_AUDIO_MBPS` |
| 4 | Демонстрация экрана | Участник показывает экран | `MF_SCREEN_MBPS_MAX` |
| 5 | Чат во время встречи | Текстовые сообщения участников | `MF_CHAT_MSG_LIMIT`, `MF_CHAT_PER_JOIN` |
| 6 | Облачная запись | Организатор включает запись встречи | `MF_RECORD_QUOTA_GB`, `MF_RECORDING_SIZE_GB` |

### 1.4. Ключевые продуктовые решения

| Решение | Значение для MVP | Что считается дальше |
| ------- | ---------------- | -------------------- |
| Расчет от групповой встречи | В средней встрече `MF_MEET_SIZE = 10` участников | Число встреч в сутки |
| Базовое качество — 720p group video | Требования Zoom к сети [^5] | Видеотрафик |
| Облачная запись | Сохраняет видео, аудио и текст чата [^7] | Хранилище записей |
| Квота на записи | У Zoom Pro/Business — 10 GB на пользователя [^8] | Верхняя граница хранилища |
| Частота чата — допущение | Есть лимит длины сообщения, но нет публичной частоты [^6]: берем 5 сообщений на участие | Нагрузка и хранилище чата |
| Данные встреч хранятся 30 дней | Метаданные, участники, чат и записи старше 30 дней удаляются | Объем хранения (2.3) |
| Худший случай для записей | Записывается каждая встреча: реальная доля публично неизвестна | Хранилище и его стоимость (2.3, 11.2) |
| Материковый Китай не обслуживаем | Нужен отдельный локальный контур: локализация данных и блокировки трафика | Доли ДЦ (3.2) |

## 3. Глобальная балансировка нагрузки

«ДЦ» в работе — регион провайдера из 3 зон доступности (AZ): отказ зоны закрывается внутри ДЦ, отказ всего ДЦ — глобальной балансировкой.

### 3.1. Функциональное разбиение по доменам

| Домен | Основная нагрузка | Куда направляется запрос | Точка записи |
| ----- | ----------------- | ------------------------ | ------------ |
| `Auth / Users` | логин, профиль | ближайший ДЦ по GeoDNS | `users` — primary `auth_pg` в `DC-US-EAST`; `user_sessions` — ДЦ, где выполнен логин |
| `Meeting Control Plane` | `POST /meetings`, `join`, `leave`, список встреч | ближайший ДЦ; `join` и `leave` проксируются в `home_dc` встречи | `meetings`, `meeting_invite_links` — `home_dc` |
| `Media Plane / SFU` | видео, аудио, screen sharing | только SFU в `home_dc` встречи, адрес приходит в ответе `join` | не хранится, это поток |
| `Presence / Heartbeat` | `WS /presence/heartbeat` | WS-endpoint `home_dc` встречи | `meetings_runtime` — Redis `home_dc` |
| `Meeting Chat` | сообщения внутри встречи | `home_dc` встречи | `chat_messages` — ScyllaDB `home_dc` |
| `Recording` | запись встречи | SFU → recording workers в `home_dc` | файлы — S3 `home_dc`, метаданные — `recording_pg` `home_dc` |
| `User meetings list` | top-100 встреч пользователя | ближайший ДЦ, чтение локальной копии | `user_meetings` пишется в `home_dc` встречи, ScyllaDB реплицирует его во все ДЦ |

`home_dc` — ДЦ встречи: его выбирает control plane при создании встречи (ближайший к организатору), а код ДЦ записан в `meeting_id`.

### 3.4. Точки записи данных

У каждого объекта одна точка записи (primary), чтение — по возможности из локальной копии: два ДЦ никогда не пишут один объект одновременно.

| Данные | Точка записи | Где читаются | Репликация между ДЦ |
| ------ | ------------ | ------------ | ------------------- |
| `users` (`auth_pg`) | **один primary на весь мир — `DC-US-EAST`**, синхронная standby в другой AZ | реплика в каждом ДЦ | асинхронная: primary → 7 реплик [^27][^89] |
| `user_sessions` (`session_redis`) | ДЦ логина; код ДЦ — префикс `session_id` | там же; другой ДЦ один раз забирает сессию по префиксу | нет, перенос по запросу |
| `meetings`, `meeting_invite_links` (`meeting_pg`) | `home_dc` встречи | `home_dc` | реплика в парный ДЦ |
| `meeting_participants` (`meeting_scylla`) | `home_dc` | `home_dc` | нет; снапшоты — в S3 парного ДЦ |
| `meetings_runtime` (`runtime_redis`) | `home_dc` | `home_dc` | нет |
| `chat_messages` (`chat_scylla`) | `home_dc` | `home_dc` | нет; снапшоты — в S3 парного ДЦ |
| `recordings` и файлы (`recording_pg`, S3) | `home_dc` | `home_dc`, по presigned URL | метаданные — реплика в парный ДЦ; файлы — ≥ 3 копии в 3 AZ `home_dc` |
| `user_meetings` (`meeting_scylla`) | `home_dc` встречи | ближайший ДЦ, локально | RF=3 в каждом ДЦ [^80][^81] |

### 3.5. Схема DNS-балансировки

ДЦ выбирается и переключается через GeoDNS/GTM — managed-сервис с геолокацией, latency-routing, health checks и весами пулов [^15][^16][^17]. При отказе ДЦ новые подключения уходят в здоровый ДЦ примерно за минуту.

| DNS-имя | Что выбирает | Политика | TTL |
| ------- | ------------ | -------- | --: |
| `api.meetflow.example` | VIP API edge ближайшего здорового ДЦ | geo + latency + health + веса | 30 с |
| `ws.<dc>.meetflow.example` | WebSocket edge конкретного `home_dc` | фиксированное региональное имя, приходит в ответе `join` | 30 с |
| SFU, IP:port | конкретный SFU в `home_dc` | не DNS: адрес и ICE-кандидаты приходят в ответе `join` | — |
| `rec.<dc>.meetflow.example` | скачивание записей из object storage `home_dc` | региональное имя, presigned URL | 300 с |
| `static.meetflow.example` | веб-клиент и статика | CDN провайдера | по CDN |

```mermaid
sequenceDiagram
    participant C as Клиент
    participant NS as GeoDNS / GTM (NS на Anycast IP)
    participant E as API edge ближайшего ДЦ
    participant H as home_dc встречи
    C->>NS: 1. DNS-запрос api.meetflow.example
    NS->>NS: 2. гео + latency + health + веса
    NS-->>C: 3. VIP ближайшего здорового ДЦ
    C->>E: 4. HTTPS: login, create, join
    E->>H: 5. join проксируется в home_dc по коду из meeting_id
    H-->>C: 6. join_token: meeting_id, home_dc, ws.#lt;dc#gt;, IP SFU
    C->>H: 7. WSS: presence и чат
    C->>H: 8. SRTP по UDP в SFU
```

### 3.7. Регулировка трафика между дата-центрами

Регулировка — через веса пулов в GTM: `effective_weight = geo_match * health * capacity_weight * manual_weight` [^16][^17].

| Ситуация | Что делаем | Кого затрагивает |
| -------- | ---------- | ---------------- |
| Норма | Пользователь → ближайший здоровый ДЦ | — |
| ДЦ перегружен | Снижаем `capacity_weight`: новые пользователи и встречи уходят в резервные ДЦ | только новые |
| Плановые работы | `manual_weight = 0` (drain): новые встречи не создаются, текущие доживают | только новые |
| ДЦ недоступен | `health = 0`, ДЦ убирается из DNS-ответов | все, см. п. 9.2 |
| Деградация пула SFU | Control plane не назначает этот пул новым встречам; при отказе SFU клиент получает новый SFU и заново устанавливает медиасоединение (ICE + DTLS) [^84] | встречи на этом SFU |

| Основной ДЦ | Парный ДЦ (резерв 1) | Резерв 2 |
| ----------- | -------------------- | -------- |
| `DC-US-EAST` | `DC-US-WEST` | `DC-UK-LONDON` |
| `DC-US-WEST` | `DC-US-EAST` | `DC-JP-TOKYO` |
| `DC-BR-SAOPAULO` | `DC-US-EAST` | `DC-DE-FRANKFURT` |
| `DC-UK-LONDON` | `DC-DE-FRANKFURT` | `DC-US-EAST` |
| `DC-DE-FRANKFURT` | `DC-UK-LONDON` | `DC-US-EAST` |
| `DC-IN-MUMBAI` | `DC-SG-SINGAPORE` | `DC-DE-FRANKFURT` |
| `DC-SG-SINGAPORE` | `DC-JP-TOKYO` | `DC-IN-MUMBAI` |
| `DC-JP-TOKYO` | `DC-SG-SINGAPORE` | `DC-US-WEST` |

Трафик отказавшего ДЦ GTM раздает по нескольким ДЦ пропорционально свободной емкости (п. 9.2). Методика долей ДЦ, подробности точек записи и переключения, сценарии — в [приложении 3](appendix/3-global-balancing.md).

## 4. Локальная балансировка нагрузки

### 4.1. Границы локальной балансировки

| Поток | Где балансируется | В расчете NGINX L7 |
| ----- | ----------------- | ------------------ |
| HTTPS API | L4 (IPVS) → NGINX L7 → поды сервисов | Да |
| WSS: heartbeat, доставка чата и presence-событий | L4 (IPVS) → NGINX L7 → WebSocket-поды | Да |
| Метаданные записей и ссылки на скачивание | L4 (IPVS) → NGINX L7 | Да |
| RTP/SRTP медиа | Напрямую на публичный IP:порт SFU из ответа `join`; SFU для встречи выбирает control plane | Нет |
| Скачивание файла записи | Напрямую из object storage `home_dc` по presigned URL | Нет |
| Поток записи SFU → recording workers | Внутри ДЦ, по адресу из control plane | Нет |
| Межсервисные вызовы внутри ДЦ | gRPC, клиентская балансировка по endpoints Kubernetes Service | Нет |
| Межрегиональные вызовы: прокси `join` в `home_dc`, перенос сессии | gRPC с mTLS между ДЦ | Нет |

Медиа идет мимо L4 и L7 напрямую в SFU: балансировщикам не нужно пропускать 78 Тбит/с, а встреча остается на одном SFU.

### 4.2. Схема локальной и межсервисной балансировки

```mermaid
flowchart TD
    U["Client"] --> L4["L4: IPVS, Direct Routing + keepalived, VIP ДЦ"]
    L4 --> L7["NGINX L7 pool: TLS termination, HTTP/WS routing"]
    L7 --> API["Auth / Control Plane / Chat pods"]
    L7 --> WS["WebSocket / Presence pods"]
    API -->|"gRPC, round-robin по endpoints"| INT["Внутренние сервисы"]
    API --> PGB["PgBouncer"]
    U -->|"SRTP по UDP, адрес из ответа join"| SFU["SFU media pool"]
    SFU --> REC["Recording workers"]
```

L4 — свой, на IPVS + keepalived: Direct Routing, VIP переезжает по VRRP [^92][^93]. L7 — пул NGINX с TLS termination. Между сервисами — gRPC с round-robin по подам [^52].

### 4.3. Механизмы резервирования

| Уровень | Что делает | Резервирование | Формула |
| ------- | ---------- | -------------- | ------- |
| L4: IPVS + keepalived | TCP-вход HTTPS/WSS в ДЦ, VIP | Active/standby: при отказе директора VIP переезжает по VRRP [^93] | `N+1` |
| NGINX L7 pool | HTTPS/WSS, TLS termination, routing | Active-active; keepalived исключает узел, не прошедший health check | `N+1` |
| NGINX L7 strict HA | Потеря AZ или стойки | Двойная емкость | `N*2` |
| SFU media pool | Видео, аудио, screen sharing | Sticky meeting + health checks; при отказе SFU клиент получает новый адрес и заново устанавливает медиасоединение | `N+1` |

### 4.4. Количество балансировщиков

| ДЦ | WSS-соединений в пик | NGINX L7, `N+1` | NGINX L7, `N*2` | L4 (IPVS) |
| -- | -------------------: | --------------: | --------------: | --------: |
| `DC-US-EAST` | 4 866 750 | **6** | 10 | 2 |
| `DC-US-WEST` | 1 248 750 | **3** | 4 | 2 |
| `DC-BR-SAOPAULO` | 784 688 | **2** | 2 | 2 |
| `DC-UK-LONDON` | 685 125 | **2** | 2 | 2 |
| `DC-DE-FRANKFURT` | 6 022 688 | **7** | 12 | 2 |
| `DC-IN-MUMBAI` | 848 813 | **2** | 2 | 2 |
| `DC-SG-SINGAPORE` | 1 176 188 | **3** | 4 | 2 |
| `DC-JP-TOKYO` | 1 242 000 | **3** | 4 | 2 |
| **Итого** | **16 875 000** | **28** | **40** | **16** |

Главный ограничитель L7 — память под WSS-соединения: до 54 KB на соединение, ≈ 1.04 млн соединений на узел 24 vCPU / 64 GB [^77][^78]. Закладываем `N+1` — 28 узлов; `N*2` (40) переживает потерю зоны доступности. Ограничители и расчет — в [приложении 4](appendix/4-local-balancing.md).

### 5.3. Требования к консистентности

| Таблица | Консистентность | Почему |
| ------- | --------------- | ------ |
| `users` | Strong | Нельзя авторизовать несуществующего пользователя |
| `user_sessions` | Strong | Ошибка сессии ломает вход во встречу |
| `meetings` | Strong в `home_dc` | `join` должен видеть актуальный статус встречи |
| `meeting_participants` | Strong в `home_dc` | Нельзя дважды добавить одного участника |
| `meeting_invite_links` | Strong | Токен должен быть однозначно валиден или отозван |
| `user_meetings` | Eventual | Список встреч может обновиться с небольшой задержкой |
| `chat_messages` | Strong append внутри `meeting_id` | Внутри встречи важен порядок сообщений |
| `recordings` | Strong metadata + immutable file | UI должен видеть корректный статус записи |
| `recording_upload_buffer` | At-least-once + checksum | Часть можно перезалить под тем же номером, итоговый файл проверяется |
| `meetings_runtime` | Eventual, last write wins | Эфемерное состояние: после потери его восстанавливают heartbeat-ы клиентов |
| `chat_seq`, `chat_dedup` | Strong в одном шарде Redis: проверка и выдача номера — один атомарный скрипт | Номер выдается ровно один раз, повтор запроса не создает дубль |

### 5.4. Распределение нагрузки по ключам

| Ключ | Где используется | Распределение | Риск hot key | Что делаем логически |
| ---- | ---------------- | ------------- | ------------ | -------------------- |
| `user_id` | `users`, `user_sessions`, `user_meetings` | Почти равномерно | Низкий | Храним пользовательские данные отдельно от встреч |
| `meeting_id` | `meetings`, `participants`, `chat`, `recordings` | Неравномерно | Высокий на больших встречах | Встреча закрепляется за `home_dc`, код ДЦ — в первом байте `meeting_id` |
| `meeting_id + user_id` | `meeting_participants`, `user_meetings` | Равномернее, чем один `meeting_id` | Средний | Участники пишутся отдельными строками |
| `session_id` | `user_sessions` | Равномерно | Низкий | Сессия ищется по прямому ключу |
| `token` | `meeting_invite_links` | Равномерно | Низкий | Уникальный токен приглашения |
| `message_id` | `chat_messages` | Равномерно | Низкий | Порядок задается внутри `meeting_id` |
| `recording_id` | `recordings`, `recording_upload_buffer` | По созданным записям | Средний | Файл после финализации не изменяется |
| `storage_url` | `recordings` | Может перекоситься по ДЦ и дате | Средний | Путь строится как `home_dc/date/hash(recording_id)` |

### 6.2. Выбор СУБД

### 6.3. Индексы

| Таблица | Индекс | Для какого запроса |
| ------- | ------ | ------------------ |
| `users` | `PK(id)` | Получение пользователя по `user_id` |
| `users` | `UNIQUE(email)` | Логин и проверка дубля |
| `users` | `INDEX(created_at)` | Админские выборки по дате |
| `user_sessions` | `KEY session:{session_id}` + `TTL(expires_at)` | Проверка сессии, автоудаление |
| `meetings` | `PK(id)` | `join`, `leave`, метаданные записи |
| `meetings` | `INDEX(owner_id, scheduled_start)` | Список встреч владельца |
| `meetings` | `INDEX(home_dc, status)` | Выбор активных встреч в ДЦ |
| `meeting_participants` | `PK(meeting_id, bucket, user_id)` | Вход и выход участника |
| `meeting_participants` | `INDEX(user_id, last_joined_at)` | История участника |
| `meeting_invite_links` | `PK(token_hash, id)` | Citus сразу идет в нужный шард по `token_hash = hash(token)` [^94] |
| `meeting_invite_links` | `UNIQUE(token_hash, token)` | Вход по ссылке |
| `meeting_invite_links` | `INDEX(expires_at)` | Удаление истекших ссылок |
| `user_meetings` | `PK(user_id, scheduled_start, meeting_id)` | Top-100 встреч пользователя |
| `meetings_runtime` | `KEY runtime:{meeting_id}` + TTL, его продлевает heartbeat | Heartbeat и счетчики; брошенная встреча удаляется сама [^22] |
| `chat_seq`, `chat_dedup` | `KEY chat_seq:{meeting_id}`, `KEY chat_dedup:{meeting_id}:{client_msg_id}` | Ключи встречи в одном слоте Redis Cluster [^31]: проверка повтора и выдача номера — один атомарный скрипт |
| `chat_messages` | `PK(meeting_id, bucket, message_seq)` | Чтение сообщений по порядку |
| `chat_messages` | Ключ идемпотентности `SET chat_dedup:{meeting_id}:{client_msg_id} <seq> NX EX 60` [^98] | Повтор сообщения не создает дубль [^45] |
| `recordings` | `PK(meeting_id, id)` | Карточка записи; PK включает колонку распределения [^94] |
| `recordings` | `INDEX(meeting_id, created_at)` | Список записей встречи |
| `recordings` | `INDEX(status, created_at)` | Очередь обработки |
| `recording_upload_buffer` | `UNIQUE(recording_id, chunk_number)` + `TTL(expires_at)` | Повторная загрузка части ее перезаписывает; брошенные загрузки удаляет lifecycle [^46] |

### 6.4. Шардирование и резервирование

Шардирование двухуровневое: сначала по ДЦ (`home_dc`, код в `meeting_id`), затем внутри ДЦ — по ключу из таблицы.

| Таблица | Ключ шардинга | Резервирование |
| ------- | ------------- | -------------- |
| `users` | не шардируем на MVP | синхронная standby в другой AZ + реплика в каждом ДЦ |

| `meetings` | `meeting_id` | Citus: синхронная standby в другой AZ + реплика в парном ДЦ |
| `meeting_participants` | `meeting_id + bucket` | ScyllaDB, RF=3 по 3 AZ `home_dc` |
| `meeting_invite_links` | `token_hash` | как у `meetings` |
| `user_meetings` | `user_id` | ScyllaDB, RF=3 в каждом ДЦ |
| `meetings_runtime` | `meeting_id` | Redis replica; потерю восстанавливают heartbeat-ы |

| `recordings` | `meeting_id` | как у `meetings` |

## 7. Алгоритмы

### 7.1. Список алгоритмов

| Алгоритм | Задача | Вход → результат | Почему так |
| -------- | ------ | ---------------- | ---------- |
| Adaptive Bitrate | Подобрать качество видео под сеть участника | Потери, RTT, jitter и доступная полоса из RTCP-отчетов [^44][^41] → профиль 720p / 360p / 180p / audio_only | SFU видит всех подписчиков и управляет слоями; звук важнее видео; понижение быстрое, повышение плавное |
| Выбор SFU-слоя видео | Не перекодировать видео, а выбирать готовый слой | Слои simulcast/SVC [^42], размер плитки, активный говорящий [^43] → слой для каждого подписчика | SFU пересылает готовые слои; MCU с перекодированием слишком дорог по CPU |

### 7.2. Adaptive Bitrate

```mermaid
flowchart TD
    A[SFU получает RTCP-отчеты клиента] --> B[SFU оценивает loss, RTT, jitter, bitrate]
    B --> C{Есть проблемы со звуком?}
    C -- Да --> D[Снизить видео до audio priority]
    C -- Нет --> E{Сеть ухудшилась?}
    E -- Да --> F[Понизить профиль сразу]
    E -- Нет --> G{Есть запас по bitrate?}
    G -- Да --> H[Повысить профиль на 1 ступень]
    G -- Нет --> I[Оставить профиль]
    D --> J[Применить target_profile]
    F --> J
    H --> J
    I --> J
    J --> A
```

### 7.3. Выбор SFU-слоя видео

```mermaid
flowchart TD
    A[Publisher отправляет video layers] --> B[SFU хранит available layers]
    C[Subscriber имеет target_profile] --> D[SFU выбирает layer]
    B --> D
    D --> E{Крупная плитка или active speaker?}
    E -- Да --> F[Выбрать слой выше]
    E -- Нет --> G[Выбрать слой ниже]
    F --> H[Отправить consumer stream]
    G --> H
```

Альтернативы, шаги и структуры данных алгоритмов — в [приложении 7](appendix/7-algorithms.md).

## 8. Технологии

### 8.1. Разработка

| Технология | Где используется | Почему |
| ---------- | ---------------- | ------ |
| `C++23` | Backend, control plane, SFU, recording workers | Низкая latency, контроль памяти, строгая типизация [^47] |
| `TypeScript` | Web-клиент и админка | Типизированный frontend, удобная работа с WebRTC API [^48] |
| `SQL`, `CQL` | PostgreSQL / Citus, ScyllaDB | Транзакции и составные индексы [^25][^26]; запросы по partition key [^62] |
| `CMake` + `Conan 2` | Сборка C++-сервисов и зависимости | Target-based сборка, зафиксированные версии библиотек [^49][^50] |
| `Boost.Asio / Boost.Beast` | HTTP, WSS, асинхронная сеть | Асинхронная сеть в C++ без лишнего runtime [^51] |
| `gRPC + Protobuf` | Внутренние вызовы между сервисами | Строгие контракты, генерация C++ client/server кода [^52] |
| `OpenSSL` | TLS / mTLS | Шифрование HTTPS/WSS и внутренних соединений [^61] |
| `WebRTC` | Аудио, видео, screen sharing | Стек real-time media, RTCP feedback и media stats [^40][^41] |
| `SFU` | Media Plane | Маршрутизация потоков без смешивания видео, simulcast/SVC [^14][^42] |

### 8.2. Инфраструктура и данные

| Технология | Где используется | Почему |
| ---------- | ---------------- | ------ |
| `GeoDNS / GTM (managed)` | Выбор ДЦ и переключение между ДЦ | Geo + latency routing, health checks, веса пулов; NS-серверы на Anycast [^15][^16][^17][^83] |
| `IPVS + keepalived` | L4 в каждом ДЦ | Балансировка TCP в ядре Linux; Direct Routing; VIP переезжает по VRRP [^91][^92][^93] |
| `NGINX L7` | HTTPS/WSS edge | TLS termination, L7 routing, балансировка API [^19][^20] |
| `Kubernetes`, `Docker / OCI`, `Helm` | Оркестрация, упаковка и деплой сервисов | Scaling, service discovery, self-healing; один образ для всех сред; версионируемые шаблоны [^53][^54][^55] |
| `PostgreSQL` | `users`, метаданные встреч и записей | Транзакции с изоляцией (strong consistency) [^26], составные индексы [^25] |
| `Citus` | Шардирование PostgreSQL | Распределение таблиц по `meeting_id` / `token_hash` [^29] |
| `PgBouncer` | Пул соединений PostgreSQL | Меньше постоянных соединений к PostgreSQL [^32] |
| `Patroni` | Failover PostgreSQL | Внутри ДЦ автоматически переключает на синхронную standby [^86]; между ДЦ standby-кластер повышают вручную [^97] |
| `Redis Cluster` | Сессии, `meetings_runtime`, счетчики | TTL, hot state, быстрый доступ по ключу [^22][^31] |
| `ScyllaDB` | Участники, чат, `user_meetings` | Высокая нагрузка на запись, чтение по ключу без JOIN, мультиДЦ-репликация [^33][^34][^80] |
| `S3-compatible Object Storage` | Записи встреч и части загрузки | Большие неизменяемые файлы, multipart upload [^23][^46] |
| `Prometheus`, `Grafana`, `OpenTelemetry`, `Loki`, `Jaeger` | Метрики, дашборды, логи, трассировка | Единый сбор метрик, логов и трасс; поиск узких мест между сервисами [^56][^57][^58][^59][^60] |

## 9. Обеспечение надежности

### 9.1. Резервирование компонентов

| Компонент | Резервирование | При отказе |
| --------- | -------------- | ---------- |
| `GeoDNS / GTM` | Managed-сервис: health checks, веса пулов [^15][^16][^17] | ДЦ убирается из DNS-ответов, новые подключения идут в здоровые ДЦ |
| `Anycast DNS` | Один IP из многих точек присутствия [^83] | Запросы уходят в ближайшую живую точку |
| `L4: IPVS + keepalived` | `N+1`: пара директоров, VIP по VRRP [^93] | VIP за секунды переходит на резервный директор, клиенты переподключаются |
| `NGINX L7` | `N+1`, для strict HA — `N*2` | Клиенты переподключаются на живые узлы |
| `Kubernetes` и stateless-сервисы | `replicas >= 2`, `N+1` узлов [^54] | Под пересоздается, запрос уходит на живой под |
| `SFU` | `N+1` в каждом ДЦ, health checks | Новый SFU и новое медиасоединение (ICE + DTLS) [^84] |
| `Recording workers` | `N+1`, retry, multipart upload [^46] | Незавершенную запись дописывает другой воркер |
| `PostgreSQL auth_pg` | Primary + синхронная standby + 7 реплик, Patroni [^86] | Standby становится primary без потери данных; при отказе всего `DC-US-EAST` дежурный повышает реплику `DC-US-WEST` [^97] |
| `PostgreSQL + Citus` | Координатор + standby в ДЦ, реплика в парном ДЦ | Standby в соседней AZ; при отказе ДЦ дежурный повышает реплику в парном ДЦ [^97] |
| `PgBouncer` | 3 на ДЦ [^32] | Приложение переходит на живой pooler |
| `Redis` | 3 master + 3 replica на ДЦ [^31] | Replica становится master; сессии — повторный логин, онлайн-состояние восстанавливают heartbeat-ы |
| `ScyllaDB` | `RF=3`, `LOCAL_QUORUM` [^33][^80] | Чтение и запись работают при отказе узла |
| `S3-compatible Object Storage` | ≥ 3 копии в 3 AZ `home_dc` [^23][^24] | Файл доступен, незавершенные части дозагружаются |
| Наблюдаемость | 2 узла на ДЦ + 2 центральных | Деградируют только алерты и дашборды |

### 9.2. Отказ целого дата-центра

Худший случай — отказ самого большого ДЦ, `DC-DE-FRANKFURT` (35.69% нагрузки).

| Шаг | Что происходит | Время |
| --- | -------------- | ----- |
| 1 | Monitors GTM фиксируют отказ, `DC-DE-FRANKFURT` убирается из DNS-ответов | ≈ 30 с + TTL 30 с |
| 2 | Новые подключения GTM раздает по `capacity_weight`: сначала `DC-UK-LONDON`, затем `DC-US-EAST`, остальное — по свободной емкости других ДЦ | сразу после шага 1 |
| 3 | Встречи обрываются, клиенты переподключаются со случайной задержкой; подписанный `join_token` проверяется в любом ДЦ, поэтому комната пересоздается в резервном ДЦ | десятки секунд |
| 4 | Дежурный повышает реплику Citus в `DC-UK-LONDON` до primary [^97]; код `de-frankfurt` из `meeting_id` начинает указывать на `DC-UK-LONDON` | минуты, RPO — секунды |
| 5 | Чат и история участников недоступны до восстановления ДЦ или из снапшотов в S3 парного ДЦ | осознанный компромисс |

Емкости хватает: на время инцидента видео ограничивается профилем «high-quality» (1.0/0.6 Мбит/с вместо 2.6/1.8 [^5]), и нагрузка — 41.9% штатного пика при 64.31% оставшейся емкости. Расчет — в [приложении 9](appendix/9-reliability.md).
