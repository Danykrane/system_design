# Ревью работы MeetFlow после защиты

Документ для автора работы: что было правильно, что нет, что исправлено в ветке `review-fixes` и как отвечать на вопросы. Сама работа — [README.md](../README.md). Разбор терминов и логики — [разбор-работы.md](разбор-работы.md).

## 1. Коротко

- Все 6 замечаний ревьюера закрыты; где в README что лежит — в разделе 2.
- Дополнительно найдено и исправлено 17 ошибок и несостыковок (раздел 3). Две из них меняют итоговые числа:
  - **L7-балансировщики считались не той метрикой.** Весь RPS, включая heartbeat, делился на скорость новых TLS-рукопожатий. При этом совсем не учитывалась память под миллионы одновременных WebSocket-соединений.
  - **Пропускная способность SFU не была проверена по CPU.** 10 Гбит/с на 6-ядерный сервер — в 2.5–6 раз выше реальных бенчмарков SFU.
- Итог изменился так: K = 1.5 сам по себе снизил бы стоимость с 800 до ≈ 680 млн ₽/мес, а исправление ёмкости SFU подняло её до **≈ 977 млн ₽/мес (≈ $12.2 млн)**. Структура не поменялась: почти весь бюджет — хранение записей и медиа.
- Все числа теперь считает один скрипт [`resource/calc/meetflow_calc.py`](../resource/calc/meetflow_calc.py). Таблицы разделов 3, 4 и 11 вставлены из его вывода, поэтому суммы по ДЦ сходятся с глобальными значениями.

## 2. Замечания ревьюера

### 2.1. «K = 1.5 сделать»

**В чём была проблема.** `MF_K_PEAK = 3`: пиковый час считался в 3 раза выше среднего. Через пик это раздувало всё: онлайн, RPS, трафик, число серверов.

**Что сделано.** `MF_K_PEAK = 1.5`, всё пересчитано скриптом. Обоснование в п. 2.1: сервис глобальный, часовые пояса сглаживают суточную кривую — когда в Америке день, в Азии ночь.

**Как ответить устно.** «K — отношение пикового часа к среднему за сутки. Для глобального сервиса кривая сглажена часовыми поясами, поэтому взяли 1.5. От K линейно зависят пиковые RPS, трафик и число одновременных соединений. Объёмы хранения от K не зависят — пик меняет скорость, а не суточный объём».

### 2.2. «other_pool не понравился (расписать)»

**В чём была проблема.** 42.5% мировой нагрузки — больше, чем у всех ДЦ, кроме США, — уходило в абстрактный `OTHER_REGIONAL_POOL`. У него не было ни места, ни состава стран, под него нельзя было поставить серверы. Он же был «глобальным fallback» для всех.

**Что сделано** (п. 3.2). Other разложен по макрорегионам прозрачным методом:

1. Латинская Америка — допущение 7.5%: ни одна страна LatAm не входит в топ-5 SimilarWeb, значит, каждая < 3.69%.
2. Оставшиеся 48.08% поделены между EMEA и APAC по пропорции выручки Zoom из годового отчёта 10-K за FY2026 (EMEA 15.8%, APAC 12.1%).
3. Из итогов вычтены уже известные страны. Остаток EMEA — 23.51%, остаток APAC — 11.50%.
4. США разделены на восток и запад по переписи 2020: на регион West приходится 23.7% населения.

Получилось **8 ДЦ** с конкретными городами: Ашберн, Сан-Хосе, Сан-Паулу, Лондон, Франкфурт, Мумбаи, Сингапур, Токио. Для каждого указано, какие страны он обслуживает, его доля нагрузки и резервный ДЦ.

**Как ответить устно.** «Other — это страны вне топ-5. Латинской Америке дали 7.5% — это допущение, ограниченное сверху порогом топ-5. Остаток поделили между EMEA и APAC по пропорции их выручки у Zoom: у этих рынков близкая выручка на пользователя. Для Америк выручку не использовали — в США она на пользователя заметно выше. Каждая группа стран идёт в ближайший по задержке ДЦ. Точные доли уточняются по GeoIP после запуска, а GTM подстраивает веса».

### 2.4. «Где записано в глобальной балансировке — находится точка записи»

**В чём была проблема.** Раздел 3 не говорил, куда идут **записи**. Для `Auth / Users` стояло «любой здоровый ДЦ». Но если писать в `users` можно в любом ДЦ, то уникальность `email` и конфликты одновременных записей не решены.

**Что сделано** (новый п. 3.4). Правило: у каждого объекта одна точка записи.

| Данные | Точка записи |
| ------ | ------------ |
| `users` | один primary на весь мир в `DC-US-EAST` + синхронная standby; в остальных ДЦ — реплики для чтения |
| Всё, что относится к встрече: `meetings`, участники, чат, runtime, записи | `home_dc` встречи. Его код зашит в `meeting_id`, поэтому любой ДЦ знает, куда направить запрос |
| `user_meetings`, список встреч пользователя | пишется в `home_dc` встречи, ScyllaDB асинхронно реплицирует его во все ДЦ |
| `user_sessions` | ДЦ, где был логин; код ДЦ — префикс `session_id` |

Описано, как запрос на запись попадает в чужой ДЦ (gRPC-прокси), что такое read-your-writes и что происходит при отказе точки записи (Patroni, RPO).

### 2.5. Вопрос Быкова: «Пользователь залогинился в США, а потом поехал в Японию»

**Что сделано** (новый п. 3.8): sequence-диаграмма и таблица из 9 шагов.

**Ответ одной фразой.** GeoDNS отправит пользователя в Токио по текущему местоположению. Сессия переносится из США один раз по префиксу `session_id`, перелогиниваться не нужно. Профиль и список встреч читаются из локальных копий. Встречи американских коллег по-прежнему живут в `DC-US-EAST`: `join` проксируется туда, медиа идёт туда же (RTT ≈ 153 мс — в пределах нормы ITU-T G.114). Новые встречи, созданные в Японии, получают `home_dc = DC-JP-TOKYO`. Мигрировать ничего не нужно, потому что в системе нет «домашнего ДЦ пользователя».

### 2.6. «Механизм переключения какой? Anycast или DNS»

**В чём была проблема.** В прошлой версии было противоречие. В п. 3.4 `api.meetflow.example` выбирался DNS по latency, а в п. 3.5 тот же API шёл через Anycast — для одного имени заявлены два механизма. Если DNS возвращает один Anycast IP, ДЦ выбирает BGP, а не DNS.

**Что сделано** (п. 3.5–3.7, 3.9). Однозначный ответ: **DNS (GeoDNS/GTM)**.

- Anycast используется только для доставки DNS-запросов к авторитетным NS-серверам и в CDN для статики.
- Для API, WebSocket и медиа Anycast не подходит, и это объяснено. BGP выбирает маршрут по AS-path, а не по загрузке ДЦ, поэтому весов и drain нет. При перестроении маршрута долгие TCP- и UDP-сессии уходят в ДЦ, где нет их состояния.
- Медиа переключается на уровне приложения: control plane выдаёт новый SFU, клиент делает ICE restart.
- Посчитано время переключения: ≈ 1 минута. Есть клиентский fallback на случай, если резолвер игнорирует TTL.

## 4. Что было правильно и осталось без изменений

- **Методика раздела 2.** Каждая метрика подписана источником и годом, формулы выписаны. Вся арифметика перепроверена скриптом: 30 млн встреч, 16.2 млрд participant-minutes, 11.25 млн онлайн в среднем, 38.88 млрд heartbeat, 0.761 GB на запись, 685.26 PB за 30 дней — всё сходится.
- **Разделение control plane и media plane.** Медиа идёт мимо L7, чтобы не терминировать TLS на десятках Тбит/с и держать встречу на одном SFU.
- **SFU вместо MCU, simulcast/SVC, server-guided ABR** (раздел 7) — стандартные и правильные решения для группового видео.
- **Выбор СУБД под паттерн доступа.** PostgreSQL — где нужны транзакции и уникальность, ScyllaDB — для write-heavy данных без JOIN, Redis — для горячего состояния с TTL, S3 — для файлов.
- **Денормализация и отказ от JOIN** в hot path, read model `user_meetings`, `message_seq` для порядка чата.
- **Индексы, таблица консистентности, идея `home_dc`.** Её не хватало только довести до точек записи и сценариев.
- **Подход к резервированию**: `N+1`, RF=3, WAL/PITR.
